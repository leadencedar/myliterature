## 0. 结论摘要（先读这里）

1. **方向成立，但仍未定稿。** 把默认首页从「居中阅读式正文」改成「章节—正文—本章计划」的创作工作台，是针对「太像阅读器」的正确修正；但设计归档自己也没有把它标为确认（`README.md`、`manifest.json` 均写「待评审确认」）。
2. **资料分两层，只有一层能交付。** v1「留白书写」包是完整交付物（`设计方案.md` + tokens + components + 31 个 SVG + 独立原型 + 验收清单 + 验证记录）；新方向只有一个 235 行的会话原型 HTML 和一份修订说明，**没有令牌、组件规格、页面规格和验收清单**，不能直接施工。
3. **新方向与产品文档有 3 处必须对齐的问题**：写作页信息架构（产品文档把大纲树/章节列表/推演入口/外传都放在写作页，新方向没给这些入口位置）、书架形态与信息项（形态可重设计，但卡片承载的章数/字数/设定数/待确认数不能丢）、AI 生成流程（「整章生成」的注入清单、目标字数、停止/截断/部分结果/继续补写，新原型三段式远少于这些）。详见 §4。
4. **新方向相对 v1 丢了至少 5 项已定义交互**（快速查找、目录固定偏好、保存状态区、切章失败处理、AI 完整状态机），另有 18 条原型退化/实现缺陷（其中 12 类可复现，如空章续写、拼接格式、焦点丢失、aria-live 逐键播报）。是「这一稿没画」还是「方向性取消」，必须在 v2 里逐条回答。详见 §3.1/§3.2。
5. **确实有比现有工程更严格的地方（两处真实缺口）**：① v1 要求「后续编辑存在时，撤销不覆盖当前正文」，现有编辑器是裸撤销栈（`ChapterEditorScreen.tsx:540-548, 602-620`），撤销会直接恢复旧快照；② v1/设计方案要求「AI 采用前检查基准」，现有采用路径只有空结果守卫与不完整稿降级，没有基准比对。这两条设计稿是对的、工程要补。
6. **三栏的行长预算要用「工作台实际宽度」算，不能用固定视口断点。** 原型三栏的固定占用是 2（外框）+180（章节栏）+258（辅助栏）+40（中央内边距）+2（编辑框边框）+42（正文内边距）=**524px**，正文文本宽 = 工作台外宽 − 524；容器 ≤900px 时原型自动降为两栏（固定占用 248px）。扣除本仓库 224px 导航后：视口 1440 → 工作台 1216 → 正文 692px（17px 约 41 字/行，19px 约 36 字）；若再套 `Page` 的 1152px 上限与桌面 padding，正文只剩约 564px。**「≥1400 三栏」不能直接定案**，需要先统一字体、行长目标与是否保留 Page 限宽（见 §3.4）。
7. **工程实现比设计稿成熟的地方不能动**：保存串行队列、退出拦截与草稿导出、AI 采用的三方合并、提案收件箱、摘要/归档链路。UI 改造必须包在它们外面，而不是替换它们。
8. **测试面小，但测试不能证明布局，也不能当作零回归依据。** 全仓库 132 个测试文件 / 2478 个用例（静态统计，本轮未重跑全套）；jsdom 不加载 CSS（`vite.config.ts:113-119`），三栏这类纯布局不会被现有测试拦截——这只说明测试没有覆盖布局，不代表改造零成本。真正的成本在编辑器承载方式、`role=dialog`、文案与四态状态（粗估 30–60 个用例，集中在写作域，见 §6.6）。
9. **评审结论：方向可以批准，规格不能批准；决策不要一次全抛给用户。** 工程路径先依据现有结构收敛，只把真正影响创作习惯的选择（字体、导航密度、章内任务方式、命名）做成可比界面让作者拍板（§9 已分 A/B 类）。实施按「令牌→空壳验证→编辑器承载验证→右栏→数据→移动端」推进；不建议按原型 HTML 直接改工程。

### 2.1 总体评价

**做对的（应保留）**

- 把「默认状态」当作设计对象：先定义作者一整天的工作台，再谈专注与阅读，方向正确且比 v1 更贴近产品定位。
- **真正的增量是「章级任务层」而不是三栏。** 本章目标、场景节拍、作者备忘补上了「大纲（写之前）」与「章节摘要（写之后）」之间的空档；本仓库 `Chapter` 只有 `content/wordCount/status`，缺写作中的任务载体——这个想法比布局更有长期价值，也最需要先定数据归属。
- 「同一份章节目标，不建重复目标」「采用前检查基准」「空建议不能采用」等约束，与本仓库的数据一致性原则一致，属于可以直接沿用的设计资产。
- 示例内容用「进行中的初稿」呈现（写到一半、节拍 1/3、待改备忘），是有效的评审道具，v2 应保留同一条示例贯穿所有状态。

**不足的（需在 v2 解决）**

- 新方向只有「一张图 + 一段说明」，没有令牌、组件、状态和验收清单，评审通过也无法交接。
- 默认布局与降级规则没有数值（宽度阈值、正文最大宽度、断点归属），而这是三栏方案唯一的硬约束；实测默认三栏反而是全篇行长最差的形态。
- AI 部分与产品已有能力脱节：三段式写得像完整流程，实际只是一次固定示例生成；真正的注入清单/字数/截断状态全部缺失，等于要求回退已交付能力。
- 与产品文档的信息架构没有对账，容易出现「设计上更顺、产品上重复入口」的情况。
- 文档与原型已经出现「说了但没做」的分叉（保存状态、状态转换、焦点保持），评审不能把文档措辞当作已实现事实。

### 3.4 响应式与可访问性风险（含实测与复核修正）

**先定义口径，再比较宽度**（v1.0 曾混用「textarea 边框盒宽」与「正文文本宽」，相差 42px；复核已统一为文本宽）：

- 工作台外宽 **W = 浏览器视口 − 224px 全局侧边栏**（`src/index.css:38`）。若写作页仍用 `Page width="wide"`，再加 `max-w-6xl=1152px` 与 `lg:px-8` 限制，内容区 **W' = min(W, 1152) − 64**（`src/ui/Page.tsx:17-20,45-56`）。
- 原型三栏固定占用 = 2（外框）+180（章节栏）+258（辅助栏）+40（中央内边距）+2（编辑框边框）+42（正文内边距）= **524px**，所以**正文文本宽 = W − 524**。
- 容器宽度 ≤900px 时原型自动降两栏（章节 170 + 中央内边距 16），固定占用 = 2+170+32+2+42 = **248px**，所以**正文文本宽 = W − 248**。
- 下表是 CSS 静态估算（未计滚动条、浏览器缩放与字体差异），**不是新一轮浏览器实测**；本机 Chromium 此前量到的是 textarea 边框盒宽（比文本宽多 42px）。

| 场景                      | 工作台外宽 W | 实际布局              | 正文文本宽 | 17px 字数/行 | 19px 字数/行 |
| ------------------------- | ------------ | --------------------- | ---------- | ------------ | ------------ |
| 原型独立页 1440（无侧栏） | 1440         | 三栏                  | 916px      | ≈54          | ≈48          |
| 原型独立页 1024（无侧栏） | 1024         | 三栏（>900）          | 500px      | ≈29          | ≈26          |
| 本仓库 1440（仅扣侧栏）   | 1216         | 三栏                  | 692px      | ≈41          | ≈36          |
| 本仓库 1400               | 1176         | 三栏                  | 652px      | ≈38          | ≈34          |
| 本仓库 1280               | 1056         | 三栏                  | 532px      | ≈31          | ≈28          |
| 本仓库 1200               | 976          | 三栏                  | 452px      | ≈27          | ≈24          |
| 本仓库 1024               | 800          | **两栏**（≤900 容器） | 552px      | ≈32          | ≈29          |
| 本仓库 1440 + Page wide   | 1088         | 三栏                  | 564px      | ≈33          | ≈30          |
| 本仓库 1024 + Page wide   | 736          | 两栏                  | 488px      | ≈29          | ≈26          |

**修正与结论**：

1. **「原型在 1024 视口仍三栏、正文只剩 318px」是 v1.0 的错读。** 1024 视口扣侧栏后工作台 800px，容器 ≤900 已触发两栏；三栏只在容器 >900 时成立。318px 只能作为「禁止在 1024 强制三栏」的反例，不能称为原型实际行为。
2. **40 字/行与字体绑定**：17px 时 40 字 ≈ 680px，19px 时 ≈ 760px。于是：
   - 三栏 + 40 字：需 W ≥ 1204（17px）或 ≥1284（19px），即视口约 ≥1430 / ≥1510，且**不能保留 Page 的 1152px 上限**（保留时文本宽最多 628px，约 37/33 字）。
   - 两栏 + 40 字：17px 需 W ≥ 946（视口约 ≥1170），19px 需 W ≥ 1026（视口约 ≥1250）；若保留 Page 上限，1440 视口下两栏文本约 822px，可用正文 `max-width` 680/760 收口。
3. **不要写死视口断点**，改成「工作台宽度 + 全局导航形态」的规则：
   - 全局导航常驻且允许写作页全宽：W ≥ 1284 → 三栏；否则两栏（右栏抽屉/浮层）。
   - 全局导航在写作路由折叠：1200–1400 视口也可支撑两栏 40 字。
   - W < 800 或视口 <1024：单栏 + 任务视图。
4. `Page` 是 `min-h-dvh` + 粘性头 + 文档滚动（`src/ui/Page.tsx:31-57`），三栏需要 `h-dvh overflow-hidden` + 栏内独立滚动，**写作页必须脱离 `Page` 骨架**，同时保留 `main#main` 与「跳到主内容」（`AppShell.test.tsx` 有断言）。
5. 编辑器现在是 `role="dialog" aria-modal` + `fixed inset-0`（`ChapterEditorScreen.tsx:755-765`）。桌面内嵌、手机全屏若只用一套 DOM + CSS，`aria-modal` 与焦点陷阱无法靠 CSS 切换，需要单独决策（§9 D11）；只改外层 grid **不会**让 fixed 编辑器自动变成中栏。

其他风险：

- **R-宽度口径**：先定字体（17/19px）与行长目标（是否严格 40 字），再定三栏阈值；否则三套数字互相打架。
- **R-焦点**：面板/视图切换会重建 DOM 并丢焦点（原型探针已复现）；**勾选资料与节拍不重建、焦点保留**（复核探针确认）。内嵌后要保证切面板不重建编辑节点、焦点归还。
- **R-焦点样式**：原型没有自定义 `:focus-visible` 令牌，依赖浏览器默认——不能据此断言「完全没有焦点轮廓」，但也无法保证对比度与一致性；v2 必须有焦点令牌（v1 是 2px + 3px offset）。
- **R-读屏结构**：工作台视图 `h1/h2=0`；右栏 tab 是 `aria-pressed` 按钮而非 `tablist/tab`；手机面板切换无 live 通知。
- **R-键盘与输入法**：产品明文「输入法组字时 Esc 不生效」，编辑器刻意不绑 Esc（`ChapterEditorScreen.tsx:486-505`）；设计方案 §4.3「Esc 关闭最上层」只能落在面板层实现。
- **R-缩放**：200% 缩放下 1440 视口 ≈720 CSS px，落入两栏/单栏区间；需要专门验收（静态推算，未实测）。
- **R-触控**：原型桌面按钮 34px、小按钮 30px、select 30px，低于 v1 的 36px 与工程 `sm` 36px；`pointer:coarse` 只把 button 提到 44px。
- **R-滚动**：内嵌后要重做滚动容器，并保证 `pagehide`/卸载冲刷仍然生效（`ChapterEditorScreen.tsx:387-418`）。

### 5.2 差异结论与迁移建议

1. **新方向没有自己的令牌**，原型直接沿用了 v1 的棕色系，但布局宽度（180/258）和字号行高（17/1.85）又和 v1（200/320、18/2.05）不一致。这是 v2 必须解决的第一件事：要么以 v1 令牌为基线更新，要么以本仓库 `@theme` 为基线，**不能三套并行**。
2. **新旧版本迁移没有显式声明（文档却写「颜色可继续参考」）**：背景 `#FAF9F6→#F5F4F0`、副标题高度 28→23px、正文 `18/2.05→17/1.85`、栏宽 `200/320→180/258`、控件 `36→34/30`、圆角 `5·8·9→5·6·9`。v2 必须出逐项映射表并说明取舍，否则「复用 v1 素材」会带着旧规格进工程。
3. **主色是品牌级决定，不是页面级决定**。本仓库的朱砂橙贯穿导航高亮、按钮、focus 环、错误提示（`--color-seal`）；改成棕色需要全站回归。建议 v2 明确二选一，并给出切换清单。
4. **正文默认字体与产品决策冲突**。产品文档 §5.4 的桌面阅读体验建立在宋体 + 限宽上；设计稿主张黑体，合理做法是做成「正文字体偏好」（宋体/黑体），默认保持宋体，而不是改默认。
5. **圆角与控件高度差异属于低风险**，可在 v2 统一到 5/8/9 与 36/44，但要注意本仓库已有 `rounded-xl/2xl` 的视觉一致性。
6. **本仓库现存两个对比度问题会被 v2 继承**：`ink-300`（`#98a1ae`）用于占位/加载文字，对纸白约 2.55:1；`seal`（`#d9561f`）用于 11px 选中导航文字，约 3.86:1——都低于 AA 的 4.5:1。v2 做令牌时应一并修正，而不是只复验新配色。
7. **新原型的对比度本身不差**：浅色正文约 12.2:1、次级 5.46:1（背景）/5.81:1（纸面），深色 7.3–12.4:1；但 `--wa-line` 只有约 1.26:1（仅作分隔线可接受），且焦点色未纳入检查。v1 的 20 组数值检查需要按新令牌重跑。

### 5.3 深色模式

v1 有完整深色令牌（`tokens.css:60-107`），原型用 `light-dark()` 自动跟随；但本仓库目前没有任何 `dark:` 样式（全量 grep 为 0），PWA 主题色固定为深色。若采纳深色模式，工作量是 14 个使用 `lg:` 的页面 + 全部基础件的系统级回归，应作为独立里程碑，不要混进 UI 重构。当前状态是「技术上有、规格上没有、验收上不算」——v2 必须明确三选一：纳入并给样张、不纳入并删掉 `light-dark()`、或标注「非本轮承诺」。

## 6. 工程现状盘点（映射基线）

### 6.1 路由、导航与布局策略

- 路由：`/`（书架）、`/knowledge`、`/write`、`/write/scenario/:scenarioId`、`/plan`、`/settings`（`src/app/AppShell.tsx:51-70`）。作品 id 不进 URL，由全局当前作品驱动。
- 导航：5 个 Tab 唯一事实源在 `src/app/navigation.ts`；窄屏底部 Tab 栏，`lg` 以上左侧边栏（`AppNav.tsx:18-29`）。
- 页面骨架：`Page`（粘性标题 + 限宽内容列，默认 `max-w-3xl`）= `src/ui/Page.tsx`；桌面内容列 768px，与「三栏工作台」不是一套结构。
- 响应式：**单套 DOM + 媒体查询**，`lg` 是主分界（14 个文件使用），`md` 用于平板/列表多列，`xl` 只在知识库/书架卡片网格出现。
- 结论：三栏如果直接塞进 `Page` 结构，会和现有「居中限宽内容列」打架；需要新的页面骨架（或写作页专用骨架）。

### 6.2 写作主链路

```
AppShell：底部 5 Tab（<lg）/ 左侧 224px 侧边栏（lg+），单套 DOM
└─ WritingPage（Page 骨架，文档滚动页）
   ├─ 待确认提案（有 pending 时）
   ├─ 互动推演入口卡
   ├─ 全书进度（已写/目标/章节数）
   ├─ 大纲（OutlineTreeView；点节点开 OutlineNodeSheet）
   ├─ 章节正文（ChapterListItem 列表 → 打开编辑器）
   │   └─ 导出入口
   ├─ 外传（SideStorySheet）
   └─ ChapterEditorScreen（role="dialog" aria-modal，fixed inset-0 z-50）
       ├─ 返回 / 标题 input / 删除；保存状态、撤销、翻译、规范检查、文风检查、摘要、草稿↔完成
       ├─ 正文 textarea（reading-column，46rem，桌面 19px/2.1）
       ├─ 底部：加工这一段 / 生成本章
       └─ Sheets: GenerateChapterSheet / ReviseSheet / StyleCheckSheet /
          NormCheckSheet / TranslateSheet / ChapterSummarySheet /
          ArchiveInboxSheet / ConfirmDialog
```

关键事实：

- 编辑器是**全屏模态**（`ChapterEditorScreen.tsx:755-765`），离开靠 `closeWithFlush`（保存成功才关，失败进入退出拦截，`:513-533`）。
- 保存是**串行队列 + 800ms 防抖 + 卸载/pagehide/visibilitychange 冲刷**（`scheduleSave`、`saveChainRef`、`pendingRef`，`:37,289-297,373-378,387-418`），状态 4 态（`SAVE_LABELS`，`:50-55`）。
- 章节切换靠 `key={chapter.id}` **强制重挂**编辑器来重置草稿态（`WritingPage.tsx:477-497`）；内嵌常驻后必须换成显式 reset + 切章前 flush。
- AI 采用走 `commitContent`：压入撤销栈、立即落盘（`:540-548`）；但既没有「采用前基准比对」，撤销也没有「后续编辑保护」（`:602-620`）。
- 状态只有「草稿 ↔ 已完成」二态（`:871-895`）；转 `done` 触发后台摘要/归档，**非测试代码里 `status === 'done'` 共 22 处、8 个文件**。
- 摘要/归档是「标记完成 → 后台生成提案」链路，与 `done` 状态强绑定。

### 6.6 测试耦合与改动影响

> 说明：以下测试数量来自静态统计（grep 计数），本轮未重跑全套测试；30–60 个用例与工期是粗估，不作为承诺。

- 全仓库 **132 个测试文件 / 2478 个用例**（`src/**/*.test.ts(x)`），其中 `*.test.tsx` 45 个、带 DOM 查询的 44 个。
- **关键利好**：`vitest` 配置 `css: false`（`vite.config.ts:113-119`），测试里没有 `toHaveClass`/`getComputedStyle` 断言。因此**纯 CSS 的三栏布局变更理论上 0 个用例破坏**——反过来说，也没有任何测试能证明布局正确，必须另做浏览器验收。
- **会破坏用例的是 DOM/角色/文案变更**：
  - 编辑器 `role="dialog"` 命名断言 5 处 / 4 个文件（如 `WritingPage.test.tsx:557,690`、`ChapterEditor.test.tsx:1007`）；
  - 「返回」按钮名 12 处 / 7 个文件；「章节正文」textarea 的 aria-label 被 79 处查询依赖（19 个文件出现该词）；
  - 章节列表可访问名「继续写第…」19 处 / 11 个文件——若左栏与页面保留两份列表会出现多匹配；
  - `WritingPage.test.tsx`（约 119 处 DOM 查询）与 `ChapterEditor.test.tsx`（约 229 处）是最重的两个文件；渲染 `WritingPage` 的测试文件共 14 个（含 m1/m3/m4 的 UI e2e）。
- **四态状态 + 章节栏 + 外传重排**：预估需要改 **30–60 个用例**，占全量 2478 的 1.2%–2.4%，但集中在写作域，属于「必须同步改、不能靠忽略」的部分。
- **CI 约束**：`format:check` 会拦住未格式化的批量改动（`.github/workflows/ci.yml:37-38`），大范围类名/令牌重命名要先过 Prettier。
- **建议**：UI 重构单独分支，先冻结数据层与测试基线；不要和同期数据可靠性修复混在一个 PR。

## 11. 若确认方向，建议的实施路径

顺序原则（按复核意见重排）：**先规格与口径，后布局；先空壳验证，再尽早验证编辑器承载方式，最后挂接真实右栏与数据**。测试环境不加载 CSS，只说明现有测试无法证明布局正确，不能据此宣称「三栏改造零回归成本」。

**阶段 0：规格与决策（约 1 周）**

- 拍板 §9 的 B 类决策；A 类由工程给默认方案随 v2 评审；产出 §10 的 P0 材料；同步更新 `docs/产品文档.md` 的相关条目。
- 验收：字体/行长/工作台宽度口径统一；令牌一套；编辑器承载方式（dialog/region、内嵌/全屏）有结论；原型缺陷清单已转成 v2 条目。

**阶段 1：令牌 + 空壳布局验证（1–2 周，可回滚）**

- 先把颜色/圆角/字号/间距收敛为语义令牌，保留旧名做别名；补 success/warning/danger/focus/motion；同时修 `ink-300`/`seal` 两个现存对比度问题。
- 写作页做**空壳** grid：章节栏 + 中栏占位 + 右栏占位，**暂不动编辑器容器**；正文区加与字体匹配的 `max-width`（17px→680，19px→760）。
- 验收：1024/1200/1280/1440/1500/390 真实浏览器测工作台宽度与行长；现有测试全绿（仅说明未破坏既有行为，不证明布局）；补浏览器宽度验收脚本。

**阶段 2：编辑器承载方式最小验证（1–2 周，风险最高）**

- 先验证最小问题：桌面内嵌 vs 保持全屏；若内嵌，抽 `ChapterEditorBody`，处理 `role=dialog/aria-modal`、焦点陷阱、滚动容器、退出拦截与切章冲刷。
- 切章：可保留 `key={chapter.id}` 重挂（复核认为可行），也可显式 reset；以保存协调、选区恢复、生命周期为准，不预先强制一种。
- 验收：切章不串稿；退出拦截可用；`ChapterEditor.test.tsx` 回归；键盘/输入法不冲突。

**阶段 3：右栏挂接（1–2 周）**

- 右栏先接 `synopsis`（有节点时）与 `linkedEntryIds` 资料，再挂 AI 入口（复用 `GenerateChapterSheet`/`ReviseSheet`，保留注入清单/目标字数/截断等完整流程）。
- 验收：目标编辑不抢焦点；写后 `invalidate` 不闪烁；大纲/右栏一致；AI 完整能力未缩水。

**阶段 4：数据增量（按 D2/D3/D4/D12，1–2 周）**

- 首轮默认不新增概念：保留 `draft/done` + 空白辅助；可勾选节拍不做；备忘仅在确认价值后加 `Chapter.note`。
- 若新增：schema + 备份快照 + DB 迁移 + 提案枚举 + 导出 + 测试一次做完。
- 验收：旧备份可恢复；提案采用不受影响；摘要/归档链路无回归。

**阶段 5：移动端任务视图（1–2 周，按 D10）**

- 保留底部操作栏（目录/上下章/AI）；任务切换放次级位置；AppNav 在写作路由的处理方式先定。
- 验收：真机软键盘、安全区、系统返回、Tab 顺序、44px 触控；「边写边勾节拍」是否有同屏方案。

**阶段 6：暗色 / 专注 / 查找（按 D7/D8 独立里程碑）**

- 查找拆两层：章节内搜索/跳章优先（高频写作便利）；跨章节+设定+命令的全局面板后做。
- 暗色依赖语义令牌；专注是布局状态；每一步单独分支、单独验收。

**风险闸门**：任一步若需要改 `src/data`、`src/proposal`、`src/llm` 的契约，暂停并回到 §9 决策；不允许「顺手改一点」。CI 四关（format/typecheck/test/build）在每一步都必须全绿。
