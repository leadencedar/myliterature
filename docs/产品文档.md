## 1. 一句话定位

一个 AI 小说创作工作台：**从一句话点子长出可续写的知识库，再按章把小说写下去。**

一套代码同时是移动端应用和桌面端应用 —— 同一个地址，窄屏是底部 Tab 的移动端形态，宽屏是左侧边栏 + 多列 + 右侧抽屉的桌面形态。

不是聊天框套个壳，也不是通用写作助手。它假定你要写的是一部**有连续性的长篇**，并围绕「几十万字之后 AI 还记不记得前面发生过什么」这个唯一真正难的问题来组织所有功能。

---

## 2. 要解决的问题

用通用聊天工具写长篇，三件事一定会崩：

| 问题            | 表现                                                            | 本产品的答案                                         |
| --------------- | --------------------------------------------------------------- | ---------------------------------------------------- |
| **失忆**        | 写到第 30 章，AI 忘了主角的软肋、改了世界观规则、把埋过的坑忘掉 | 知识库 + 摘要链，按需注入而不是把全文塞进 prompt     |
| **设定散落**    | 设定散在几十段对话历史里，翻不到、改不动、互相矛盾              | 结构化知识库：分类 + 字段模板 + 别名，可增删改查     |
| **AI 越帮越乱** | AI 自作主张改了设定，用户发现不了，错误一路滚下去               | **所有 AI 产出必须经用户确认才落库**，架构上的单行道 |

还有一个决定这个产品有没有人用的问题：

| 问题               | 表现                                                             | 本产品的答案                                  |
| ------------------ | ---------------------------------------------------------------- | --------------------------------------------- |
| **存量作者用不上** | 已经写了四十万字，知识库是空的，任何「从零立项」的工具都帮不了他 | 旧稿导入 + 反向提取：读正文倒推出设定与摘要链 |

## 3. 目标用户

**主要用户：已经在写、或真的准备开始写长篇的人。**

- 连载中的网文作者：更在意节奏、稳定产出、不崩设定
- 写严肃／类型文学的创作者：更在意文风与结构，把 AI 当草稿工与资料员
- 有存量旧稿的作者：先要把几十万字的设定整理出来，才谈得上续写

**明确不针对**：想看 AI 一键生成整本小说的人。本产品的每一步都要求用户确认与修改，它假定作者才是作者。

---

## 4. 核心价值主张

1. **设定不会丢。** 世界观、人物、伏笔是结构化数据，不是聊天记录。
2. **长篇不会漂。** 每章写完提炼摘要与未收束伏笔，后续章节只注入摘要，成本可控、记忆不断。
3. **AI 不会越权。** 生成结果一律先成为「待确认项」，可逐字段修改、可还原、可忽略。
4. **旧稿能接上。** 存量作品导入后反向提取，补完知识库直接续写。
5. **作品能带走。** 正文导出、全量备份，随时离开这个工具。
6. **互动能沉淀。** 把主角放进世界观里一步步选择（互动推演），走出来的一条世界线可以整理成大纲与章节，再照常「写这一章」。这是它和只管陪聊的角色扮演应用的区别：玩过的东西会变成作品。

## 5. 产品原则

这五条在实现里是硬约束，不是口号。

### 5.1 AI 产出必须经用户确认

所有生成结果（设定条目、大纲、摘要、文风档案、全书进展）都先变成**提案**，进入待确认区。用户可以整批采用、逐条采用、逐字段编辑、逐字段还原、忽略。

例外有三类：**正文散文**、**AI 精简后的写作规范**，以及**互动推演的沙盒内容**（每一步的情节、世界线差异、前情摘要）。三千字的整章做字段级 diff 不提供任何信息，所以正文走「可编辑预览 → 采用 / 追加到末尾 / 放弃」，而不是提案管道。精简后的写作规范同样没有字段结构，走「可编辑预览 → 另存为新规范 / 放弃」；另存不覆盖原文，原规范自动停用、正文不变。作者自己写、粘贴、上传的写作规范与一句话立项同理，不是 AI 产出，直接保存。「按规范检查」只在会话里展示提示、不写任何数据，所以不涉及确认管道；采用其中的建议走段落加工的可编辑预览。结构化数据一律走管道。

推演沙盒为什么可以不逐步确认（见 6.8）：

1. **5.1 防的是「AI 越权改了作品」**：设定、大纲、摘要这些会被后续所有生成读到的数据，被 AI 悄悄改了作者发现不了。沙盒内容只通过两条**已确认**的通道影响作品：①「提升为世界观」提案；②「沉淀」—— 作者先在大纲提案里确认这段路径的分章，之后整章生成才会把对应步骤的原文与状态作为**生成材料**注入，产出的正文仍走可编辑预览。除这两条之外，没有任何链路读取沙盒：段落加工、摘要、提取、检查、翻译的提示词都看不到它，没有沉淀的作品连整章生成也看不到它；世界观条目一个字都不会被推演改动。
2. **作者每一步都在做决定**：推进本身就是作者的选择；不满意就回退走另一条，原线保留但不影响新线 —— 回退就是「忽略」。
3. **全部可见、可改、可删**：每一步的差异、被丢弃的内容、前情摘要都在「本线状态」里，作者能逐条编辑删除；改了前面某一步，后面的步骤会提示「生成时依据的是旧事实」。
4. **出沙盒只有两个口，都经确认**：提升 → 条目提案（字段级 diff）；沉淀 → 大纲提案；之后的正文 → 可编辑预览。
5. **每一步都弹提案会毁掉游戏节奏**：等于每几百字确认一次结构化 diff，和「整章做字段级 diff 没有信息量」是同一个理由。每一步的情节是游戏过程本身，不是作品正文。

### 5.2 宁可少记，不要记错

- 提取出的条目分类对不上 → 整条丢弃，而不是塞进错误分类
- 模型给的出场角色名匹配不到已有条目 → 丢弃，而不是造一个不存在的引用
- 模型输出的字段名不在分类模板里 → 丢弃，因为它在界面上没有对应表单，存了等于看不见
- 互动推演里模型报告的世界线变化同样过一道筛：改写**锁定（底层）字段**的、指向找不到的条目或模板外字段的、给**世界规则**类条目（世界观设定分类）记死亡、被毁、被封印等处境的、新条目分类对不上或与已有条目重名的，一律丢弃，并在那一步上可见地提示「这一步有 N 处变化没有记下」。规则被「摧毁」等于绕过锁定，所以世界规则不会死

错误数据比缺失数据难收拾得多。

### 5.3 合并只补不删

反向提取命中已有条目时，合并规则是固定的：列表字段取并集、原值为空采用新值、**新值为空保留原值**、两边都有值取新值并标为改动交用户裁决。

「模型这次没提到某个字段」不等于「该字段应被清空」——这是反向提取场景最容易造成数据损失的地方。

### 5.4 两端都是第一等公民，不做「缩小版」也不做「拉宽版」

写小说这件事在手机和电脑上都会发生：地铁上想到一个设定要马上记下来，正经码字还是坐在桌前。所以两端都必须是认真做过的形态，而不是其中一端的凑合。

移动端的决定：

- 全屏面板而不是抽屉：写作需要尽可能大的可视区域
- 底部抽屉而不是居中弹窗：贴近拇指，键盘弹出时内容不被顶飞
- **排序用按钮而不是拖拽**：移动端嵌套树拖拽难瞄准，且读屏用户完全用不了
- 防抖自动保存 + 实时保存状态：移动端随时被来电或切后台打断，指望用户按保存不现实

桌面端的决定：

- **正文限宽约 40 个汉字一行**。让正文铺满 1920px 是桌面端最常见的错误，一行八十多个汉字，眼睛回到行首时会丢行
- 底部抽屉换成右侧抽屉、确认框换成居中小窗。底部抽屉在宽屏上会变成贴着屏幕下沿的横带，视线要从页面中央一路扫到底
- 焦点环、hover、手型光标、`⌘/Ctrl + S`、「跳到主内容」—— 这些在触屏上无意义，在桌面上缺一个都显得没做完
- **`Esc` 在输入法组字时不生效，章节编辑器不绑 `Esc` 返回**。中文输入法用 Esc 取消候选词，写作时这个键一分钟按好几次

**实现上是单套 DOM + CSS 断点，不是两套界面。** 按屏幕宽度渲染两棵组件树会让读屏读到两遍内容、让自动化测试同时看到两份控件，而且两条分支必然随时间漂移。底部 Tab 栏和左侧边栏是同一个 `<nav>`、同一批链接。

### 5.5 不制造焦虑

- 「今天还没写」不让连续天数归零——周期还没过完
- 欠账只回看最近 30 个周期——一个永远在变大的负债数字只会让人关掉页面
- 备份提醒攒够字数才提，可以「以后再说」安静一周

## 6. 功能范围

### 6.1 书架

多作品管理。卡片展示章节数、总字数、设定条目数、待确认项数量。有「当前作品」的概念，其余 Tab 都针对当前作品。

攒够字数且没备份过时，书架顶部出现一条可忽略的备份提醒。

### 6.2 知识库

**一句话立项**：输入「我想讲一个什么故事」+ 篇幅（短篇 / 中篇 / 长篇）→ 一次生成世界观设定、主要人物、全书大纲，全部作为提案等待确认。

**结构化条目**：固定大类 + 自由条目。内置「世界观设定」「人物」两类，各带字段模板（如人物有身份／外貌／性格／目标与动机／软肋与恐惧／关系网／说话方式／成长弧线）。可新建自定义分类，也可一键套用预置模板（势力 / 地点 / 道具 / 伏笔 / 时间线）。

条目支持别名（反向提取做重名匹配的关键）、核心设定标记（每次生成强制注入）、软删除与回收站、全字段搜索。

**作用范围与可变性**（给互动推演用，见 6.8）。世界观条目记的是**底层**，推演里发生的变化记在**世界线**上，两层分开。条目因此多两个属性，都在条目编辑里默认折叠的「互动推演设置」中：

- **作用范围**：「通用」（默认，所有世界线和正文写作都看得到）或「仅限推演」（只在选中的推演里存在，可写登场条件；在推演页的「本线状态」里还能设成「只从这一步起出现」）。限定条目在知识库里照常列出，带「限定 · 推演《X》」徽标，但**不进任何现有写作链路的提示词**：没有推演的作品，所有提示词与之前逐字节相同。推演里新建的主角就是一条限定到该推演的人物条目；想让他成为全书人物，把作用范围改成「通用」即可（作者直接编辑世界观，不需要提案）。
- **可变性**：按**字段**而不是按条目。一个人物的「身份」会因为背叛而变，「说话方式」却不该被一条世界线改掉 —— 同一个条目里两种需求并存，按条目定只能二选一。解析顺序：条目的逐字段覆盖 → 分类模板的「世界线可改写」开关（分类管理里） → 内置默认 → 可变。旧作品没存这个属性的分类按内置默认算，不需要迁移。

| 分类              | 锁定（底层）               | 可变                                     | 为什么                                                       |
| ----------------- | -------------------------- | ---------------------------------------- | ------------------------------------------------------------ |
| 世界观设定        | 定义、运作规则、限制与代价 | 对剧情的影响                             | 规则与代价是世界的物理；影响会随局势变                       |
| 人物              | 性格、软肋与恐惧、说话方式 | 身份、外貌、目标与动机、关系网、成长弧线 | 口吻与性格是「同一个人」的辨识；性格的变化应体现在成长弧线里 |
| 势力              | 简介                       | 诉求、实力与手段、弱点                   | 势力会兴衰、换目标                                           |
| 地点              | 简介                       | 氛围、叙事作用                           | 地点会被毁、被占，用状态 + 氛围表达                          |
| 道具              | 简介、能力与规则、代价     | —                                        | 道具规则同世界规则                                           |
| 伏笔              | 埋设内容                   | 预期收束、状态                           | 埋了什么是事实，怎么收是变数                                 |
| 时间线            | 时间、事件                 | 后果                                     | 已发生的事不能被改写，后果可以                               |
| 自定义分类 / 字段 | —                          | 全部                                     | 不知道语义时不替作者加限制                                   |

预置模板（势力、地点……）只在分类名没改过时按上表取默认；改了名就回到「不知道语义 → 可变」。名称、别名、一句话摘要不是模板字段，世界线不能改。

**从世界线提升为世界观**：推演里的变化只有两种能提升成全书设定 —— 对**可变**字段的改写（生成只改这一栏的条目提案）和本线新出现的条目（生成新建提案；知识库里已有同名通用条目时改成合并提案）。都走知识库顶部的待确认区，确认前世界观不变。不能提升的：锁定字段（锁定的意思就是世界线不能改它，借提升改等于绕过锁定，要改请直接编辑条目）；状态、主角状态、事件与标记（某人在这条线上死了是这条线的剧情，不是全书设定，要写进全书请沉淀成章节）。提升后，原线后续的变化继续作用在这条世界观条目上，兄弟分支看到的是它的世界观原文。

**风格档案**：每本书一份，三个正交维度——

- 文体取向：网络文学 / 严肃文学 / 类型文学，各带子类
- 创作方法论：网文节奏结构 / 三幕式 / 雪花法 / 英雄之旅 / 起承转合·章回体（决定大纲的组织方式）
- 名家风格参考：11 位已故经典作家（鲁迅、张爱玲、老舍、沈从文、曹雪芹、金庸、古龙、海明威、契诃夫、卡夫卡、马尔克斯），可多选并调强度

也可以贴一段自己的文字，让 AI 提炼成自定义文风档案。**从旧稿导入的作品不必手动挑** —— 导入流程会从稿件里归纳文风与文体取向，作为待确认项交给作者（见 6.5）。

**文风锚点与漂移检查（M4）**：整章生成会自动从同一条线更早的已完成章节里取开头约 600 字，作为「文风锚点」放进稳定前缀（风格档案之后、写作规范之前），在「本次注入」清单里显示章节来源与 token；第一章或没有更早正文时不带。它只用于对齐句式、节奏与叙述距离，明确要求不要照搬其中情节。

章节编辑器另有 **「检查文风」**：一次结构化调用读风格档案 + 锚点 + 本章正文，输出整体判断与最多 5 条问题（维度 / 差异程度 / 逐字原文 / 与锚点的差异依据 / 建议）。它**只诊断，不改稿、不生成提案、不落库**，与「按规范检查」互补：一个看语感是否漂，一个看作者定的规矩是否被违反。

> **为什么不做 AI 自动润色**：文风是作者最不愿被机器替改的部分；自动压缩/润色会改掉句子里的选择。把「漂没漂、漂在哪」指出来，改不改由作者决定。

> **为什么只收已故作家、且只存风格特征而不存原文**：版权是硬线。档案里存的是「句式节奏 / 意象偏好 / 叙述距离 / 对话风格 / 修辞习惯 / 词汇色彩 / 需要避免」七个维度的文字描述，prompt 里明确要求「据此把握语感，而不是模仿任何具体作品的文句」。塞作品片段进 prompt 既有版权风险，生成结果也更不稳定。

**写作规范**：作者给本作定下的创作约束与项目说明，比如时间截面与冻结信息、与原作的差异及其后续影响、信息分层（谁知道什么）、命名与合并规则、生成边界。一本书可以有多份，每份是「标题 + 原文」，可以启用 / 停用、上下移调整顺序，并选择作用范围（多选，默认全开）：

| 作用范围 | 覆盖的任务                       |
| -------- | -------------------------------- |
| 写正文   | 整章生成、段落续写 / 改写 / 扩写 |
| 规划     | 一句话立项、细化大纲             |
| 章节摘要 | 标记完成后的摘要与伏笔           |
| 提取设定 | 导入旧稿与世界观设定时的反向提取 |
| 检查     | 章节编辑器里的「按规范检查」     |
| 互动推演 | 推演每一步的情节与选项、收尾     |

「互动推演」是后加的第六项。已有的规范只有在原来五项全开时才自动补上它：五项全开是默认值，作者没碰过，含义就是「处处适用」；收窄过作用范围的是作者做过的选择，自动加新范围会违背它。新建的规范默认六项全开。旧备份导入时按同一条规则补。

区块在知识库「风格档案」之后。可以新建后粘贴、从 `.txt` / `.md` / `.rtf` 文件新建（编码自动识别，RTF 自动提取纯文本，读入后先进编辑面板，点保存才落库），也可以在编辑面板里上传文件追加到末尾。单份上限 60000 字。列表和编辑面板显示每份的 token 估算：单份超过约 2000 tokens 标「较长」；启用中的写正文规范合计超过约 6000 tokens 时区块顶部提示；正文里链接超过 5 个时提示来源表通常不必进提示词。

> **为什么不是世界观条目**：条目告诉模型「这个世界能发生什么」，规范告诉它「这本书选择发生什么、现在进行到哪里、按什么规矩写和整理」。条目按实体拆分、按名称合并、由反向提取产出；规范是一份完整的文档，不拆分、不合并、不被提取。把「本作开场时期之后的人物一律冻结」写成一条设定，它会和真实的设定条目混在一起被预选、被合并，约束也就失效了。两者冲突时以规范为准，注入的文案里明说这一点。
>
> |      | 知识库条目                            | 写作规范                                               |
> | ---- | ------------------------------------- | ------------------------------------------------------ |
> | 回答 | 这个世界能发生什么                    | 这本书选择发生什么、现在进行到哪里、按什么规矩写和整理 |
> | 来源 | 反向提取 / 立项 / 手建，AI 产出走提案 | 作者原文，直接保存                                     |
> | 粒度 | 一个实体一条，按名称合并              | 一份文档一条，不拆分、不合并                           |
> | 注入 | 核心设定始终注入，其余按预选勾选      | 按作用范围整份注入                                     |
>
> **为什么不是文风**：风格档案管句式与语感，其中的「额外写作要求」是一两句短约束，只进正文写作这类带文风的任务。规范要进摘要和提取（这两类任务不带文风），长度也常常是几千字。两者并存，各管各的。
>
> **为什么原文直接保存**：规范是作者自己写、自己粘贴或上传的文字，不是 AI 产出（5.1）。保存时一个字都不改，上传文件只做解码时必需的换行统一。
>
> **为什么翻译不带规范**：翻译的第一原则是忠实于原文。规范约束的是「本作接下来写什么」，放进翻译会诱导模型按规范「修正」原文，比如把原文里出现的后期装备删掉。译名一致性已经由作品级译名表负责。
>
> **为什么 AI 精简是另存而不是替换**：以来源表为主的长文，真正有约束力的往往只有几节，全文注入意味着之后每次生成、每章摘要、每章提取都多付这部分输入，还会稀释注意力（第 9 节）。所以编辑面板里提供「AI 精简」：结果是可编辑预览，作者点「另存为新规范（原文自动停用）」才在一次写入里新建精简版并停用原文；原文正文不变，觉得精简丢了东西随时切回去。有未保存修改时不能精简，避免精简的是一份库里不存在的内容。
>
> **为什么差异说明只给模板、本期不结构化**：编辑面板有「插入差异说明模板」，列出原作版本、本作开场时期、分叉事件、明确改动的事实及其后续影响、主角的信息来源、当前不可用的资源、关系进度等提示，内容仍是作者可自由增删的文字。结构化字段只有在程序会按字段做判断时才有价值；现在的检查由模型阅读规范文字来判断，拆成几个输入框再拼回提示词收益接近零。而且「原作版本」「分叉点」只对同人和改编成立，原创作品会面对一堆空框。等检查用上一段时间、看清哪些字段真的需要程序判断，再决定结构化哪些。

**导入旧稿**：见 6.5。

### 6.3 写作

**大纲树**：卷／章两层结构，可编辑标题、梗概、目标字数、状态，可关联知识条目（写这一节点时默认注入）。可用 AI 把一个节点细化成若干子节点（雪花法逐层展开）。层级与顺序用按钮调整。

**自动大纲**：两条路径，都只产出待确认的大纲提案、不写正文。①**导入作品 1:1 回溯**：按已有主线章节逐章建顶层节点（标题=章节标题、梗概=章节摘要、不设目标字数），预览后一次性创建并回填章节关联；不改章节正文/编号/标题，不重排现有节点，重复执行不重复。②**前沿规划 3–5 章**：读当前大纲尾部、全书进展、最近 3 章摘要、未收束伏笔与核心/相关设定，逐章给出场景清单、主冲突、章末钩子、引用设定、回收/新埋伏笔；生成一条待确认大纲提案，作者可改文本，采用后才追加到末卷（无卷则顶层）。不替作者决定人物命运/感情/凶手，不自动收束或新埋伏笔，不引入过多新实体。

> **为什么回溯不走模型**：导入作品的章节顺序、标题与摘要已经是事实；让模型重写一遍只会引入编造和编号漂移，而作者要的是「把已经写下的东西变成可继续规划的结构」。确定性映射 + 预览确认，比任何「智能归纳」都可靠。
>
> **为什么前沿只给 3–5 章**：给多了等于替作者写整本大纲，给少了不解决「下一章写什么」；3–5 章正好是「下一步可写」的粒度，而且一次调用就能把伏笔、进展与设定接上。

**细化大纲会读知识库**。生成前面板列出「本次注入」：核心设定（始终注入）、作者手工关联的条目，以及从节点标题 / 梗概 / 额外要求里按名称或别名识别出的条目 —— 进 prompt 的是**完整字段**（性格、软肋、说话方式、关系网、规则与代价），不再是「标题 + 一句话摘要」。识别错的「名字提到」项可以临时移除，只影响这一次。细化结果按**场景卡**写：谁想要什么、什么在阻碍、转折点、结尾局面或认知变化；并要求至少一处选择由人物软肋或世界规则代价驱动 —— 复述设定不算应用设定。

采用细化结果后，若新子节点标题 / 梗概里提到已有条目（或父节点本身有关联条目，会继承），会出现「确认自动关联」面板：逐节点列出建议（标签上直接标出命中的是名称还是别名、可取消、可全部跳过），**确认后才写入节点关联，不静默写回**；关闭面板不写任何关联。节点已有子节点时，细化前会告知将替换多少个子节点、有多少已挂章节会解除大纲关联（正文保留）。「额外要求」是一次性输入，不写库；要让它影响后续章节，应写进梗概。

**章节编辑器**：全屏，防抖自动保存，实时字数与保存状态。

- **整章生成**：生成前展示「本次注入」清单——哪几份写作规范、哪些设定、哪几章摘要、上一章结尾原文进了 prompt，每份规范带 token 估算。用户可勾选调整，写作规范可以临时取消（只影响这一次，不改知识库里的启用状态）。面板同时显示本章**目标字数及来源**（大纲节点的值，为空时默认 3000）与具体场景数参考（如「约 3–5 场」）。结果可直接编辑，再决定采用或追加到正文末尾，并显示「已生成 N 字 / 目标 M 字」；输出被截断或作者中途停止时明确标为「生成未完成」，采用不完整内容需要二次确认。完整结果明显超出目标（>115%）时标题标「生成完成（超出目标）」并给出差额提示，作者可手动删减或写更紧凑的额外要求再生成；应用不自动压缩、不硬卡字数。采用不完整稿后，编辑器会保留会话内「可能缺少结尾」提示；原本已完成的章节会自动退回草稿，避免半章冒充定稿
- **段落级加工**：选中一段做续写 / 改写 / 扩写，可临时指定文风要求、临时取消某份写作规范，带撤销栈（AI 改写是最需要一键还原的操作）
- **按规范检查本章**：用作用范围含「检查」的写作规范审读当前正文，列出可能违反之处（见下文）

> **为什么写作规范不参与预算裁剪**：规范是作者显式定下的约束，被预算悄悄挤掉等于约束失效，和核心设定同理。想省就在面板里临时取消，或在知识库里停用、收窄作用范围。规范很长时被挤掉的是后面的勾选条目，它们照常出现在「因超出预算未注入」的提示里，看得见。

> **为什么字数只给结构参考、不硬凑**：3000 字约 1–2 场、6000 字约 3–5 场，先保证梗概里的节拍全部落地；节拍不足时把一场写深，而不是用心理复述、景物堆砌凑字数。输出 token 上限只用于防截断（按目标推导、夹在安全区间），不作为字数控制器；截断与主动中止都会明确提示，避免半章被当成定稿。

- **摘要链与章节归档**：把章节标记为「已完成」时，后台自动生成本章摘要与设定——章节摘要、关键事件、出场角色、未收束伏笔、全书进展，以及知识库条目更新（可在设置里关掉条目提取）。结果全部是**待确认提案**：编辑器只显示一条非阻塞状态行，不弹全屏面板、不自动落库。摘要与进展每章一条；知识库条目按 3–5 章一个归档批次归组，每章最多 3 条实质变化，新登场人物单独即时提案；同章重复归档幂等，不会重复出提案。作者点「查看」可统一确认本批摘要与设定；摘要链断了会提示「补摘要」。
  - **安全默认**：归档批次里「对已有知识条目的合并/替换」默认标记为忽略，不会被「采用本批」写入；摘要与进展默认选中、正常写入。需要改旧条目时，展开那条点「纳入本批」再采用。收件箱顶部会提示本批共几项、其中几条合并/替换默认不选；全部纳入后提示「已全部纳入」。
  - **伏笔流水**：收件箱顶部按章显示本章「新埋 / 收束 / 现存」；误收束的伏笔可以在摘要的「未收束伏笔」里加回。流水只存本地（7 天），丢失不影响提案与数据。
- **大纲节点完成提示**：章节完成且同一大纲节点下的章节都完成时，编辑器提示「可以标为完成」；作者点击才写，不自动改状态
- **继续补写**：生成结果短于目标的 85% 或被截断时，显示「还有场景没落地？」与「继续补写」。补写是手动一次调用，只补本章尚未落地的场景，不自动循环到目标字数

> **为什么摘要要自动触发、但确认不能被打断**：摘要是后续所有章节的上下文来源。如果指望用户记得手动补，摘要链很快就会断；而断了之后的表现是「AI 越写越不记得前面的事」，用户往往归因为模型不行，其实是缺摘要。所以标记完成就自动生成；但生成完不抢焦点、不弹全屏付费面板，作者继续写或退出都行，提案留在待确认区，想处理时再「查看本批」。
>
> **为什么知识库条目要按 3–5 章归组、每章限 3 条**：逐章出提案会在几十章后堆出上百条内容高度重复的待确认项；按批归组、同名条目合并、只提实质变化，才能让「顺手更新知识库」不至于变成新的负担。新登场人物单独即时提案，是因为口吻与称呼一旦漂了，后面很难补回。

**未收束伏笔的语义是「截至本章仍未收束的累计清单」**，不是「本章新埋的」。这样写下一章只取最近一份摘要就能拿到完整的待收束清单。

**外传**：主线之外的番外、前传、后传。一部作品可以有多部具名外传（「外传·青冥旧事」），每部各自从第 1 章编号，有自己的简介和摘要链：章节摘要照常生成，伏笔只在这部外传里累计，进展摘要写进外传自己的「外传进展摘要」。外传章节在编辑器里的功能和主线一样（整章生成、段落加工、译成中文、标记完成自动摘要），只是不关联大纲节点。

「不计入主线」的含义是：不占主线编号，不进主线摘要链、全书进展和主线伏笔；生成主线章节时不注入任何外传内容；写作页的「全书进度」不含外传。但外传是真实的写作产出，所以**字数计入书架总字数、备份提醒和写作计划的每日产出**；书架卡片的章数只算主线，另显示「外传 K 章」。

> **为什么写外传默认不带主线进展**：外传在时间线上的位置不固定。给前传注入主线进展，模型会让人物「提前知道后来的事」，这是外传里最容易出现的崩坏。人物与世界规则这类稳定事实已经由知识库提供。确实是后传的，生成面板里打开「参考主线进展」就能拿到主线现状，注入清单里看得见。
>
> **为什么外传说明放在 prompt 尾部**：外传与主线共用同一份稳定前缀（作品信息 + 风格 + 写作规范 + 核心设定 + 勾选条目），说明块和外传前情都拼在易变后缀里，写外传不会让主线已经命中的缓存失效。
>
> **为什么支持多部具名外传，而不是一条「番外」序列**：两部外传挤在同一套编号和同一条摘要链里，伏笔与进展会互相污染，等于把「外传不进主线链」的问题原样搬到外传内部。外传也不挂大纲树：大纲是主线结构、直接驱动全书进度，外传的简介就是它的轻量大纲。

**外传可以来自互动推演**：把一条不在主线上的世界线沉淀下来（见 6.8），得到一部新外传和若干空章节，每章带着自己的细纲（编辑器里「本章细纲」折叠区只读显示），外传记住它是从推演的哪一步分出去的。

**来自推演的章节「写这一章」**：大纲节点或外传章节带着推演溯源时，整章生成在易变后缀里多注入四块，都在「本次注入」清单里各占一项、必选（它们就是本章要写的材料，和大纲位置同理）：

- **推演专属设定**：限定到推演的条目原文（主角档案、本章才登场的预设人物等）。限定条目不在写作页的条目列表里（为了零回归），整章生成只能从这里拿到主角的身份、性格、说话方式。主角是通用人物时，他照常作为默认勾选的设定注入
- **分叉之前的经过**（只有外传）：取推演树上的前情摘要，不取主线章节摘要 —— 主线可能根本没沉淀，或沉淀后被改写过
- **本章依据的推演原文**：本章对应各步的行动与情节
- **世界线状态**：本章开始时这条线的变化，加上本章内发生的变化

放在尾部，是因为每章都不同，进前缀会截断全书共用的缓存前缀。**段落加工不带推演材料**：加工针对的是已经写下的正文。推演主角在回收站里、或来源推演已删除时，编辑器会说明，本章只按现有材料生成。

**按规范检查本章**：章节编辑器标题栏「摘要」前的「按规范检查」。主线与外传章节都能用；没有作用范围含「检查」的规范、没配置模型、本章还没有正文时入口不可用，点一下会显示原因。

- **带哪些上下文**：作品信息、作用范围含「检查」的规范（可在面板里临时取消，至少保留一份）、核心设定、本章正文里提到的其他条目（最多 8 条）、同一条线上此前最近一份章节摘要，以及当前编辑器里的正文（不必等自动保存落盘）。不带风格档案：检查的是规范而不是文风，带上会诱导模型挑文风毛病。不带大纲：大纲是计划不是事实
- **长章分段**：超过 8000 字符按行边界切成几段依次检查，面板先显示「本章约 N 字，将分 K 段检查（K 次调用），输入约 X tokens」，作者点「开始检查」才发请求
- **截断即报错**：任一段的输出被截断、或网络与解析失败，整次检查失败并说明是第几段，不展示部分结果 —— 部分结果看上去就像「其余段落没问题」
- **结果**：逐条列出严重程度（明确违反 / 可能违反 / 需作者判断）、违反了哪份规范的哪一条、正文原句、问题与修改建议；可以「定位」到原句、「按建议改写」或「忽略」。匹配不上规范名的条目保留并标「规范名未对应」，交给作者判断
- **结果只在会话内**：关掉面板再打开还在，离开编辑器或换章即丢。正文在检查后改过，面板会提示结果可能已过期

> **为什么只提示、不自动改**：检查结果是模型对「是否违反」的判断，误报不可避免；规范常有留白（例如「生死留白不等于确定死亡」），本身就要作者裁决。自动改正文等于让 AI 替作者裁决并改写散文，违背 5.1。所以「按建议改写」只是选中那段原文、打开段落加工并预填「改写」与建议，之后照常走可编辑预览，作者点「替换原文」才写入，并进撤销栈。
>
> **为什么不保存检查结果**：检查便宜，随时可以重跑；而正文一改结果就过期，库里留一份过期判断只会误导。落库还要加表、改备份版本、做过期判定，换来的只是一份很快失效的记录。

### 6.4 计划

三种模式：每日 N 章 / 每日 N 字 / 每周 N 章。可设写作日（每日模式）与开始日期，可临时停用。

看板显示：当期目标与完成进度、连续打卡天数、累计欠账、最近 7 天产出。产出在章节保存时自动记录，不需要手动汇报。

**不做推送通知**（阶段一）。纯应用内提醒。

### 6.5 旧稿导入与反向提取

这是存量作者的入口，也是这个产品最重的一条链路。

**外文来稿也能接住。** 分章后如果检测到外文章节（按章判定，不是整本取一个），会多出一个翻译步骤，译成中文再往下走。译文替换正文、原文留底，之后的提取与续写面对的都是一部中文作品。世界观设定同样可以翻译。

**导入到哪里，在翻译之后再选。** 所有导入走同一条路：粘贴 → 分章 →（有外文时）翻译 → 导入到 → 提取 → 确认。目的地整批三选一：

| 目的地           | 写什么                                   | 提取出什么                                                                 |
| ---------------- | ---------------------------------------- | -------------------------------------------------------------------------- |
| 主线章节         | 接在主线之后编号，标记为已完成的导入稿   | 设定条目、逐章摘要、全书进展，可选文风                                     |
| 外传             | 选一部已有外传或当场新建，在外传内部编号 | 设定条目（并入同一个知识库）、逐章摘要、外传进展摘要，可选文风（默认不勾） |
| 仅作为世界观设定 | 一章都不写，不占编号                     | 只有设定条目                                                               |

纯中文稿不多一步：「导入到」直接放在分章确认页，主按钮随选择变成「写入主线 N 章」「写入外传 N 章」或「提取为世界观设定」。有外文时，分章页只负责切分，译完再进入单独的「导入到」步骤。选定目的地之前，分章结果和译文都存在导入任务上，一章都不写进作品；刷新、关面板都不丢，已经付钱的译文也不丢。

**入口在起点，不在角落。** 书架新建作品时就能选「导入已有稿件」，建完直接落在导入面板上；已有作品也能在知识库补导入。导入模式下不问「我想讲一个什么故事」—— 存量作者手里有几十万字却还没有那句话，它应当由稿件反推出来。

1. 上传 `.txt` / `.md` / `.rtf` 文件（桌面端可拖拽），或粘贴全文；RTF 读入时自动提取成纯文本
2. 自动分章（认「第一章」「第十回」「楔子」「Chapter 3」等），可改用整篇一章或自定义正则；切分结果可逐章合并、删除、改名，并对「明显偏短的章节」给出提示。超过 6000 字的外文章节会提示「翻译时会自动分段进行」
3. **外文章节译成中文**（按章判定语种，只有检测到外文时才出现这一步）。长章按段落自动切成约 3000 字一段逐段翻译，每段落地前做完整性校验（非空、长度比例、不丢受保护内容），已成功的段落盘、失败只重试该段，全部成功才拼成整章译文。半截译文永远不会被当成已译
4. **选择导入到哪里**：主线章节 / 外传 / 仅作为世界观设定（纯中文稿就在分章页选）。选主线或外传时，章节和导入任务在同一次写入里落库，要么全成要么全不成
5. 逐章反向提取：同一次调用同时产出设定条目与章节摘要。世界观设定则按章打包成几千字一段提取（几个短章合成一段，超长章按段落再切），一段失败只重试那一段。进度落盘，可暂停、继续、单章重试、跨刷新续跑
6. 全部跑完后整理成提案：新条目走「新建」，已有同名条目走「合并」并显示字段级改动
7. **从稿件归纳文风**：自动取样几段代表性片段，产出七维文风描述 + 文体取向，作为同一批里的一条提案（在「导入到」里勾选；主线默认勾、外传默认不勾、世界观不提供）
8. 在收件箱里逐条确认 → 知识库、摘要链与风格档案补齐 → 可以直接接着写下一章
9. 也可以**接着导下一批**：回到第一步，译名表与已有条目沿用，「导入到」预选上一批的目的地，新章节在所选那条线上追加编号

> **为什么设定文本可以不当章节导入**：设定集、人物小传、世界观文档不是故事正文。写成章节会出现在章节列表和书架字数里，还会被拿去生成章节摘要、推进全书进展、归纳文风 —— 每一样都会把作品档案带偏。所以「仅作为世界观设定」只出条目提案；文本与进度存在导入任务上，不落成章节，中途放弃也不留残骸。同名条目跨段累计合并。
>
> **为什么目的地要在翻译之后选**：世界观设定也可能是以故事的形式写的 —— 一段前史、一篇人物小传，读起来和正文没有区别。外文稿在翻译之前，作者往往看不出它该进主线、进外传还是只当设定参考；先选再译，等于逼人凭外文猜。所以分章之后先译，译完看着中文再决定。这也让世界观设定能和章节一样翻译、一样沿用作品译名表，提取时模型看到的是中文译文而不是原文。
>
> **为什么整批只选一个目的地**：逐章混选意味着一次导入要拆成几条线分别编号、分别承接摘要链、分别出进展提案，选择界面也要变成逐章表格，手机上很难用。正文和番外混在一个文件里时，导两次即可：第一次在分章页删掉番外章节，第二次只留番外。
>
> **为什么导入外传默认不归纳文风**：番外常常刻意换一种语气，样本也比正文少，拿它去替换风格档案判错的概率高。勾选框放在「导入到」里，是因为默认值取决于目的地，而这里仍是花钱之前最后一个能改的地方。

> **为什么导入要能连着来第二轮**：「把整本书一次性交出来」是产品经理的想象。真实情况是一章一个文件、正文与番外分开存、或者先拿一章试水看看提取质量再决定导不导全书。跑完一轮必须关掉面板重新进一次，是在惩罚最谨慎的那种用法。跨轮沿用译名表与已有条目，所以第二批提到同一个人物会走「合并」而不是新建。

> **为什么必须支持文件上传，而不是只能粘贴**：几十万字靠剪贴板在手机上根本做不到。而且中文 `.txt` 有相当比例是 **GB18030**（Windows 记事本的「ANSI」），按 UTF-8 硬读会整篇乱码 —— 那是「看起来成功了」的那种失败，用户会以为是应用坏了。所以读文件时自己拿字节做编码探测，并把识别结果显示出来。RTF（Word 的富文本格式）同样支持：它有两种中文写法 —— 老式按文件代码页（`\ansicpg`，中文几乎都是 936=GBK）编成 `\'hh` 十六进制转义，新式写 `\uN` 码位转义 —— 提取器两种都吃，输出纯文本后走与 .txt 完全相同的后续流程。
>
> **为什么不按文件名给多个文件排序**：一章一个文件的作者不少，但中文文件名的字典序会把「第十章」排到「第二章」前面。悄悄把一本书打乱，比让用户按顺序点几下糟糕得多 —— 所以按选择顺序依次追加，顺序由用户掌握且看得见。

> **为什么翻译排在反向提取之前**：颠倒过来，知识库会基于外文原文建起来，条目里混着英文原词，之后用中文续写就得在两套命名之间来回翻译。译文先落地，后面所有环节看到的都是一部中文作品。
>
> **为什么翻译必须让用户按一下才开始**：它是整个应用里唯一一次大规模输出 token 的操作，成本大致等同于让 AI 重写一遍同样长度的文字。提取可以自动跑（输入为主、单章几分钱），翻译不行 —— 用户必须先看清要译哪几章、能取消勾选。
>
> **为什么译名先到先得，而且存在作品上**：人名跑风是文学翻译最刺眼的毛病。Ashford 在第一章是「阿什福德」、第五章变成「艾许佛」，读者会以为是两个人。所以前面定下的译名不允许被后面的翻译推翻 —— 一致比「这次译得更好」重要。
>
> 译名表**挂在作品上而不是挂在某次导入上**。这一点是踩过坑才定下的：最初它存在导入任务里，而任务跑完就会被删，于是第二批外文素材进来时从空表开始，同一个人名可能换个译法 —— 「分几次导入」恰恰是存量作者最常见的用法。现在跨章节、跨批次、单章补译都用同一份，作者也能在「知识库 → 管理 → 译名表」里直接改（作者的决定覆盖模型的）。
>
> **为什么改了译名要提示、但不自动替换**：强制沿用只管得住「接下来要译的」。作者把 Ashford 从「阿什福德」改成「艾许佛」之后，已经译好的章节仍是旧译法，而这种不一致没人会自己去几十章里翻。所以译名表会拿**原文与译文对照**找出来：某一章的原文出现过 `Ashford`、译文里却找不到「艾许佛」，就列出这一章并能一点跳过去。这个判据不需要额外记录译名的历史，还能顺带发现模型当初压根没照译名表译的情况。
>
> 但**只提示，不替换**。同一个词会出现在对话、称谓、复合地名里，机械地全文替换会出事；而且中文原创章节没有留底原文，无从判定里面的「阿什福德」是不是同一个人。把不一致摊开给作者看，改不改、怎么改由他定。

> **为什么条目提案要等全部跑完才生成**：主角会在几十章里反复出现。逐章出提案的话用户要处理上百条内容高度重复的待确认项，实际上没人会看完。所以提取过程中先按名称累计合并，跑完才一次性生成。章节摘要相反，逐章即时生成——它是「这一章」的产物，攒到最后反而看不出对应关系。

> **为什么文风要自动归纳**：存量作者的文风就在稿子里。让一个已经写了几十万字的人从零挑一遍名家风格、再逐个填七个维度的描述，是把本来能从数据里读出来的事推给了用户。归纳出的结果同样是待确认项，判错了当场改。
>
> **为什么只认文风与文体，不认方法论和名家参考**：这是「哪些属性能从文本观察出来」的边界。句式节奏、叙述距离、对话密度、文体取向都写在字里行间；而**创作方法论**是「接下来怎么规划大纲」的选择，不是既有文本的属性 —— 从正文反推作者当年用的是雪花法还是三幕式是伪精确，而它直接决定后续大纲结构，猜错的代价不对称。**名家风格参考**则是「我想像谁」而不是「我像谁」，让模型判定「接近某位作家 60%」既容易错，也不该由机器替作者宣称这种关联。
>
> **为什么归纳排在最后而不是单开一步**：取样必须在翻译之后（否则归纳出的是英文的句式节奏）；而反向提取刻意不带文风，所以放在它后面对提取没有任何影响。共用同一个批次号，用户在一个收件箱里连着确认，流程上一道关卡都不多。附带调用失败时只少一条提案 —— 十几分钟提取的成果不能被一次可选的调用带崩。

### 6.6 设置

模型服务配置（服务商预置 DeepSeek / OpenAI / 自定义 OpenAI 兼容端点、接口地址、API Key、常规模型、重点任务模型）、连通性测试、模型分工一览、写作辅助（完成后自动归档、是否提取知识库条目）、备份与恢复、安全说明。

### 6.7 导出与备份

- **正文导出**：全书、单章或一部外传，Markdown 或纯文本，可只导出已完成章节，复制到剪贴板或下载文件。**全书导出默认不含外传**，打开「附带外传」后按外传顺序追加在正文后面，每部一个「外传·X」标题；外传单章的标题与文件名带「外传·X 第 N 章」，不会和主线同号章节撞名
- **分章打包**：范围第一个是「打包」—— 每一章导出一个文件，整本打成一个 zip 带走。默认格式是 Markdown / 纯文本 / RTF / PDF 四选一（默认纯文本），也可以逐章改；改过的章不跟默认格式变，点「全部改用默认格式」一次还原。可勾「只导出已完成的章节」与「附带外传」。zip 里是一个以书名命名的文件夹，主线章节直接放在里面（`第001章 离乡.txt`），每部外传一个子文件夹（`外传·青冥旧事/第001章 拜师.pdf`）；章号按这次导出的最大章号补零到至少三位，文件名排序就是章序；标题为空时文件名只剩章号，标题里的文件名非法字符会被去掉、过长会截断，书名超过 40 字也截断（书名同时是 zip 文件夹名与下载文件名）；空章节一律不导出，勾了「只导出已完成」时草稿也不导出，没有可导出章节时按钮禁用
- **全量备份**：一个 JSON 文件带走所有作品数据（含外传、互动推演的全部分支），**不含 API Key**。恢复支持「覆盖恢复」（换设备）与「合并导入」（并入另一台设备的作品）。旧版本的备份照常能恢复，其中的章节全部视为主线，条目都是通用的
- **合并导入时推演整棵替换**：同一个推演的分支树以备份为准，不和本地的树逐行取并集 —— 两台设备在同一个选项下各走了一步，拼起来就成了同一选择有两个后续，主线指针也会和树对不上。本地那几步因此不保留；本地沉淀过、但备份里没有的步骤，对应大纲与章节保留，只是解除和推演的关联

> **为什么导出默认不带外传**：投稿或贴到平台时，正文和番外通常分开发布。「附带外传」留给整理全集或私人存档。

> **为什么 PDF 用阅读器自带的字体、超出的字直接显示 □**：PDF 是「拿给人看」的版本：版式固定、能分页、能打印。要保证中文都显示，最稳的做法是把一份中文字体嵌进 PDF —— 但打包是每章一个文件，每份都背着几 MB 的字体，或者自己做一套字体子集化，为十几 KB 的一章不值这个成本，所以 PDF 不嵌字体，用阅读器自备的宋体。代价是阅读器的中文字体只覆盖 GBK 范围：扩展区生僻字（比如 `㵘`）和 emoji 不在里面，硬写进去会被显示成别的字或空白，所以导出前就把它们统一换成 `□` —— 占位是诚实的，至少不会悄悄变成错字。要一个字都不差地保留，请选 TXT/MD/RTF；PDF 实际显示成宋体还是黑体，也由阅读器决定。

### 6.8 互动推演

把一个主角放进这本书的世界观里，AI 每一步写出情节和挑战、给出几个选择，作者选（或自己写主角要做的事），AI 接着写后果和新挑战，如此循环，直到走到预设的结局或作者决定收尾。途中可以随时回到任何一步换一个选择，开出另一条世界线，原来那条保留。玩出来的线可以沉淀成大纲与章节（6.3）。入口在写作页顶部的「互动推演」卡片，一本书可以有多个推演。

**开局设定**：推演名称、主角（从人物分类里选一条已有条目，或当场新建）、起点（时间、地点选填，处境必填）、1–6 个结局目标（好 / 坏 / 中性 + 描述）、0–8 个有序里程碑、基调、预计步数（5–200，默认 30）。开局后可以改名称、目标、里程碑、基调与预计步数，只影响之后的步骤；**主角和起点改不了** —— 它们是整棵树的前提，换了等于另一局，应当新建推演。当场新建的主角直接存成一条限定到这个推演的人物条目（作者自己填的字，不是 AI 产出，不走提案）。

**一步的构成**：一次流式调用，先写几百字情节（边写边显示），再在后面带一段结构化结果：挑战、2–4 个选项、这一步的世界线变化、里程碑进展、是否触发结局。结构化部分不合格式时自动修复一次；输出被截断直接判失败、不保存。为什么不分两次调用：第二次要把正文再付一次输入费、多一次往返，而且变化是「写完之后再猜」，不如写的时候一并给出可靠。选项带「倾向」（谨慎 / 果断 / 迂回 / 对抗 / 合作 / 牺牲 / 欺骗 / 探索）和按主角此刻看得见的危险标的「风险」，都是固定选项：自由标签很容易写成「（会被识破）」这种剧透。

**选过的不能再选**：每一步 AI 当时给的选项原样存下，回退时只读它、永不重新生成。走过的选项显示「已走过」、不能再点，旁边给「去这条线」。「已走过」不另存标记，从分支树上现算（某个选项下面已经有一步），避免和树对不上。选项都走过之后可以点「再给几个选项」追加一批（每步最多 8 个），新的不和已有的重复；自由输入任何时候都可用，所以选完从来不是死路。

**自由输入是「尝试」**：写下主角要做的事（最多 200 字），提示词里一律标成「尝试，不是既成事实」。可行就写出成败与代价；违背底层设定（凭空获得能力、无视代价）就写出主角试了、失败了、付出了什么。不直接拒绝：拒绝打断游戏节奏，而「试了、失败了」本身就是好情节，也正是世界规则的体现。代码层再兜一道：改写锁定字段的变化无论如何都不会记下（5.2）。和这一步已走过的行动规范化后完全相同（忽略空白和句末标点）时不能提交，提示「这个行动在这一步已经走过了」；和没走过的选项相同就当成选了它；只是很像时提醒一句、按钮变成「仍然这样做」。不用 AI 判定是否重复：每次多一次请求、多一两秒，而且误判会挡住作者 —— 误挡比误放糟。

**回退与切换不花钱**：面包屑、「世界线」导航、「去这条线」都只是换一个节点看，**不发任何请求**；打开推演页、打开本线状态也不发。只有选选项、提交自由输入、收尾、「再给几个选项」会调用模型，也从不顺手把其他选项预先生成好 —— 作者没选的分支不该让他付钱。

**主线跟随最新**：主线 = 开局到最近一次推进出来的那一步的路径。只是回去看旧线不改主线；在旧线上推进一步，主线就切过去。不采用「查看即切换」：回头翻一眼旧线就把主线换掉，沉淀出来的东西会随手乱跳。主线存成一个显式指针而不是按时间现算，合并导入另一台设备的备份后两边时钟可能不一致。推演页标题下常驻「主线 · 第 k 步」或「外传线 · 不在主线上」+「回到主线最新一步」，面包屑与导航里主线上的步骤带「主线」文字标签，不只靠颜色。

**结局与收尾**：结局只有在此前的选择与状态直接导致时才触发，必须写明「起因」，作者一眼能看出是不是硬转。可以走到坏结局：结局之后不能再推进，但可以「回到上一个挑战」或从路径里选任何一步重来。预计步数只是节奏参考：超出后提示词要求不再开新线索、优先回收，界面提示「可以收尾了」，但**何时结束是作者的决定**，不是模型的。任何未结束的一步都能点「收尾」，可选想要的结局目标和一句说明，AI 从当前状态自然写出结局；写不出你要的那个，结局上会显示「你要的是 G1，这条线写出的是：…」，不强行圆上。

**防跑偏**：目标与里程碑每一步都在提示词里，下一个里程碑会被点名，但「是否达成由主角的选择决定」；挑战必须从上一步的后果、下一个里程碑或未收束的线索里长出来；每步最多引入两个新实体。

**本线状态**：每一步记下的世界线变化分六类 —— 字段改写、本线新条目、人物处境（登场 / 死亡 / 失踪 / 被俘 / 被毁 / 被封印 / 恢复如常）、主角状态（伤势、能力、持有物、关系、已知秘密）、事件、标记。变化**沿路继承、兄弟隔离**：某一步的有效设定 = 世界观原文 + 开局到这一步沿路叠加的变化，现算不存；另一条分支看不到这条线上的变化。「本线状态」面板分「本线变化」「有效设定」「主角状态」「事件与标记」，每条标出来自第几步；作者可以编辑、删除任意一步的变化（新增改写只列可变字段），改了前面的步骤，后面的步骤提示「生成时依据的是旧事实」，不重新生成。每 5 步有一份前情摘要，在面板里可查看、可编辑。

**沉淀**：在某一步点「沉淀这条线」。这一步在主线上 → 追加到本书主线大纲（卷 / 章，梗概里写关键事件与出场人物，每章记着对应第几步）；不在主线上 → 新建一部外传及其空章节（6.3），继续玩同一条外传线时默认「追加到外传《X》」。分章由模型按场景切（建议 3–6 步一章），不一步一章（几百字的碎章），也不固定 N 步一章（节奏不均匀）。结果是一个大纲提案，作者可以改，「对应步骤」必须首尾相接地覆盖这次的范围，否则采用失败、提案留着 —— 宁可让作者改一下，也不把章节挂到错的步骤上。再沉淀同一推演时只沉淀还没被覆盖的那一段（续沉淀；中间删掉过某章时只补那个洞，补出的卷放在大纲末尾，用大纲树的「调整位置」挪）。主线已有大纲时一律追加，不替换、不禁止：主线大纲可能是作者手写的，多个推演拼成一部长篇也是合理用法。一段已沉淀为外传的路径后来成了主线时，面板提示「其中第 a–b 步已沉淀为外传《X》」，仍允许沉淀进主线：外传留不留由作者决定。

**主线换了之后**：已沉淀的大纲一律保留。对应步骤不全在当前主线上的章节现算出「来自旧主线」标记，推演页顶部提示「本书主线大纲里有 N 章来自旧主线」，大纲节点面板里同样标出。不删除、不自动重建：作者可能已经在那些章节上写了几千字，任何自动动作都是在替作者裁决。删大纲节点只解除关联、不删正文。

**删除推演**：分支全部永久删除；已沉淀的大纲、外传与章节保留，只是不再关联推演。默认勾选「同时把只属于这个推演的条目（含主角）移进回收站」—— 新建的主角大多只为这一局存在，进回收站可恢复，所以默认勾上不危险。反过来，推演还在时，回收站里的推演主角不能彻底删除（提示「这个条目是推演《X》的主角，先删除推演」），否则推演就没有主角了。

推演里的规范：作用范围含「互动推演」的写作规范进推演的提示词（6.2）。「按规范检查」第一期不支持推演节点：推演不是作品正文，真正交付的文字是沉淀后写出的章节，那里已经能检查。

## 7. 信息架构

五个主导航项（窄屏在底部，宽屏在左侧边栏）：

```
书架 ── 多作品管理、当前作品切换、备份提醒
知识库 ── 一句话立项 · 设定条目 · 风格档案 · 写作规范 · 分类管理 · 导入旧稿 · 译名表 · 回收站
写作 ── 互动推演（入口卡片 → 推演页：路径 · 世界线导航 · 本线状态 · 收尾 · 沉淀）· 全书进度 · 大纲树 · 章节列表 · 外传 → 章节编辑器（生成 / 加工 / 摘要 / 按规范检查）· 导出
计划 ── 当期目标 · 坚持情况 · 最近 7 天
设置 ── 模型服务 · 连通性测试 · 模型分工 · 备份与恢复 · 安全说明
```

**互动推演为什么不是第六个主导航**：底部 Tab 的通行建议是 3–5 个，多一个会让所有页面、所有用户的每个 Tab 变窄（375px 下每项从 75px 变 62px），而推演只对一部分作品有用。它放在写作页顶部（「全书进度」之上）一张一行高的卡片里：互动本身是目的，藏在大纲和几十章章节列表之后会找不到；沉淀的产物（大纲、外传）就在同一页，玩 → 沉淀 → 写这一章不跨 Tab。推演页有自己的地址（`/write/scenario/…`），刷新后还在同一个推演，主导航高亮仍是「写作」。

断点分两档：`md`（768px）起列表变多列、抽屉变对话框，照顾平板横屏与半屏窗口；`lg`（1024px）起才换成侧边栏外壳。

「知识库 / 写作 / 计划」都针对**当前作品**；没有选定作品时会引导先去书架选一本。

待确认项出现在它所属的页面顶部（设定与大纲在知识库，大纲相关在写作页），或出现在生成它的面板里。同一批内容不会同时出现两个确认入口。

## 8. 关键流程

### 8.1 新作品：从一句话到第一章

```
书架 新建作品
   ↓
知识库 输入一句话 + 选篇幅 → 生成
   ↓
确认世界观 / 人物 / 大纲（可逐条改）
   ↓
知识库 设定风格档案（文体 + 方法论 + 名家风格）
   ↓
写作 点大纲叶子节点 →「写这一章」
   ↓
核对注入清单 → 生成 → 编辑 → 采用
   ↓
标记「已完成」→ 自动提炼摘要 → 确认
   ↓
写下一章（自动带上前情）
```

### 8.2 存量作品：从旧稿到续写

```
书架 新建作品 → 选「导入已有稿件」→ 只填书名
   ↓
（自动落在导入面板）上传 .txt / .md / .rtf，或粘贴全文
   ↓
核对分章结果（合并 / 删除 / 改名）
   ↓
（有外文时）勾选要译的章节 → 开始翻译（可暂停、可关页面稍后继续）
   ↓
导入到：主线章节 / 外传（已有或新建）/ 仅作为世界观设定
   ↓
写入并开始提取（可暂停、可关页面稍后继续）
   ↓
收件箱逐条确认：新条目新建、已有条目合并（看字段级改动）
   ↓
知识库补全 + 摘要链补齐（外传进外传自己的链）
   ↓
写作 直接写下一章 · 或继续导入下一批素材
```

纯中文稿没有翻译这一步，「导入到」就在分章确认页上，点击次数和只导入主线时一样。

### 8.3 日常：按计划推进

```
计划 设定「每日一章」
   ↓
写作 写完 → 标记已完成 → 产出自动记入当日
   ↓
计划 看当期进度、连续天数、欠账
```

### 8.4 从一局推演到一章正文

```
写作 顶部「互动推演」→ 开始一局：选或新建主角、起点、结局目标、里程碑
   ↓
推演页 读情节 → 选一个选项 / 写下主角的尝试 → 下一步（循环）
   ↓
不满意就回到任何一步换个选择（不花钱），原线留作另一条世界线
   ↓
走到结局，或在某一步「收尾」
   ↓
「沉淀这条线」→ 生成大纲（主线 → 主线大纲；旁支 → 新外传）→ 在提案里改分章、确认
   ↓
写作 打开那一章 →「写这一章」：清单里多出推演原文、世界线状态等 → 生成 → 编辑 → 采用
   ↓
（可选）本线状态里把值得留下的人物或改写「提升为世界观」→ 知识库确认
```

## 9. 成本与性能取舍

用户自带 API Key，所以省钢就是省用户的钱。三条策略：

1. **上下文窗口不是瓶颈，成本才是。** 装箱的目标不是「塞得进去」，而是控成本 + 避免长上下文稀释模型注意力。注入量对用户透明可见、可调。
2. **必须命中 prompt 缓存。** 命中与未命中的输入价差可达 50 倍，所以稳定内容（系统提示 + 风格档案 + 写作规范 + 核心设定 + 关联人物）严格放在 prompt 前缀且顺序逐字节可复现；易变内容（最近章摘要、上一章结尾、本次指令）一律拼在尾部。写作规范排在核心设定之前，是因为前缀里越靠前的内容越该是最不易变的：规范写好后很少改，核心设定却会随知识库确认而增减。规范放在后面，作者每确认一条核心设定，规范那几千 token 就跟着失去缓存；放在前面，只有改规范本身才会让后面的内容失去缓存。没有启用任何规范时，提示词与之前逐字节相同。
3. **按任务分配模型与参数。** 结构化推理任务（立项、大纲、提取、摘要）开思维链、低温度；正文创作关思维链、高温度——推理模式会让散文解释性过强、文气断裂。立项与大纲用「重点任务模型」，其余用常规模型。

反向提取时一次调用同时产出设定与摘要，避免为同一章正文付两遍输入费。

**互动推演的成本**：推演一步一次调用，步数一多就是最频繁的请求，所以同样按这三条做：

- **前缀与分支无关**：同一个推演里所有步骤、所有分支、收尾、「再给几个选项」、前情摘要共用到【推演规则】为止的前缀（作品信息、文风、规范、核心设定、主角原始设定、开局与目标、推演规则）。世界观条目在前缀里只出现原文，世界线上的改写只出现在尾部的「本线变化」里，并明说冲突时以它为准 —— 把改写后的值渲染进前缀，会让每条分支的前缀都不同，兄弟分支和回退后的新分支就都命中不了缓存。
- **回退不花钱，不预生成**：跳到任何一步只是换个节点看，零请求；没选的分支永远不生成。
- **长路径靠检查点**：只带最近 3 步原文，更早的由每 5 步一次的前情摘要承担，摘要沿树继承、兄弟分支共享分叉前的那份，所以提示词长度与路径长度无关。缺摘要太多时先补齐再生成（界面显示「正在整理前情…」），不往提示词里硬塞几十步原文。
- **按任务分模型**：步骤与收尾关思维链（散文为主，首字也更快，流式才有游戏感），前情摘要开思维链、低温度，沉淀分章用重点任务模型。

第 1 条「注入量可见、可调」在推演里的落实：推演页正文下方默认折叠的「本步依据 · 约 X tokens」列出下一步会带上的每一项与 token 估算。**从最近几步原文、前情里推断出来的相关设定**每条一个复选框，取消后之后的推进不带它；勾选状态只在这次打开推演页期间有效，离开即恢复，因为它是「这几步先别带这个」的临时调节，不是设定。其余各项只读并写明原因：核心设定、主角、开局设定、规范是作者显式定的约束；本线变化、前情、最近几步是这一步的事实依据，去掉会让模型写出和这条线矛盾的情节。

## 10. 安全与隐私

| 事项         | 做法                                               |
| ------------ | -------------------------------------------------- |
| API Key 存放 | 只在这台设备的浏览器本地存储里，不经任何中间服务器 |
| 出站连接     | 内容安全策略把出站限制在已登记的模型服务商域名内   |
| 第三方脚本   | 不引入任何第三方脚本                               |
| 备份文件     | **不含 API Key**，结构上就不收集设置               |
| 共用设备     | 提供「清除密钥」                                   |
| 数据所有权   | 全部数据在本地，随时可全量导出                     |

**已知局限（阶段一）**：纯前端应用无处安全保管密钥，同一网站的脚本理论上都能读取本地存储。这是「无后端」换来的代价，阶段二会把模型调用转为服务端代理。设置页的「安全说明」向用户明示了这一点。

## 11. 非目标

明确不做的事，以及原因：

| 不做                               | 原因                                                                                                                 |
| ---------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| 一键生成整本小说                   | 与产品前提冲突：作者才是作者                                                                                         |
| 独立的桌面端代码 / Electron 客户端 | 同一套响应式代码已经能给出两端各自合理的形态；再开一份意味着两条必然漂移的分支                                       |
| 通用翻译器（中译外、任意语对）     | 只做「把外文来稿并入一部中文作品」这一个方向。目标语言固定为中文，做成通用工具会让提示词、译名表、字数统计都失去锚点 |
| 模仿在世作家的具体文句             | 版权风险，且生成质量不稳定                                                                                           |
| 改译名后批量替换已有正文           | 同一个词会出现在对话、称谓、复合地名里，机械替换会出事。只做不一致提示 + 跳到那一章                                  |
| 推送通知（阶段一）                 | Web Push 要服务端，阶段一无后端                                                                                      |
| 拖拽排序                           | 移动端嵌套树难瞄准，读屏不可用                                                                                       |
| 内置账号与云同步（阶段一）         | 阶段一要先把创作链路跑通，同步留给阶段二                                                                             |
| 协作与多人编辑                     | 单人创作工具，协作会把数据模型复杂度推高一个量级                                                                     |

| 推演的图形化分支流程图（第一期）   | 用面包屑 + 「当前路径及其直接分支」列表导航：几百步的推演在手机上也能用，读屏不会读到整棵树                          |

## 12. 演进路线

**阶段一（已完成）**：纯前端 + IndexedDB，用户自带 Key，完整创作链路，手机与电脑同一套应用。

- 19 个功能模块全部落地
- 1770 个自动化测试（76 个文件），连跑稳定
- 可走通链路：立项 → 知识库 → 大纲 → 按章写 → 摘要链 → 旧稿导入反向提取（含文风归纳）→ 计划推进 → 导出备份 → 写作规范 → 互动推演沉淀成文

阶段一的两个已知缺口：

- **未注册 Service Worker**，所以只做到「可安装到桌面 / 主屏、独立窗口打开」，离线打不开。数据本身已在本地，补一个 SW 即可补齐，但缓存策略需要和版本更新一起设计，没有草率上
- **跨设备不同步**。数据在各自浏览器里，手机与电脑之间要靠导出／导入备份文件搬运。这是阶段二的核心内容

打包体积：六个页面已按路由懒加载拆包，首屏主 chunk 从 939 kB（gzip 294 kB）降到 540 kB（gzip 167 kB），「写作」「知识库」「推演」等重分支按需加载。剩余主 chunk 是框架与全部页面共用的核心，暂无进一步拆分价值。

**阶段二**：账号与多设备

- Supabase 实现同一套数据访问接口 + 账号鉴权 + 云同步（含冲突处理）
- 模型调用转服务端代理：密钥不再落在客户端，可做限流与额度
- Service Worker + PWA Web Push 提醒

数据访问层从一开始就被抽象成一个可替换接口，组件层不接触任何具体存储实现，所以阶段二的替换不需要改动功能代码。

**互动推演第二期**（第一期已落地：开局、推进、回退与世界线导航、本线状态、收尾、提升为世界观、沉淀为大纲 / 外传、来自推演的章节「写这一章」）

- 多主角：放开主角数量上限，提示词按主角分块
- 图形化分支流程图
- 「按规范检查」推演节点：现有检查绑定章节编辑器（定位原句、按建议改写都作用于编辑器），搬过来要做一套只读变体
- 「原作事件表」：同人 / 改编按时间截面列出原作事件，按世界线标记判断某事件在这条线上是否仍然发生（推演节点已记事件与标记，不需要预留字段）
- 外传章节的细纲在编辑器里可编辑（第一期只在沉淀提案里可改，编辑器里只读）

**阶段三**：检索增强

- 知识条目与历史章节做向量化
- 新增 RAG 版上下文构建器，与摘要链混合召回——摘要链保证「线性剧情记忆」，RAG 补上「跨章细节召回」

## 13. 衡量指标

阶段一没有埋点（无后端、不收集数据），以下是阶段二接入后应该看的：

**留存的先行指标**

- 新建作品后 7 天内是否完成第一章（立项链路是否真的通）
- 导入旧稿的用户是否在导入后 3 天内写了新章节（存量入口是否真的接上）

**产品健康度**

- 待确认项的采用率与逐字段编辑率：编辑率过高说明生成质量不够，过低可能说明用户在盲目采用
- 摘要覆盖率（已完成章节中有摘要的比例）：这是长篇连贯性的命脉
- 每千字的 token 成本与缓存命中率

**风险信号**

- 备份率过低 → 数据丢失事故迟早发生
- 连续打卡中位数持续下降 → 计划功能在制造压力而不是习惯
