# 译文截断问题 · 修改方案评估

> 问题：「译文超出单次输出上限被截断」出现后，超长章没有任何出路 —— 整章重试还是截断。
> 本文评估可选修改方案并给出推荐。相关代码：`src/features/writing/translate.ts`、
> `src/features/import/ImportScreen.tsx`（`translateOne`）、`src/features/writing/TranslateSheet.tsx`。

---

## 1. 现状（问题定位）

| 事实                                                                                 | 出处                                                                |
| ------------------------------------------------------------------------------------ | ------------------------------------------------------------------- |
| 翻译是**整章一次流式调用**，一章只有一个请求                                         | `ImportScreen.translateOne` / `TranslateSheet`                      |
| `TRANSLATE_SOFT_LIMIT = 6000` 字符，只提示「可能被截断」**不拦截**                   | `translate.ts`、分章页提示                                          |
| 截断判定只认 `finishReason === 'length'`，且只有**导入链路**查；编辑器链路根本不查   | `translateOne` 抛错；`TranslateSheet` 无此判断                      |
| 缺失 `finishReason`、SSE 正常 EOF 断流、损坏尾帧都不算截断 —— 半截译文可能被当作成功 | `.agents/chunked-translation-implementation/requirements.md` 已核实 |
| 截断后整章标失败、保留原文；重试是**整章重试** → 超过上限的章永远译不完，死路        | `translateOne` 失败路径                                             |
| `useLlm.runStream` 不接受 `maxTokens`（客户端其实已支持 `max_tokens` 透传）          | `llm/useLlm.ts` / `OpenAiCompatibleClient.ts`                       |
| 世界观设定提取已有分块先例（`splitWorldviewText`，6000 字/块），但**翻译**没有分块   | `import/worldview.ts`                                               |

**根因**：6000 字符的软上限本身就是矛盾的 —— 它大于多数服务商默认输出上限（DeepSeek 默认约 4k token），所以「提示了也照样截断」；而真截断之后，产品给出的唯一出路（切小重译）意味着用户已经付过的输出 token 全部作废。

---

## 2. 方案对比

| 方案                                                                                                  | 改动量 | 能否根治        | 主要风险                                                                                                                          | 结论                 |
| ----------------------------------------------------------------------------------------------------- | ------ | --------------- | --------------------------------------------------------------------------------------------------------------------------------- | -------------------- |
| **A. 透传并调大 `max_tokens`**                                                                        | 极小   | 否，缓解        | 服务商绝对上限仍在；调太大对不支持的服务商报错                                                                                    | 顺手做               |
| **B. 续写循环**（截断后把已译尾部送回「继续」）                                                       | 中     | 否              | 续写点对不齐（重复/漏译/重写）；每轮重付前缀与已译上下文，成本高；中断即丢                                                        | 不做                 |
| **C. `.agents` 完整分段设计**（segment 计划 + attempt/lease/outbox/二分树 + 协议 envelope + 备份 v5） | 极大   | 是              | 两轮评审未过（15 + 5 项发现，3 项 HIGH）；分布式任务系统量级，单用户本地应用用不上租约与 outbox 协调；Dexie v8 + 备份 v5 迁移风险 | 不按原样实施，借思想 |
| **D. 轻量章内分段**（顺序逐段翻译 + 逐段落盘 + 单段重试）                                             | 中大   | 是              | 段间语感衔接；编辑器任务的持久化要新增数据模型                                                                                    | **推荐**             |
| **E. 降低软上限 + 引导切小**（现状强化）                                                              | 极小   | 否              | 只是把问题推回给用户                                                                                                              | 可顺手做兜底         |
| **F. 按服务商输出上限定段预算**（presets 声明 `maxOutputTokens`）                                     | 小     | 与 D 组合才成立 | —                                                                                                                                 | 与 D 组合            |

### 2.1 A：透传 `max_tokens`

把 `runStream` 的选项加 `maxTokens`，翻译任务按 profile 给一个较大值（如 8000 token）。

- 有效场景：服务商默认上限低、但允许更高（DeepSeek 默认 4k 可到 8k），能让软上限「6000 字符」重新落在可译范围。
- 局限：① 绝对上限仍在，长章照截；② 大 `max_tokens` 对部分服务商直接报错（需要能力位）；③ 不解决「缺失 finishReason 时无法证明完整」。
- 结论：**一行级改动，先做**，但只能当方案 D 的地基，不是答案。

### 2.2 B：续写循环

截断时把「已生成译文结尾 + 请从某处继续」再发一次，拼接。

- 拼接点对齐是文学翻译里最不可靠的事：模型极易重复上一段、漏掉一句、或「总结式重写」。要保证质量就得做接缝校验，而接缝校验的复杂度与分段方案相当 —— 花同样的钱，拿不到分段方案的恢复能力。
- 每轮都重付系统前缀 + 已译上下文，长章多轮下来输入成本高于分段。
- 结论：**不做**。

### 2.3 C：`.agents` 完整分段设计（为什么不直接上）

`.agents/tasks/chunked-translation-implementation/design.md`（1920 行）已经设计了完整方案：安全切分、segment/attempt/candidate 状态机、lease 租约、outbox 按序译名同步、失败二分、run batch 成本上限、协议 envelope、备份 v5。方向是对的，但：

1. **两轮评审都是 CHANGES_REQUESTED**（第一轮 15 项、第二轮 5 项，含 3 项 HIGH：备份 merge 数据丢失、stale 窗口覆盖作者输入、v5 损坏备份可静默丢付费进度）；
2. 复杂度是**分布式任务系统**的量级 —— 租约、outbox、批次数、二分树，是为多标签页并发与崩溃恢复设计的。这是单用户本地应用，实际并发来源只有一个浏览器标签页；
3. Dexie v8 + 备份 v5 的迁移与评审修复意味着数千行改动和高回归风险。

**但它的三个核心思想值得借**：① Markdown/Unicode 安全切分（不拆围栏、不拆 grapheme）；② 每段落地前做本地完整性校验；③ 译名按段先行同步（先到先得不被后面的段推翻）。

### 2.4 D：轻量章内分段（推荐）

**做法**：

1. **切段**：按段落/空行边界切，保护 Markdown 围栏、表格、行内代码（整块作为一个原子段，超预算也不拆）；切点落在 grapheme 边界。单段预算 3000 字符（或按服务商输出上限折算，见 F）。
2. **逐段顺序调用**：
   - 系统提示词**整章共用、逐字节相同** → 第二段起命中 prompt 缓存，输入成本增量很小（这是分段方案成本可行的关键）；
   - 每段用户提示 = 已定译名（只注入本段出现过的）+ **上一段译文结尾 ≤300 字**（接住语感）+ 本段原文；
   - 每段照旧走流式纯文本 + 尾部译名表解析。
3. **每段落地即持久化**（导入 → `ImportDraft.translationPlan`，drafts 是 blob 字段，**不升 Dexie 版本**；编辑器 → 新增一张任务表，见下）—— 中断恢复时已付费的段不重跑。
4. **完整性校验**（本地，不引入协议 envelope）：译文非空、译/源长度比例在 `[0.2, 3]` 区间、抽查受保护 token（数字编号、代码、URL 等不能丢）。
5. **失败**：单段重试一次；仍失败 → 该章标失败，但保留已成功段，重试只跑失败段。不做自动二分。
6. **译名**：每段完成后立即并入本章累计表（内存），供下一段注入；整章完成后才写作品级译名表（避免半章污染库）。
7. 全部段成功后拼接成整章译文，之后流程与现在完全一致（写入 drafts / 编辑器可编辑预览）。

**成本账**：N 段 = N 次调用，输出 token 总量基本不变；输入多付 N−1 次用户提示（每段原文 + 尾部衔接），系统前缀因缓存命中只付一次。对比现状：超限章整章重试一次失败 = 全部输出 token 白花，分段后失败面只有一段。

**主要工作量与风险**：

- 核心切分/组装/循环约 500–800 行 + 40–60 个测试；
- 编辑器链路（`TranslateSheet`）的持久化是唯一需要数据模型决策的点：现状运行状态全在 React state，关面板即丢。两个选项：① 与导入共用思路，加一张 `ChapterTranslationJob` 表（Dexie v8）；② 第一期只做导入链路，编辑器仍整章（超限时提示走导入），第二期再补。**建议选项 ② 起步**——用户报的问题发生在导入链路，编辑器单章翻译的场景（作者自己贴的长文）频率低得多，先不扩大迁移面。
- 段间语感衔接用「上一段尾注入」缓解，质量风险可控。

### 2.5 E：降低软上限 + 引导切小

`TRANSLATE_SOFT_LIMIT` 从 6000 降到约 4000（按多数服务商默认上限保守折算），超限章在分章页给更醒目的提示（标红 + 说明切小后每章都更稳）。

- 与 D 不冲突：D 落地前它是兜底，D 落地后它退居为「预算提示」。
- 结论：零风险，顺手做。

### 2.6 F：按服务商输出上限定段预算

`presets.ts` 给每个服务商加 `maxOutputTokens` 能力声明（DeepSeek 8k、OpenAI 64k、Anthropic 32k 等，自定义端点取保守值），段预算 = 上限的保守折算（按中文 ≈0.6 字/token 反推）。与 D 组合后，长章在输出上限高的服务商上分 1–2 段，在 DeepSeek 上分多段 —— 分段数自适应，成本最优。

## 3. 推荐

**实施方案 D（轻量章内分段）+ F（按输出上限定预算）+ A（maxTokens 透传），E 作为兜底顺手做。**

第一期范围（建议）：

1. `translate.ts` 拆出「安全切段 + 逐段循环 + 校验 + 拼接」共享核心；
2. 导入链路接上：`ImportDraft.translationPlan` 落段进度，断点续跑、单段重试、失败保留已成功段；
3. `useLlm` 透传 `maxTokens`，presets 声明输出上限；
4. 编辑器链路暂保持整章（超限提示「导入旧稿」路径），第二期再做 `ChapterTranslationJob` 持久化。

**明确不做**：`.agents` 那版设计里的 lease 租约、outbox 协调、二分树、协议 envelope、备份 v5 —— 单用户本地应用用不上多标签页并发协议，把复杂度留给真正需要的阶段二（云同步）再评估。

工作量粗估：核心 + 导入链路约 500–800 行实现、40–60 个测试；比现状多付的输入成本被 prompt 缓存吸收大半；失败重试成本从「整章」降到「单段」。

## 4. 实施记录（2026-10-25）

方案 D 已按上述第一期范围落地（导入链路），详见 [开发计划.md](./开发计划.md)「增量：长章自动分段翻译」。与原方案的两处出入：

- **单段章节走旧路径**：一段就译完的章节，提示词与文案与改动前逐字节相同（`noScenarioBaseline` 基线不动），多段才出现「第 k/N 段」标注；
- **译名回滚天然成立**：段译名只在段成功时提交，失败段从不提交贡献，无需显式回滚。

`maxTokens` 透传（A）与编辑器链路（第二期）仍未做：分段预算 3000 字已落在多数服务商默认输出上限内，暂不需要 A。
