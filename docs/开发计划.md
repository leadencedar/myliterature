## Task 1: 项目脚手架与移动端外壳

- [x] 完成

**目标**：一个能在手机上打开、可添加到主屏、导航可用的空壳应用。

**实现要点**

- Vite + React + TypeScript + Tailwind CSS
- 测试环境：Vitest + React Testing Library + jsdom
- 底部 Tab 导航五项：书架 / 知识库 / 写作 / 计划 / 设置
- 移动端适配：`safe-area-inset` 处理、最小 44px 触控目标、`viewport-fit=cover`
- PWA manifest，支持添加到主屏
- 严格 CSP，`connect-src` 白名单化，不引入任何第三方分析 / 广告脚本

**测试要求**

- 导航渲染与路由切换冒烟测试

**Demo**：手机浏览器打开可在五个空白 Tab 间切换，可添加到主屏。

**实际落地记录**

- 依赖全部锁定精确版本：React 19.3.0 / Vite 8.3.0 / Tailwind 4.3.3 / Vitest 5.0.1 / TypeScript 7.0.2 / Zod 4.6.5 / Dexie 4.4.6
- CSP 通过 Vite 插件注入 `index.html`，开发模式额外放开 `ws:`/`wss:`（HMR 需要），生产不含。`connect-src` 白名单化，只允许已登记的模型服务商域名 —— 密钥存本地时这是防外传的关键一层。新增自建端点需同步在 `vite.config.ts` 的 `LLM_ENDPOINT_ALLOWLIST` 登记
- PWA 采用「manifest + apple-touch-icon，不注册 Service Worker」：iOS 添加到主屏只需 manifest，省去 SW 的缓存失效复杂度。若后续要 Android 安装横幅或离线能力，再补 SW
- 图标用 `scripts/generate-icons.mjs` 手写 PNG 编码器生成（zlib + 有向距离场 + 3×3 超采样），零图形依赖、产物可复现
- 验证结果：typecheck 通过、8 个测试通过、生产构建通过（gzip 后 JS 84.5 kB / CSS 3.35 kB）

## Task 2: 数据层与小说 CRUD

- [x] 完成

**目标**：持久化基础设施就位，小说可增删改且刷新不丢。

**实现要点**

- Zod 定义全部实体 schema，作为 TS 类型与运行时校验的**唯一事实源**
- 定义 `NovelRepository` 接口（阶段二替换实现的边界）
- Dexie（IndexedDB）实现，含版本化迁移骨架
- 书架页：小说建 / 改 / 删，卡片展示字数与更新时间

**测试要求**

- Repository 全接口单元测试（跑在 fake-indexeddb 上）
- 迁移测试

**Demo**：创建多本小说、重命名、删除，刷新页面数据仍在。

**实际落地记录**

- `src/domain/schema.ts` 一次性定义了全部 10 类实体的 Zod schema（Novel / Category / KnowledgeEntry / OutlineNode / Chapter / ChapterSummary / StyleProfile / Proposal / WritingPlan / DailyLog），后续任务直接复用，避免schema 分批定义导致漂移
- `NovelRepository` 接口覆盖全部实体的读写，`DexieNovelRepository` 提供完整实现。后续任务只消费接口，不再碰 Dexie
- 关键实现决定：
  - **时间表示分两种**：`createdAt`/`updatedAt` 用 epoch 毫秒便于排序，写作计划与日志用本地日期字符串 `YYYY-MM-DD` —— 「每日一章」关心的是用户时区的自然日，用时间戳做日界判断会在跨时区和夏令时出错
  - **软删除字段不建索引**：IndexedDB 不为 null 建索引项，「未删除」这个最常用查询反而走不了索引，统一在内存过滤
  - **章节字数始终由正文推导**，`updateChapter` 忽略外部传入的 `wordCount`，从源头杜绝两者不一致
  - **删除小说级联硬删**十张表的从属数据；**删除大纲节点级联删子树但保留章节正文**，仅解除关联（正文是用户资产）
  - **内置分类删除保护**：`updateCategory` 强制保留原 `builtin` 值，防止绕过保护；分类下有条目时拒绝删除
  - `findEntryByName` 按 title ∪ aliases 归一化匹配，这是 Task 12 反向提取判断「新增还是合并」的基础
- **不用 dexie-react-hooks 的 useLiveQuery**：它依赖 Dexie 的可观察性，会把组件层与存储实现绑死。改为 `useRepoQuery` + 全局数据版本号显式失效，用少量重复查询换取存储无关性，阶段二换 Supabase 时组件层零改动
- UI 层顺带修掉两个可用性问题：`新建作品` 曾同时作为头部图标按钮与空状态按钮的可访问名（读屏无法区分），空状态改为「创建第一本作品」；Sheet 标题栏的文字「取消」与确认框底部的「取消」重复，标题栏改为图标式「关闭」，遮罩层改为 `aria-hidden` 不再暴露为重复的可聚焦控件
- 验证结果：typecheck 通过、57 个测试通过（含 40 个仓储层用例 + 9 个书架页交互用例）、生产构建通过

## Task 3: LLM 适配层与设置页（DeepSeek 优先）

- [x] 完成

**目标**：能真实调用 DeepSeek 并看到流式输出，结构化输出可靠。

**实现要点**

- OpenAI 兼容适配器，默认预置 DeepSeek：`https://api.deepseek.com`，模型 `deepseek-flash` / `deepseek-v4-pro` 可选
- `fetch` + SSE 流式解析、请求取消（AbortController）、错误与限流处理
- thinking 模式按任务类型配置：推理类开 `reasoning_effort: high`，正文关闭
- 结构化输出双模式：能下发 JSON Schema 就下发，否则 prompt 内嵌 schema 说明
- 响应一律 Zod 校验，失败携带错误信息做一次修复重试
- 设置页：baseUrl / apiKey / model / 温度、「测试连接」、密钥本地存储风险提示

**测试要求**

- mock fetch 覆盖：流式分块解析、schema 校验失败后修复重试、请求取消、thinking 参数透传

**Demo**：填入 DeepSeek Key，点「测试连接」看到流式文字逐字出现。

**实际落地记录**

模块划分（`src/llm/`）：

| 文件                        | 职责                                   |
| --------------------------- | -------------------------------------- |
| `types.ts`                  | 请求/响应/能力位的公共类型             |
| `errors.ts`                 | `LlmError` 与 HTTP 状态码映射          |
| `sse.ts`                    | SSE 流解析（独立可测）                 |
| `presets.ts`                | 服务商预置与能力声明                   |
| `taskProfiles.ts`           | 任务 → 模型/温度/thinking 的映射       |
| `OpenAiCompatibleClient.ts` | 请求组装、流式与非流式调用             |
| `structured.ts`             | JSON Schema 下发 + Zod 校验 + 修复重试 |
| `settingsStore.ts`          | 配置持久化（localStorage）             |
| `useLlm.ts`                 | 业务层唯一调用入口                     |

关键实现决定：

- **能力位显式声明，不靠 baseUrl 猜**。`ProviderCapabilities` 有四个开关：`jsonSchema` / `thinkingToggle` / `reasoningEffort` / `streamUsage`。DeepSeek 是 `jsonSchema: false`（只有 `json_object`）但 `thinkingToggle: true`；OpenAI 反之。**自定义端点取最保守能力集** —— 宁可退化成 prompt 内嵌 schema，也不要因为下发了不被支持的参数导致整次请求失败
- **结构化输出三层防护**（因为模型输出不可信，DeepSeek 的 `json_object` 只保证是合法 JSON）：① JSON Schema 内嵌进 prompt（所有 provider 都吃这套）；② 支持严格模式的额外下发 `response_format`；③ 一律 Zod 校验，失败则把**原始输出 + 具体字段错误**一起回灌给模型做修复重试。回灌具体错误而非单纯重试，是成功率的关键
- **`z.toJSONSchema(schema, { io: 'output' })`**：output 模式会把带默认值的字段也列入 `required`，强制模型输出每个字段。否则模型省略字段、本地默认值悄悄补上，会掩盖生成缺陷
- **SSE 解析单独成模块并重点测试**：网络分块与事件边界毫无关系，一个 JSON 对象经常被拦腰截断。覆盖了跨分块截断、分块边界正好落在换行符、CRLF、心跳注释行、`[DONE]` 提前终止、无换行收尾等 10 种情形。单条坏 chunk 返回 undefined 而不是抛错 —— 一条坏 chunk 不该让整次生成失败
- **按任务分配参数**（`TASK_PROFILES`）：结构化推理任务开 thinking（立项/大纲用 `high`，摘要用 `medium`），正文创作关 thinking —— 推理模式会让散文解释性过强、文气断裂。温度同步分化：抽取与摘要压到 0.2 保证可复现，正文给到 0.95
- **回显 token 缓存命中数**。`TokenUsage.cachedPromptTokens` 同时兼容 DeepSeek 的 `prompt_cache_hit_tokens` 与 OpenAI 的 `prompt_tokens_details.cached_tokens`，连通性测试会显示出来 —— 这是后续验证「稳定前缀是否真的命中缓存」的唯一可观测指标
- **密钥存 localStorage 而非 IndexedDB**。备份导出走 IndexedDB 全量导出，密钥从物理上就不可能进备份文件，比「导出时记得过滤」这种依赖自觉的做法可靠。切换服务商时一并清空旧 Key（Key 不通用，留着只是风险）
- 错误分类到可操作粒度：402 → 提示充值，429 → 提示稍后重试，网络失败 → 提示检查连接白名单，401 → 提示检查密钥，并保留服务端原文供排查

**验证结果**：typecheck 通过、125 个测试通过（新增 68 个：SSE 解析 12、客户端 24、结构化生成 21、设置页 11）、生产构建通过。
**尚未验证**：没有真实 API Key，未对 DeepSeek 线上接口做过实际调用。设置页的「测试连接」就是这条验证路径，填入 Key 点一下即可确认。

## Task 4: Proposal 确认管道与折叠预览组件

- [x] 完成

**目标**：所有 AI 产出的唯一落库通道建成，确认 UI 可复用。

**实现要点**

- `Proposal` 模型：`create` / `merge` / `replace` 三种意图
- 字段级 diff 计算
- accept / reject 与事务化落库
- 通用预览组件：可折叠分区、分区「重新生成」、行内编辑、底部「全部采用」

**测试要求**

- diff 计算与合并落库单元测试
- 预览组件交互测试

**Demo**：从任意 prompt 生成一个知识条目，预览中编辑后采用，条目入库。

**实际落地记录**

模块划分：

| 文件                                       | 职责                                                     |
| ------------------------------------------ | -------------------------------------------------------- |
| `src/proposal/fields.ts`                   | 字段规格：把各类实体拍平成可展示/可编辑/可比较的字段列表 |
| `src/proposal/diff.ts`                     | 差异计算、差异摘要、合并规则、行内编辑回写               |
| `src/proposal/build.ts`                    | 三种提案的构造函数 + `newBatchId()`                      |
| `src/proposal/apply.ts`                    | 落库（唯一写库通道）+ 批量采用/忽略                      |
| `src/ui/ProposalReview.tsx`                | 折叠分区预览组件（纯展示，不碰数据层）                   |
| `src/features/proposals/ProposalInbox.tsx` | 接数据层的收件箱，Task 6 / 8 / 11 / 12 共用              |
| `src/app/RequireNovel.tsx`                 | 「当前作品」上下文守卫，三个 Tab 共用                    |

关键实现决定：

- **`applyProposal` 是 AI 产出进入数据库的唯一通道**。功能模块没有旁路可以直接写库，所以「所有自动生成内容都要经用户确认」是架构上的单行道，而不是各处自觉。`switch` 用 `never` 做穷尽检查，将来新增 target/action 组合会直接编译报错提醒补实现
- **字段规格（FieldSpec）统一抽象**。确认管道要面对知识条目、大纲节点、章节、摘要、风格档案、小说六种形态，如果每种写一套预览 UI 和编辑逻辑会失控。知识条目的字段规格由**所属分类的 `fieldTemplate` 动态生成**，所以用户改过分类字段后预览界面自动跟着变
- **合并契约**（与 Task 12 的提取提示词配套，写死在 `mergeEntities`）：
  - 列表字段取并集去重（忽略大小写）—— 别名、关键事件是累加信息，覆盖会丢数据
  - 原值为空 → 采用新值
  - **新值为空 → 保留原值**。模型没提到某字段不等于该字段应被清空，这是反向提取最容易造成静默数据损失的地方
  - 两边都有值且不同 → 采用新值并标为「改动」交给用户裁决。敢直接取新值的前提是：提取时会把现有内容一并给模型，要求它输出**整合后的完整字段**，所以新值本身是「旧值 + 新信息」而非替代品
- **合并类提案的 payload 存的是合并结果**，diff 记录相对原值的变化。用户既能整体采用，也能对单个字段点「还原」退回原值 —— 这是「整体预览 + 局部编辑」交互取向的落点
- **批量采用逐条处理而非整体事务**。一条失败（比如目标条目已被手动删除）不该让其余十几条一起回滚；失败项保持 pending 并在界面上报告原因，用户可单独处理
- **落库用的是用户编辑后的 payload**，不是模型原始输出 —— 预览里的修改直接参与 accept，无需先保存再确认
- 两边都空的字段不进 diff、不渲染，否则一个人物条目会展开出十几个空输入框
- 忽略提案只改状态不删记录，便于回溯「当时拒绝了什么」

**验证结果**：typecheck 通过、196 个测试通过（新增 29 个：字段编解码 13、diff 与合并 18、落库 12、预览组件 19、收件箱集成 10）、生产构建通过。
**已知待办**：打包体积触发了 Vite 的 500 kB 分包提示（gzip 后 162 kB）。移动端目前可接受，后续若继续增长，按路由做动态 import 拆包。

## Task 5: 风格档案模块

- [x] 完成

**目标**：风格可选可调，且 prompt 稳定前缀可复现以命中缓存。

**实现要点**

- 三维度选择器：文体取向（含子类）/ 创作方法论 / 名家风格参考
- 内置作家风格库（结构化 rubric，可读可编辑）
- 名家风格强度滑杆 0–100，可选 0–2 位
- 自定义风格档案
- 「文风取样」：从示例文本提炼 rubric，走确认管道
- prompt 稳定前缀组装器，保证同一档案两次组装**字节级一致**
- UI 上一行版权边界说明

**测试要求**

- 同一档案两次组装输出完全一致（缓存友好性回归测试）
- rubric 提炼集成测试

**Demo**：新建小说时选「网络文学·仙侠 + 古龙风格 70%」，或贴一段文字生成自定义风格档案。

**实际落地记录**

模块划分：

| 文件                                  | 职责                                                       |
| ------------------------------------- | ---------------------------------------------------------- |
| `src/prompt/voiceLibrary.ts`          | 11 位名家的风格 rubric 库 + `RUBRIC_DIMENSIONS`            |
| `src/prompt/traditions.ts`            | 文体取向（含子类约定）与创作方法论（含大纲结构）           |
| `src/prompt/sections.ts`              | prompt 片段组装 + `composeStylePrefix` 稳定前缀            |
| `src/features/style/styleSample.ts`   | 文风取样的 schema、提示词与长度校验                        |
| `src/features/style/StyleSection.tsx` | 三维度编辑器（摘要卡片 + 抽屉表单）                        |
| `src/ui/Controls.tsx`                 | SegmentedControl / ChipGroup / RadioList / Slider / Toggle |

关键实现决定：

- **风格库存的是特征描述，不是作品原文**。每位作家一组七维 rubric（句式节奏、意象偏好、叙述距离、对话风格、修辞习惯、词汇色彩、需要避免），全部是对可观察手法的归纳。这样既不把他人作品塞进 prompt，也让生成更可控 —— 模型照特征写比照片段模仿稳定得多。范围限定已故经典作家，界面上明示「不宜宣称与某位作家的关联」
- **强度转成档位词而非裸数字**。滑杆值 0–100 在进 prompt 时映射为「强烈贴近／明显偏向／适度借鉴／略带一点」，模型对档位词的理解比对「70」稳定
- **文体取向与方法论的文案集中在一处**。`guidance` 管怎么写、`outlineStructure` 管大纲长什么样，立项、大纲扩写、正文生成三个环节引用同一份定义，避免模型在不同环节收到互相矛盾的要求
- **切换文体取向时清空子类**。子类列表随取向变化，留着会产生「严肃文学 + 仙侠」这种无效组合
- **稳定前缀的可复现性是硬约束，有专门的回归测试**：同一输入两次组装必须逐字节相同；对象属性书写顺序不同不影响输出；`updatedAt` 变化不影响输出。测试还校验四个段落按固定顺序出现、段间恰好一个空行 —— 这些都是 prompt 缓存命中的前提，输入价差可达 50 倍
- **文风取样复用确认管道**。提炼结果转成 `styleProfile:replace` 提案，在抽屉内嵌 `ProposalInbox` 按批次确认，与其他 AI 产出的处理路径完全一致
- 自定义 rubric 与名家风格**叠加**而非互斥，且确认后可在界面上继续逐字段修改

**修掉的一个真实缺陷**：抽屉的状态重置 effect 原本依赖 `style` 对象，而它在任何数据刷新后都是新引用。结果文风取样一落库就触发刷新，刚生成的确认面板被立刻卸载，用户未保存的编辑也会被冲掉。改为只在「关闭 → 打开」的瞬间重置（`useRef` 记录上一次的开合状态，用 ref 读取最新档案）。

**Demo**：输入一句话，得到一套完整初始知识库，任一分区可单独重生成。

**实际落地记录**

模块划分：

| 文件                                  | 职责                                  |
| ------------------------------------- | ------------------------------------- |
| `src/proposal/outlineText.ts`         | 大纲树 ↔ 缩进标题文本的双向转换       |
| `src/features/setup/projectSetup.ts`  | 输出 schema（动态）、篇幅规模、提示词 |
| `src/features/setup/SetupSection.tsx` | 立项表单 + 生成 + 确认                |

**最关键的设计决定：大纲作为一个整体提案，内容用缩进标题文本承载。**

逐节点提案走不通有两个原因：技术上，子节点的 `parentId` 在父节点落库前不存在，逐条确认会把落库顺序变成隐式依赖；体验上，一份二十节点的大纲拆成二十个折叠块，在手机上根本没法通读，而大纲恰恰是需要整体把握的东西。

改为整棵树一个提案后，payload 只是一个字符串字段（`outlineText`），于是 diff、行内编辑、还原、忽略全部复用现成机制，确认管道不需要为树结构开任何特例。用户看到的是一段可直接编辑的大纲文本，调整层级就像改 Markdown 列表。格式：

```
# 第一卷 风起（约 30000 字）
主角被追杀，逃入雪山。
## 第1章 雪夜（约 3000 字）
追兵临门。
```

解析以容错为先：层级跳跃（`#` 后直接 `###`）、开头就是深层标题、标题前有杂散文字、半角括号、带千分位的字数都能正确处理，因为这段文本会被用户手改。

其他关键决定：

- **输出 schema 由分类的字段模板动态生成**。内置分类的字段可能被用户改过，立项就应该按当前模板生成，否则结果会带着界面上不存在的字段、或缺掉用户新加的字段。有专门的测试证明 schema 真的跟着模板走
- **模型输出的大纲限定两层**（卷 → 章）。两层足够表达全书结构，也让下发的 JSON Schema 保持可读，避免递归 schema 的麻烦
- **长篇只要求展开前两卷**。后段应当在写作过程中随剧情生长，过早细化只会被推翻，也白花 token
- **`core` 标记映射为条目的 `pinned`**。由模型判断哪些是「每次写作都必须遵守的底层规则」，提示词里限定通常 1–2 条，避免全部标成核心导致每次注入过量
- 一句话是用户自己写的，不属于 AI 产出，直接落库；只有生成结果走确认管道
- 已有大纲时生成 `replace` 提案并把现有大纲作为 diff 原值，用户能看清改了什么；`replace` 落库时先清空旧节点（删根节点级联子树），章节正文不受影响

**修掉的一个真实缺陷**：同一批提案往往在同一毫秒创建，仅靠 `createdAt` 排序结果不确定，用户每次看到的顺序都可能不同（大纲可能排在世界观前面）。给 `Proposal` 增加了显式 `order` 字段，排序改为 `createdAt → order → id`，末位用 id 兜底保证任何情况下都是确定序。立项按「世界观 → 人物 → 大纲」显式编号。

**测试稳定性**：这一步暴露了两类测试竞态，都已修正 —— 一是 `findByText(/已生成/)` 在提案列表异步加载完成前就返回，后续同步查询扑空；二是大纲 `replace` 是「先删旧、再逐个建新」，存在节点数不足的瞬时状态，断言必须整体等到终态。修正后连续运行 10 次全绿。

**已知限制**：`applyProposal` 对大纲 `replace` 的删除与创建跨多次 await，不是原子操作。中途失败会留下部分替换的大纲。因为仓储接口没有暴露跨调用事务，且失败后重新采用提案即可恢复，暂不处理；若后续要解决，需要在 `NovelRepository` 上开一个事务入口。

**验证结果**：typecheck 通过、305 个测试通过（新增 56 个：大纲文本转换 24、立项 schema 与提示词 14、立项端到端 18）、生产构建通过。

关键实现决定：

- **界面过滤在内存里做**，不是每敲一个字就查库：单本小说条目量在数百级别，内存过滤是即时的，而搜索框最需要的就是无延迟反馈

- **条目删除走软删除 + 回收站**。设定条目常常是写了几万字之后才发现「当初那条其实有用」，给一条后悔的路比省一张表重要
- 分类被删但条目仍在时，列表兜底显示为「未分类」分组，不让条目凭空消失
- 条目卡片没有摘要时，退而展示第一个有内容的字段，避免卡片上只剩一个名字

**修掉一个影响全局的缺陷**：`RequireNovel` 在每次数据失效时都会进入 `loading` 分支返回占位页，**把整棵子树连同所有打开的抽屉和未保存输入一起卸载重建**。表现是「新建空白分类后编辑抽屉一闪而过」，但影响面远不止此 —— 任何写操作后的刷新都会毁掉用户正在填的表单。

根治方式是改 `useRepoQuery` 的语义为 stale-while-revalidate：

- 已有数据时刷新**保留数据**，只把新增的 `refreshing` 标志置真，`loading` 保持假；
- `deps` 变化（如切换到另一本书）才清空数据并回到 `loading` —— 此时旧数据不再相关，短暂显示上一本书的内容比空白更糟。

这条不变量很容易在将来被改回去，因此补了专门的测试守住它。Task 5 里那处「用 ref 记录 open 状态才能避免抽屉被冲掉」的绕法，本质上也是这个缺陷的局部症状。

**实际落地记录**

大纲落在「写作」Tab 而不是「知识库」：它是写作的目录，Task 9 的章节编辑器会直接从节点进入。知识库页只留一个概览。

| 文件                                        | 职责                                           |
| ------------------------------------------- | ---------------------------------------------- |
| `src/features/outline/outlineTree.ts`       | 树结构的纯逻辑：建树、折叠摊平、四种移动、统计 |
| `src/features/outline/OutlineTreeView.tsx`  | 树视图与行内排序操作                           |
| `src/features/outline/outlineExpand.ts`     | AI 细化的 schema 与提示词                      |
| `src/features/outline/OutlineNodeSheet.tsx` | 节点编辑 + 关联设定 + AI 细化                  |
| `src/features/writing/WritingPage.tsx`      | 进度概览 + 大纲树                              |

关键实现决定：

- **排序用明确的按钮而不是拖拽**。移动端在嵌套树上做拖拽既难瞄准（手指遮挡目标位置），也无法被读屏用户使用；按钮方式每一步结果确定，还能把层级逻辑做成纯函数单测。为了不让每行都挂四个按钮，它们收在行内的排序把手后面，一次只展开一行
- **所有树操作都是纯函数**：输入节点列表 + 操作，输出 `{id, parentId, order}` 更新列表。任何操作之后都**重新归一化受影响分组的 order 为 0..n-1**，而不是做增量调整 —— 稀疏或重复的 order 一旦出现极难排查，每次重排一遍的代价可以忽略。24 个纯函数测试覆盖了移动、缩进、层级上限、可逆性
- **层级上限 3 层**（卷/章/节）。再深移动端缩进就没法看了。`canIndent` 会连同被移动节点的子树高度一起判断，避免降级后超限
- **AI 细化复用 `outlineTree` 提案**，payload 增加可选 `parentId`：为空是整本书顶层（立项场景），指定节点则是「把这份子树挂到该节点之下」（雪花法逐层扩写）。`create` 追加到已有兄弟之后，`replace` 先清空该层再重建。一个 target 覆盖两种场景，不必再引入新的提案类型
- 细化的提示词会带上**祖先链、同层兄弟节点、已有子节点、关联设定** —— 兄弟节点用于划定边界（「不要写进它们的内容」），这是避免相邻节点内容重叠的关键

**修掉两个真实缺陷**：

1. **`buildOutlineDrafts` 假定根节点的 `parentId` 为 null**。给它传一个子节点列表会得到空树，导致「细化已有子节点的节点」时 diff 把替换误判成纯新增，用户看不到将被覆盖的原有细目。改为接受显式的 `rootParentId` 参数，并要求传入完整节点列表（否则孙节点会丢）
2. **同一批提案出现两个确认入口**：细化生成的提案既在抽屉内的确认面板里，也在页面背后的「待确认」区。视觉上被遮住了，但读屏与自动化都能看到两份，用户也可能误操作两次。在 `Sheet` 里加了全局弹层计数 `useAnyModalOpen()`，页面级确认区在有弹层打开时不渲染。知识库页存在同样的隐患（风格抽屉内嵌确认面板），一并修了

另外把组件文件从 `OutlineTree.tsx` 改名为 `OutlineTreeView.tsx`：它与逻辑文件 `outlineTree.ts` 仅大小写不同，在 macOS 的大小写不敏感文件系统上会被 TypeScript 判为同一文件。

**验证结果**：typecheck 通过、386 个测试通过（新增 48 个：树逻辑 26、写作页与细化 22），连跑 3 次稳定，生产构建通过。

## Task 9: 章节编辑器与整章生成

- [x] 完成

**Demo**：选中大纲节点生成整章正文，并能看到本章依据了哪些设定。

**实际落地记录**

| 文件                                            | 职责                                |
| ----------------------------------------------- | ----------------------------------- |
| `src/context/tokens.ts`                         | token 估算与展示格式化              |
| `src/context/ContextBuilder.ts`                 | 接口与类型（阶段三 RAG 的替换边界） |
| `src/context/SummaryChainContextBuilder.ts`     | 摘要链实现：装箱、预算、注入清单    |
| `src/features/writing/chapterDraft.ts`          | 正文生成提示词                      |
| `src/features/writing/ChapterEditorScreen.tsx`  | 全屏编辑器 + 自动保存               |
| `src/features/writing/GenerateChapterSheet.tsx` | 注入预览 + 流式生成 + 确认          |

**装箱顺序与缓存的关系（这一步最关键的决定）**

```
稳定前缀  1 作品信息+风格档案 → 2 核心设定 → 3 勾选的关联条目
易变后缀  4 大纲位置 → 5 全书进展 → 6 最近章节摘要 → 7 上一章结尾原文
```

与最初的设计方案相比，**把「大纲位置」从稳定前缀移到了易变后缀**。理由：prompt 缓存是按前缀匹配的，大纲每章都不一样，放进前缀会让公共前缀截断在很靠前的位置，后面的核心设定与人物档案就全都命中不了缓存。前缀里只放「整本书都一样」的东西，缓存收益才最大。

其他关键决定：

- **预算约束的是成本与模型注意力，不是上下文窗口**。DeepSeek 有 1M 窗口，塞得进去不代表该塞 —— 无关设定越多模型越容易被带偏，钱也白花。默认预算 24k tokens
- **作品信息、核心设定、大纲位置不参与预算裁剪**。缺了这三样模型根本不知道在写什么，宁可超预算
- **核心设定与用户勾选是两个互不重叠的集合**。pinned 条目始终注入且不出现在可勾选列表里 —— 若让它也走勾选逻辑，就会变成能被预算挤掉的普通条目，「核心设定」这个标记也就没意义了。修这个问题时顺手改了默认预选的语义：只含「节点关联 ∪ 上一章出场」
- **上一章出场的条目要带进默认预选**，否则连续两章里同一个人物的说话方式会突然变样，这是长篇里最容易被读者察觉的崩坏
- **默认预选后来补了两个推断来源**（大纲标题/梗概、上一章摘要正文/关键事件的本地名称匹配）。见下面「已修缺陷记录：默认预选形同虚设」
- **token 估算只是估算**（中文 0.8/字，拉丁 0.25/字）。引入真 tokenizer 要几百 KB 体积，而请求返回的 `TokenUsage` 才是准数
- **生成流程分三步：先看依据 → 再生成 → 再确认**。生成前摆出注入清单与预估 token，用户能判断依据够不够、花销值不值
- **正文不走 Proposal 管道，改用轻量确认**（可编辑预览 + 采用/追加/放弃）。散文没有字段结构，对三千字整章做字段级 diff 不提供任何额外信息，预览本身就是最好的确认。结构化数据（设定、大纲、摘要）仍然一律走确认管道 —— 这是一条有意的分界，不是遗漏
- **编辑器做成覆盖全屏的面板而非底部抽屉**：写作需要尽可能大的可视区域。保存采用 800ms 防抖自动保存，离场时立即冲刷；标题栏实时显示「有改动 / 保存中 / 已保存」，让用户对「我的字有没有丢」始终有把握
- 从叶子大纲节点点「写这一章」即建章节、挂上关联、并把节点标记为「在写」；有子节点的节点不提供该入口（说明还该继续往下拆）

**修掉一个真实缺陷**：`OpenAiCompatibleClient` 在构造时就把 `globalThis.fetch` 绑定住了。客户端实例被 `useMemo` 缓存较长时间，构造时绑定使它对运行环境的后续变化完全免疫 —— 测试里表现为「替换了全局 fetch 却不生效」，生产里则意味着任何对 fetch 的后续包装（埋点、重试代理）都会被绕过。改为每次请求时解析。

**验证结果**：typecheck 通过、430 个测试通过（新增 44 个：token 与装箱 21、编辑器与生成 23），连跑 3 次稳定，生产构建通过。

## Task 10: 段落级续写 / 改写 / 扩写

- [x] 完成

**目标**：人机共创手感，移动端负担小。

**实现要点**

- 编辑器内选中文本触发操作
- 支持「按当前风格」或临时指定风格
- 结果以 diff 确认后替换，支持撤销

**测试要求**

- 选区映射与替换的边界用例（首尾、跨段）

**Demo**：选中一段对话点「扩写」，对比后接受，可撤回。

**实际落地记录**

| 文件                                   | 职责                                      |
| -------------------------------------- | ----------------------------------------- |
| `src/features/writing/revise.ts`       | 选区归一化、上下文取样、替换回写、提示词  |
| `src/features/writing/ReviseSheet.tsx` | 操作选择 + 临时文风 + 流式生成 + 对照确认 |
| `ChapterEditorScreen.tsx`（扩展）      | 选区捕获、撤销栈                          |

**选区归一化是这一步的核心难点**。用户在手机上划选很难精确到字，选中内容前后经常粘上空格或换行；若直接用原始的 `selectionStart/End` 做替换，段落分隔符会被吃掉，正文结构瞬间崩坏。因此所有操作都先把选区收缩到真正的文字边界再替换。纯函数测试覆盖了：选区两端带空白、起点在正文最开头、终点在最末尾、跨段落选择、反向拖选（终点在起点之前）、全空白选区、下标越界、空正文 —— 共 33 个用例。

其他关键决定：

- **三种操作的放置方式不同**：改写与扩写是「就地替换选中片段」，续写是「在选区之后另起一段插入」。续写的分隔符处理要避免出现三个以上连续换行，空正文时也不能产生前导空行
- **续写允许不选中**，此时目标是正文末尾；改写与扩写必须先选中，界面会直接说明原因并禁用主操作按钮，而不是让用户点了才报错
- **临时文风**是这一步独有的能力：想给某一段换个笔法试试，不必去改作品的风格档案，试完不满意直接放弃。提示词里明确声明「只是本次的临时要求，不改变作品既有的文风设定」，并且确实不落库
- **提示词把前文 / 待处理片段 / 后文分开给出**，后文标注「不要写进去，但要能接上」—— 否则模型经常把后文内容重写一遍，造成重复
- **自己维护撤销栈**，不依赖浏览器：程序化修改 `textarea.value` 会清掉原生撤销历史，而 AI 改写恰恰最需要「一键还原」—— 用户敢不敢试，取决于能不能退回来。整章生成与段落改写共用同一个栈，可逐步撤销
- 选区捕获同时监听 `onSelect`/`onKeyUp`/`onMouseUp`/`onTouchEnd`，移动端与桌面端的触发来源不一致

**顺手修掉的可用性问题**：分段控件里有「改写」选项，底部主操作按钮原本也叫「改写」，同一个抽屉里两个同名按钮，用户和读屏都难分辨。主操作改为「开始改写 / 开始续写 / 开始扩写」。

**验证结果**：typecheck 通过、484 个测试通过（新增 54 个：选区与替换纯逻辑 33、抽屉交互与撤销 21），连跑 3 次稳定，生产构建通过。

**实际落地记录**

| 文件                                           | 职责                               |
| ---------------------------------------------- | ---------------------------------- |
| `src/features/writing/chapterSummary.ts`       | schema、伏笔累计、名称解析、提示词 |
| `src/features/writing/ChapterSummarySheet.tsx` | 生成与确认                         |
| `ChapterEditorScreen.tsx`（扩展）              | 标记完成时自动触发、缺摘要提醒     |

**`openThreads` 的语义是「截至本章仍未收束的伏笔（累计）」，不是「本章新埋的伏笔」。** 这样上下文装箱只取最近一章的摘要就能拿到完整的待收束清单，不必回溯全书做集合运算。模型负责报告「本章新埋了什么」与「收束了此前哪几条」，集合运算在本地完成（`mergeOpenThreads`）—— 让模型做它擅长的判断，让代码做它擅长的精确计算。

其他关键决定：

- **由「把章节标记为已完成」自动触发生成**。摘要是后续所有章节的上下文来源，如果指望用户记得手动补，摘要链很快就会断；而断了之后的表现是「AI 越写越不记得前面的事」，用户往往归因为模型不行，其实是缺摘要。已完成但没有摘要的章节，编辑器上的入口会高亮成「补摘要」
- **一次调用同时产出本章摘要与更新后的全书进展**，省一个来回。落库时拆成两条提案（`chapterSummary` + `novel`），各自可独立确认或退回
- **`rollingSummary` 是整体替换而非增量**，提示词里专门强调「要写成完整独立的一段，不要写成增量补充」—— 否则模型会输出「此外，主角还……」这种没法单独阅读的片段
- **出场角色由模型从给定名单中选，名称在本地解析成 id**，匹配不上的直接丢弃。宁可少记一个出场，也不要往库里塞不存在的 id。别名也参与匹配，`林越` 与 `阿越` 会归并成同一条
- **摘要任务的系统提示只带作品信息，不带文风**。摘要与文风无关，省 token；而且这段前缀在全书各章之间完全一致，缓存命中率是所有任务里最高的
- 伏笔收束的匹配做了标点宽容处理：模型抄回时常多一个或少一个句号，严格比较会导致漏收束

**测试**：新增 37 个（纯逻辑 25 + 端到端 12）。端到端部分完整走了一遍「第一章写完 → 标记完成 → 自动提炼 → 确认 → 写第二章 → 生成时注入第一章摘要 / 关键事件 / 未收束伏笔 / 全书进展 / 上一章结尾原文」，这是摘要链真正要保证的东西。

修掉两处测试竞态（与前几步同类）：提案是依次落库的，多条提案的断言必须放进同一个 `waitFor`；渲染后直接写库的数据页面查询不可见，测试数据要在渲染前准备好。

**验证结果**：typecheck 通过、522 个测试通过，连跑 5 次稳定，生产构建通过。

**实际落地记录**

| 文件                                     | 职责                                                               |
| ---------------------------------------- | ------------------------------------------------------------------ |
| `src/features/import/splitChapters.ts`   | 分章：内置规则 / 整篇一章 / 自定义正则，以及合并、删除、改名、体检 |

| `src/features/import/ImportScreen.tsx`   | 全屏四步面板：粘贴 → 分章 → 提取 → 确认                            |
| `src/domain/schema.ts`（扩展）           | `ImportJob` / `ImportChapterState` / `ImportEntryDraft`            |

| `KnowledgePage.tsx`（扩展）              | 「管理」区的导入入口                                               |

**导入进度存 IndexedDB，不存组件状态也不存 localStorage。** 几十章的提取要跑十几分钟，移动端切后台、来电、误刷新都很常见，进度丢了就得重花一次钱。`ImportJob` 里带着每章标题与错误信息，长篇稿件下体积不小，localStorage 撑不住。一本书同时只允许一个任务（`&novelId` 唯一索引），重开面板直接落在提取步骤上。

其他关键决定：

- **一次调用同时产出设定与章节摘要**。两者都要求通读整章，拆成两次调用等于把最贵的那部分（输入 token）付两遍
- **提取提示词必须要求「整合后的完整字段」**。这是 Task 4 合并契约成立的前提：合并时标量字段直接取新值，只有当新值本身已经是「旧值 + 本章新信息」时才不会丢数据。因此本章涉及的已有条目要带**完整现有字段**一起给模型，并明确要求整合回填
- **条目草稿先在任务里按名称累计，跑完才 materialize 成提案**。主角会在几十章里反复出现，逐章出提案的话用户要处理上百条高度重复的待确认项，实际上没人会看完。累计的合并规则与 `mergeEntities` 完全一致，避免「章内累计」与「入库合并」两套语义打架
- **章节摘要提案相反，逐章即时创建** —— 它是「这一章」的产物，攒到最后反而看不出对应关系。批次号在建任务时就定下并存进 `ImportJob`，摘要与条目提案因此落在同一个收件箱里，可以一次「全部采用」
- **模型输出的 `fields` 用键值对数组而不是对象**。提取同时涉及多个分类、字段模板各不相同，写不成固定形状；而 `z.record` 转出的 JSON Schema 带 `additionalProperties`，在 OpenAI 的 strict 模式下会被整体拒绝。落地时模板外的键一律丢弃 —— 它们在条目编辑器里没有对应表单，存进去等于数据不可见
- **本地预筛出本章涉及的条目**（title/aliases 子串匹配，pinned 无条件包含），只把命中的展开成完整字段，其余只给名称用于对齐命名。长篇跑到后期条目数会到几百条，全量注入既贵又稀释注意力
- **分类名对不上的提取条目整条丢弃**。把人物塞进世界观分类会让字段模板完全错位，比少一条更难收拾
- **导入的章节直接记为 `status: 'done'`、`source: 'imported'`**，并接在已有章节之后编号。否则进度看板会把几十万字算成待写
- **一章失败就停下**，不继续往下跑。失败通常源于 Key、余额或网络，继续只会把同一个错误重复几十遍并烧掉 token。失败章节可单独重试，也可以「跳过失败章节，直接整理提案」
- **合并提案的 `sourceChapterIds` 显式补成并集**。溯源字段不在字段规格里（它不该出现在确认界面上），所以 `mergeEntities` 不会带上本次章节，需要在提案构建后补写
- **放弃导入只清进度，不删章节**。已写入的正文是用户资产，确认框里明确说明这一点
- 导入面板打开时，`KnowledgePage` 的页面级待确认区不渲染 —— 与弹层同一个理由：同一批内容出现两个确认入口，视觉上被遮住了但读屏与自动化都能看到两份

**测试**：新增 95 个（分章纯逻辑 42 + 提取逻辑 32 + 端到端 19 + 入口 2）。端到端部分完整走了一遍「粘贴三章 → 自动分章并调整 → 写入章节 → 逐章提取 → 收件箱出现 create/merge 混合提案 → merge 显示字段级 diff 与溯源章节 → 全部采用 → 知识库补全 + 摘要链补齐 + 伏笔按章收束」，并覆盖失败中断、重开续跑、放弃导入三条异常路径。

顺带修掉一个**间歇性的 unhandled rejection**（已存在于 Task 5 的用例中，此前未暴露为失败）：用例只等到「落库」就结束，而采用提案是「写实体 + 标记提案已处理」两步，`afterEach` 关库后第二步变成无人接管的 rejection。两处修正 —— 用例把两步断言放进同一个 `waitFor`；`createTestHarness().cleanup()` 先显式卸载组件树再关库（用例文件的 `afterEach` 比全局 setup 里的 RTL 自动卸载**先**执行）。另外给提取循环加了统一的 `catch`：后台任务必须自己兜住异常。

**验证结果**：typecheck 通过、617 个测试通过，连跑 5 次稳定，生产构建通过。

**Demo**：设「每日一章」，首页显示今日目标与连续天数，写完一章后进度更新。

**实际落地记录**

| 文件                                    | 职责                                                   |
| --------------------------------------- | ------------------------------------------------------ |
| `src/features/plan/planProgress.ts`     | 周期切分、当期进度、连续达成、欠账、最近产出（纯函数） |
| `src/features/plan/recordProgress.ts`   | 当日产出记录的唯一入口                                 |
| `src/features/plan/PlanEditorSheet.tsx` | 计划设定                                               |
| `src/features/plan/PlanPage.tsx`        | 进度看板                                               |
| `ChapterEditorScreen.tsx`（扩展）       | 保存时自动记产出                                       |

**三种模式被统一成「周期」这一个概念**：每日模式的周期是一天，每周模式的周期是一周。看板、连续天数、欠账三处因此只写一遍逻辑，而不是为每周模式开一条平行分支。所有计算都以本地日期字符串（`YYYY-MM-DD`）为输入 —— 用 UTC 时间戳做日界判断，跨时区或夏令时会把连续天数算错，而连续天数是这个页面上唯一有激励作用的数字。

其他关键决定：

- **当前周期未达成不算断档**。把「今天还没写」显示成连续天数归零，只会让人在下午就放弃今天。达成了才计入，没达成就维持昨天的数字
- **非生效日既不打断连续，也不产生欠账**。设了「周一到周五」的人，周末不写不该被判违约
- **欠账只回看最近 30 个周期**（`DEBT_LOOKBACK_PERIODS`）。更早的欠账追不回来，而一个永远在变大的负债数字只会让人关掉这个页面，而不是多写一章
- **每周模式忽略生效星期**。「每周三章」不在乎哪天写，再叠一层生效日限制会让规则变得没人能解释清楚。开始那一周的周期起点裁剪到开始日，否则开局就凭空多出几天欠账
- **换模式时目标值重置为该模式的默认值**，不做跨量纲换算 —— 1 章不等于 1 字，把「1」直接搬到字数栏比重置更让人困惑
- **只记录正向增量**（`recordProgress` 里 clamp）。`DailyLog.words` 是非负累计值，把删字算成负数的话一次大改就能抹平当天记录甚至写入非法值。删掉的字不是没写过，只是被改掉了
- **完成计数在编辑器的一次挂载周期内只记一次**，避免反复切换「草稿／已完成」刷进度
- **产出记录挂在自动保存上**，不设单独按钮。写作计划要有意义就必须自动统计，指望用户每天手动汇报等于这个功能不存在。导入旧稿走的是 `createChapter`，不记产出 —— 几十万字存量稿不该算成今天写的
- 进度条用 `role="progressbar"` + `aria-valuetext`，迷你柱状图的柱子 `aria-hidden`、数值走 `sr-only` 文本，读屏能拿到「昨天：2500 字」这种可读信息而不是一排无意义的 div

**测试**：新增 60 个（纯逻辑 38 + 看板与设定 18 + 自动记产出 4）。纯逻辑部分覆盖了周界、生效日过滤、开始日裁剪、生效星期为空时不死循环、欠账回看上限。

**验证结果**：typecheck 通过、677 个测试通过，连跑 5 次稳定，生产构建通过。

**备份文件用 Zod 逐表校验，不是宽松的 `Record<string, unknown[]>`。** 备份是外部输入：用户会手动编辑、跨版本导入、拿错文件。一个宽松的 schema 等于把损坏的数据直接灌进库里，而这时候「导入失败」远好于「导入了一半」。导入整份走一个 Dexie 事务，中途失败不留半套数据。

其他关键决定：

- **快照 schema 本身就不收集设置**，所以 API Key 在结构上进不去备份文件。测试里额外对成品文件文本做了一次 `不含 apiKey / sk-` 的断言 —— 这条规则值得有一道机械防线，因为备份文件会被丢进网盘、发给自己、传到聊天软件里
- **导出包含软删除的条目**。不带走回收站的话，恢复后用户会发现「我删掉但还想找回来的东西」凭空消失了
- **两种恢复语义都提供**：`replace` 用于换设备或清过数据后恢复，`merge` 用于把另一台设备的作品并过来（id 相同以备份为准）。`replace` 走破坏性确认框，文案里明确提示「现有数据还没备份就先导出一份」
- **复制到剪贴板与下载文件并列，不分主次**。移动端浏览器对下载的处理差异很大（iOS 会跳界面、部分内嵌浏览器直接吞掉），而「贴进平台编辑器」本来就是最常见的去向
- **`saveTextFile` 在 `createObjectURL` 失败时退回 data URL**。部分内嵌浏览器禁用 blob URL，宁可多占一点内存也不要让导出整个失效（顺带让这条路径在 jsdom 里可测）
- **导出跳过空章节**，否则目录里会凭空多出几个只有标题的条目
- **备份提醒放在书架而不是设置页**：需要提醒的恰恰是不会主动翻设置的人。攒够 3000 字才提，可以「以后再说」安静一周 —— 反复弹同一条横幅比不提醒更容易被永久忽略
- 顺带修掉一个**导入旧稿后的真实断路**：`WritingPage` 原先只看大纲是否为空，导入的作品有几十万字章节却没有大纲，于是章节列表被整个藏起来，用户在「写作」页找不到自己刚导进来的稿子。改为「大纲与章节都为空」才算空，并在无大纲时把大纲区降级成一个「添加第一个大纲节点」的入口

**测试**：新增 62 个（正文格式化 15 + 备份往返与提醒判定 18 + 导出面板 12 + 备份区 9 + 书架横幅 4 + 写作页入口与无大纲旧稿 4）。往返一致性用「导出 → 换一个空库 → 导入 → 逐字段比对快照」验证，这正是「清空浏览器数据后恢复」的真实路径。

`SettingsPage.test.tsx` 因为备份区要用仓储，从裸 `render` 改为走测试 harness 的 Provider。

**验证结果**：typecheck 通过、739 个测试通过，连跑 5 次稳定，生产构建通过（gzip JS 213kB）。

**Node 版本**：当前环境为 v22.18.0，而 `jsdom@30.1.0` 声明需要 `^22.22.2 || ^24.15.0 || >=26.0.0`，`undici@8.10.2` 需要 `>=22.19.0`，安装时产生 EBADENGINE 警告。实测测试套件可正常运行，暂不处理；若后续出现 jsdom 相关的诡异失败，优先升级 Node 到 22.22+ 而非降级 jsdom。

**TypeScript 7 差异**：`baseUrl` 已被移除，`paths` 必须写相对路径（`"@/*": ["./src/*"]`）。CSS 侧效导入需要在 `types` 中引入 `vite/client`。

**npm 安装耗时**：默认 registry 的元数据请求约 3 秒/包，首次完整安装需要数分钟。若过慢可临时加 `--registry=https://registry.npmmirror.com`（仅命令级，不改全局配置）。

**实现要点**

**实际落地记录**

| 文件                   | 职责                                                        |
| ---------------------- | ----------------------------------------------------------- |
| `src/app/AppNav.tsx`   | 自适应主导航（取代 `BottomTabBar.tsx`）                     |
| `src/app/AppShell.tsx` | 两列外壳 + 跳到主内容                                       |
| `src/ui/Page.tsx`      | 限宽内容列（新增 `width` prop）+ 新增 `SectionGrid`         |
| `src/ui/Sheet.tsx`     | 新增 `size: 'drawer' \| 'dialog'`；Esc 的输入法守卫         |

| `src/index.css`        | 侧边栏宽度、`reading-column`、`skip-link`、焦点环、细滚动条 |

**只做 CSS 断点，不做 JS 媒体查询分叉。** 按屏幕宽度渲染两套组件有三个代价：同一份内容出现两棵 DOM，读屏会读到两遍；`display:none` 在测试环境里不生效，一个 Tab 会被查询到两个链接；两条分支必然随时间漂移。因此整套桌面形态是同一组元素换布局类 —— 底部 Tab 栏和左侧边栏是同一个 `<nav>`、同一批 `NavLink`。

其他关键决定：

- **断点分两档**。`md`（768px）起把列表变多列、抽屉变对话框；`lg`（1024px）起才换成侧边栏外壳。平板横屏用得上中间那一档
- **正文列限宽 46rem**（约 40 个汉字一行）。桌面端最容易犯的错是让正文铺满 1920px，一行八十多个汉字，眼睛回到行首时会丢行。编辑器的头部与底部操作区也收进同一列宽，否则返回按钮在最左边、正文在正中间，视线要横跨整个屏幕
- **确认框在桌面端是居中小窗，不是右侧抽屉**。把一句确认文案拉成一条 1080px 高的竖条荒谬且难读，所以 `Sheet` 给了 `size` 而不是一套样式通吃
- **导航 DOM 顺序留在内容之后，靠 `lg:order-first` 移到左侧**。这样移动端读屏的阅读顺序仍是「内容 → 导航」（与 iOS/Android 的 Tab 栏惯例一致）；桌面端键盘到侧边栏偏后，由「跳到主内容」链接补偿
- **hover 用 `enabled:hover:` 而不是裸 `hover:`**。`:hover` 与 `:disabled` 特异性相同，谁生效取决于生成样式表的先后顺序 —— 那是不该依赖的实现细节
- **`cursor-pointer` 必须显式加**。浏览器给 `<button>` 的默认光标是 `default`，桌面端不加就是「看着能点但手感不对」
- **输入框的 `font-size: max(16px, 1rem)` 在指针设备上取消**。那条规则是为了躲开 iOS 的自动放大，在桌面上只会让表单显得笨重
- **`:focus-visible` 全局焦点环**。移动端全靠触控、焦点环基本看不到；桌面端相反，没有焦点环，键盘用户在几十个控件之间完全不知道自己在哪
- **只加一个快捷键：Cmd/Ctrl+S**。内容本来就在自动保存，它的价值不在保住数据，而在于不拦住的话浏览器会弹出「保存网页」对话框 —— 那才是真的打断

**修掉一个真实缺陷：Esc 与中文输入法冲突。** 中文输入法把 Esc 当作「取消当前候选词」，写作场景下这个键会被频繁按到。原先 `Sheet` 无条件在 Esc 时关闭，用户一次误触就会丢掉整段还没提交的输入 —— 而他本来只是想撤掉一个选错的词。现在加了 `event.isComposing` 守卫。同一个原因，章节编辑器**刻意不绑 Esc 返回**：绑上就等于写中文时随机退出编辑器。

**测试**：新增 22 个（`Sheet` 14 + 自适应外壳 3 + 桌面端键盘 5）。刻意不断言 Tailwind 类名 —— 那种测试脆弱且不说明任何行为。改为验证真实行为（Esc 的组字守卫、快捷键拦截与解绑、导航只有一份、跳转目标真实存在），CSS 的正确性用构建产物核对：`@media (width>=64rem)`、`.lg\:w-[var(--spacing-sidebar)]`、`.skip-link:focus`、`.reading-column`、`:focus-visible`、`enabled:hover` 复合选择器、`@media (hover:hover)` 与 `(pointer:fine)` 均已正确编译。

**验证结果**：typecheck 通过、761 个测试通过，连跑 5 次稳定，生产构建通过（CSS 从 gzip 5.7kB 增至 6.75kB，JS 基本不变）。

## Task 16: 稿件文件上传与导入入口前置

- [x] 完成

**目标**：存量作者能直接上传稿件文件建库续写，而不是只能粘贴、且入口埋在角落。

**背景**：Task 12 做完了反向提取，但留了两个实际上堵死这条路的缺口 —— 只能粘贴（几十万字在手机上根本粘不进去），入口只在「知识库 → 管理」（必须先手动建作品，而建作品的表单问的是「我想讲一个什么故事」，对存量作者是错的问题）。

**实现要点**

- 上传 `.txt` / `.md`，桌面端支持拖拽
- 自动识别 UTF-8 / GB18030 / UTF-16 编码
- 多文件按选择顺序依次追加
- 书架新建作品提供「导入已有稿件」路径，建完直接落在导入面板

**测试要求**

- 编码探测（含手写 GB18030 字节）
- 上传后能走到分章
- 从书架一路到导入面板的真实路由链路

**Demo**：书架 →「导入已有稿件」→ 填书名 → 拖入一个 GBK 编码的 txt → 分章 → 提取 → 续写。

**实际落地记录**

| 文件                                    | 职责                                   |
| --------------------------------------- | -------------------------------------- |
| `src/features/import/readManuscript.ts` | 编码探测、文件体检、换行与 BOM 归一    |
| `ImportScreen.tsx`（扩展）              | 上传区、拖拽、已读入文件列表、编码提示 |
| `ShelfPage.tsx`（扩展）                 | 新建作品的两条路 + 跳转意图            |
| `KnowledgePage.tsx`（扩展）             | 消费跳转意图自动打开导入面板           |

**不能直接用 `FileReader.readAsText`。** 它默认按 UTF-8 解码，而中文作者手里的 `.txt` 有相当比例是 **GB18030**（Windows 记事本的「ANSI」就是它）。按 UTF-8 读一个 GBK 文件的结果是整篇乱码 —— 而且是「看起来成功了」的那种失败，用户会以为是应用坏了。所以读字节后自己做探测：

1. 有 BOM 就信 BOM（UTF-8 / UTF-16 LE / BE），这是唯一确定的信号
2. 用 `0x00` 的分布嗅出 BOM-less 的 UTF-16 —— UTF-8 与 GB18030 都不会产生 `0x00`
3. 用 **严格模式**（`fatal: true`）试 UTF-8。GB18030 的双字节序列几乎不可能同时是合法 UTF-8，所以「严格 UTF-8 解不通」就是「这是 GBK 系」的强证据
4. 最后退到 GB18030（GBK 的超集，能覆盖生僻字）

识别结果显示给用户；少量坏字节只标注不拒绝 —— 几十万字里错几个字，用户自己改比被拒之门外好得多，但必须说清楚，否则他会以为是自己当年写错了。

其他关键决定：

- **多文件按选择顺序追加，不按文件名排序**。一章一个文件的作者不少，但中文文件名的字典序会把「第十章」排到「第二章」前面。悄悄打乱一本书比让用户按顺序点几下糟糕得多，所以顺序由他掌握，并把已读入的文件按序列出来
- **扩展名校验必须在代码里也做一遍**。`accept` 属性只是文件选择器的过滤器，用户在系统对话框里选「所有文件」就绕过了，拖拽更是完全不经过它。`.docx` / `.pdf` 给的是「请在原软件里另存为纯文本」这种能照着做的提示，而不是「格式不支持」
- **导入模式下不问「我想讲一个什么故事」**。存量作者手里有几十万字却还没有那句话，它应当由稿件反推出来 —— 逼他在这里现编一个，等于让整个知识库从一句假话长出来
- **跳转意图只消费一次**。路由 state 会一直挂在那条历史记录上，不清掉的话用户关了导入面板、页内来回一次就会再自动弹开一遍

**测试**：新增 39 个（编码探测纯逻辑 20 + 上传交互 10 + 从书架到导入面板的端到端 9）。GB18030 用手写码位造字节（Node 没有内置 GBK 编码器）。端到端那组走真实路由跑 `AppShell`，因为「建作品 → 跳转 → 自动打开」这三段分别在三个文件里，只有串起来才说明它真的通。

测试过程发现并修掉两个问题：`sniffUtf16` 对空文件会误判成 UTF-16（`0 * 4 < 0` 为假，比例判断退化），已加长度与零值守卫；另外我原以为 `0x80` 在 GB18030 里非法，实际它是欧元符号，测试数据改用真正非法的 `0xFF`。也记下一条工具事实：`userEvent.upload` 默认遵守 `accept`，`applyAccept` 是 setup 级选项、不能按次传。

**验证结果**：typecheck 通过、800 个测试通过，连跑 4 次稳定，生产构建通过。

## Task 17: 外文稿件翻译与中英混排字数修正

- [x] 完成

**目标**：手里有几章外文稿的人，能译成中文后接着用中文写。

**背景**：用户问「原文是英文，可以翻译成中文吗」。实测后发现两件事 —— 分章本来就认 `Chapter N`，反向提取也会顺带产出中文条目（因为指令是中文写的）；但**没有翻译能力**，而且 `countWords` 对英文按字符数算，`He shouldered the pack before dawn.` 六个词被算成 30 字，让写作计划失真约五倍。

**实现要点**

- 修正字数统计：东方文字按字符、拉丁文字按词
- 按章判定语种，「部分章节是外文」自动识别
- 逐章翻译，保留原文，跨章译名一致
- 翻译步骤插在导入流程的**提取之前**，且只在检测到外语时出现

**测试要求**

- 纯中文文本的字数与修正前完全一致
- 译名跨章沿用
- 原文可还原

**Demo**：导入两章英文 + 一章中文 → 只有那两章被勾上翻译 → 译完后正文是中文、原文留底 → 提取出的知识库是中文 → 接着写第四章。

**实际落地记录**

| 文件                                      | 职责                                          |
| ----------------------------------------- | --------------------------------------------- |
| `src/domain/primitives.ts`                | `countWords` 修正 + `isCjkCodePoint`          |
| `src/domain/language.ts`                  | 按章语种判定                                  |
| `src/features/writing/translate.ts`       | 翻译提示词、译文/译名表解析、译名合并         |
| `src/features/writing/TranslateSheet.tsx` | 单章翻译                                      |
| `ImportScreen.tsx`（扩展）                | 翻译步骤与逐章循环                            |
| `schema.ts` / `db.ts`（v3）               | `Chapter.sourceContent`、`ImportJob.glossary` |

**字数修正不需要迁移，因为纯中文的结果没有变。** 新算法是「CJK 字符逐个计一个字 + 连续的非 CJK 非空白算一个词」。对纯中文文本，它与旧的「去空白后数字符」**逐字节等价**（全角标点计入、全角空格属于 `\s` 被跳过）—— 测试里直接拿旧算法做对照断言，证明既有作品的字数不会因为这次修正而变动。只有含英文的文本数字会变小，而那正是修正的目的。

**译文不包进 JSON、不走 Proposal 管道。** 一章译文动辄三千字，包进 JSON 字符串有两个坏处：转义出错会让整章白译（输出 token 是最贵的部分，重试一次就是再付一遍钱），而且没法边译边看。所以译文走流式纯文本，译名表附在后面用 `---译名表---` 分隔、在本地解析 —— **关键是译名表解析失败不影响译文**：拿不到译名表只是下一章少一点约束，拿不到译文才是真的损失。没有分隔行时整段都算译文。

其他关键决定：

- **译名先到先得**。人名跑风是文学翻译最刺眼的毛病：Ashford 在第一章是「阿什福德」，到第五章变成「艾许佛」，读者会以为是两个人。所以前面章节定下的译名不允许被后面推翻 —— 一致比「这次译得更好」重要。想改就去正文里改，那是作者的决定
- **只注入本章出现过的译名**。跑到后期译名表会有几百条，全量注入既贵又稀释注意力
- **翻译步骤不自动开始**。提取可以自动跑（输入为主、单章几分钱），翻译是整个流程里唯一一次大规模输出，必须让用户先看清要译哪几章、能取消勾选，再自己按下开始
- **按章判定语种，不给整本书取一个**。导入的稿子常常部分章节外文、部分中文，整本取一个会让该翻的漏掉、不该翻的被重译
- **语种判定只认字母、不认标点**（与字数统计用的 `isCjkCodePoint` 刻意不同）。把「。，！」算进中文占比，会让一段中文标点夹着的英文被误判成中文
- **原文存进 `Chapter.sourceContent`**。翻译不可逆，而机器译文一定有需要回头核对原句的地方。单章翻译还会把原文压入编辑器的撤销栈，一键退回外文原稿
- **翻译带上作品的风格档案，但忠实优先**。译文要和后续的中文续写读起来像同一本书，否则读者会在第四章的位置感到换了个作者；提示词里同时写明「风格只影响措辞与语感，冲突时一律以忠实于原文为准」
- **`translate-chapter` 关思维链、温度 0.7、用强模型**。推理模式会让译文带解释性赘语、句子之间的气也断掉；温度比正文（0.95）低、比提取（0.2）高 —— 再低就成了逐词硬译的生硬中文

**Dexie v3**：`sourceContent` / `sourceLanguage` 都不建索引，本不需要改 `stores`。仍然升一个版本是因为旧行里这两个字段是 `undefined`，而读取路径为了性能不做 Zod parse，界面上 `chapter.sourceContent.trim()` 会直接抛错。用一次迁移把旧行补齐，比在几十个读取点各写一个 `?? ''` 可靠。

## 已修缺陷记录：译名表放错了层

**症状**：分几次导入多份外文素材时，第二批的人名可能换个译法 —— 第一批的 Ashford 是「阿什福德」，第二批变成「艾许佛」。

**原因**：译名表当初存在 `ImportJob.glossary` 里，而 `finalize()` 收尾时会 `deleteImportJob` —— 译名表跟着任务一起被删。第二批导入的新任务从**空表**开始。
单章翻译（`TranslateSheet`）意识到了这个问题，退一步从知识库条目的拉丁别名反推译名，但那条路不可靠：提取提示词对 `aliases` 的要求是「填其他称呼、绰号、尊称」，**从来没要求把原文名写进去**。批量翻译连这条退路都没有。

**根因不是忘了持久化，是层放错了。** 任务是临时的（只为断点续跑而存在），而「Ashford 译作阿什福德」是这部作品的永久事实。把永久事实存在临时容器里，删容器时必然一起丢。

**修法**：

1. 新增作品级 `Glossary` 表（Dexie v4，`&novelId` 一书一份，与 `plans` / `styleProfiles` 同构），并**删掉 `ImportJob.glossary`** —— 留着就是两个事实源，那正是在修的那类 bug
2. 合并规则从 `features/writing/translate.ts` 下沉到 `src/domain/glossary.ts`。仓储层要用它，而数据层依赖 feature 是反向依赖
3. 两套语义分开：模型产出走 `mergeGlossaryTerms`（**先到先得**），用户修改走 `setGlossaryTerm`（**覆盖**）。都在仓储的同一条写入路径上执行，三处调用方不会写漏
4. 批量翻译、单章翻译、译名表界面共用同一份；译名表进备份快照与级联删除
5. 新增「知识库 → 管理 → 译名表」：可改、可删、可在翻译前预先定好关键人名

**顺带修掉的两处**：

- 提取提示词补一条：正文是译文时把**外文原名也放进 `aliases`**。这让条目自带溯源，也让后续外文素材的本地预筛（按 title ∪ aliases 子串匹配）认得出是同一个对象，不会新建重复条目
- `ChapterEditorScreen` 的「重译」入口原先读 `chapter.sourceContent`（父级查询的快照），采用译文后要等上游刷新才出现。改为本地 state 立即生效；并且撤销那次翻译时把 `sourceContent` 一并清空 —— 否则这一章会同时是「正文为原文」和「译过一次」，挂着一个什么都没译过的「重译」按钮

**文档同步修正**：`使用说明.md` 原先写「想改某个译名，去正文里直接改」。译名表持久化之后这句话是错的 —— 改正文不会改译名表，后面的章节照旧用回原译法。

**验证**：新增 4 条跨批次断言（第一批的译名在任务删除后仍在、第二批的 prompt 带上第一批的译名、用户改过的译名盖住模型后来的产出、翻译前预设的译名第一章就生效）。924 个测试，连跑 4 次稳定。

**留给后来人的规矩**：往「任务」「会话」「草稿」这类临时容器里写数据前，先问一句它的生命周期是不是真的和容器一致。跨越容器生命周期的事实，必须挂在它真正的主人身上。

## 已修缺陷记录：默认预选形同虚设

**症状**：「生成本章正文」里的「参与写作的设定」几乎总是一条都没勾上，每次生成都得从几十条
条目里自己挑一遍。

**原因不是没实现。** `computeDefaultEntryIds` 一直在，语义是
「大纲节点的 `linkedEntryIds` ∪ 上一章摘要的 `appearingEntryIds`」，设计方案里也写着。
问题是**这两个来源在最常见的路径上都是空的**：

1. **立项生成的大纲节点永远不带关联**。大纲走 `outlineTree` 提案，payload 只有一段缩进标题
   文本，`createOutlineTree` 落库时只写 `title` / `synopsis` / `targetWords` / `parentId` / `order`。
   `OutlinePayload` 虽然支持 `linkedEntryIds`，但那条路只有**逐节点**提案才会走 ——
   AI 生成整棵树时根本不经过它。于是除非作者事后在大纲抽屉里手动逐个关联，它永远是 `[]`。
2. **第一章没有上一章**，第二个来源也空。
3. **导入的旧稿没有大纲**（这是刻意的），而且早期章节摘要的 `appearingEntryIds` 也基本是空的
   —— 提取那一刻新条目还没落库，`resolveEntryNames` 只能解析已在库里的名字。

三条叠起来，绝大多数用户看到的预选就是零。**功能在，数据不在。**

**修法**：给预选补两个**推断**来源，用本地名称匹配，不花钱、不调模型 ——

| 档   | 来源                                              | 上限                       |
| ---- | ------------------------------------------------- | -------------------------- |
| 显式 | 节点 `linkedEntryIds`、上一章 `appearingEntryIds` | 无                         |
| 推断 | 节点的标题与梗概、上一章摘要的正文与关键事件      | `MAX_INFERRED_ENTRIES = 8` |

梗概写着「沈砚在渡口遇见裴照」，这两个人显然该进上下文 —— 这个信息一直就在库里，
只是没人去读。

**显式排在推断之前**：装箱顺序即优先级，预算紧张时该先丢掉猜出来的那些。
**推断必须设上限**：一个用常见词做别名的条目（别名「师父」「他」）会命中大量文本，
不设上限会把几十条无关设定拉进 prompt，那正是装箱要避免的事。显式来源不受限 ——
作者亲手关联了十五条，就该给他十五条。

**匹配逻辑下沉到 `src/domain/entrySearch.ts` 的 `mentionedEntries`**。原先这套子串匹配
只存在于 `features/import/extractSettings.ts` 的 `findMentionedEntries` 里，而上下文构建器
要用同一套规则 —— 各写一份的话，同一段文字在不同入口匹配出不同结果，这种不一致极难察觉。
下沉时刻意**不带 `pinned` 特例**：核心设定要不要无条件包含是调用方的策略而非匹配规则，
提取时要（读不到会让模型自行发明设定），默认预选时不要（它们本来就始终注入）。
`findMentionedEntries` 改为复用它再叠加 pinned。

**界面上说清预选是怎么来的**：设定勾选区上方一行小字，未手动改过时显示
「已按大纲梗概与上一章摘要自动勾上相关条目，点标签可以增减」，改过之后变成「已手动调整过」。
不说的话用户无法判断「这几条是谁选的、可不可信」。

**猜不出来就老实空着。** 没有大纲也没有摘要时预选仍然是空的 ——
塞一堆无关设定比让用户自己勾更糟。

**验证**：新增 12 条（梗概命中、标题命中、摘要正文命中、关键事件命中、别名命中、
核心设定不进预选、显式排在推断之前、显式与推断去重、推断有上限而显式无上限、
无线索时不瞎猜、已删除条目不被勾上、预选条目真的进了稳定前缀）。1004 个测试。

## 增量：导入可以连着来第二轮

「把整本书一次性交出来」是产品经理的想象。真实情况是一章一个文件、正文与番外分开存、

| 已落库的提案             | 上一批没处理完的待确认项不属于「本轮状态」，它们会留在知识库页的待确认区 |

## 增量：译名一致性检查

上一节把译名表挪到了作品上，跨批次的**新**翻译从此一致。但那只管得住「接下来要译的」——
作者把 Ashford 从「阿什福德」改成「艾许佛」之后，已经译好的章节仍是旧译法，而且**没有任何地方提示**。
不一致静默地留在正文里，这才是最难发现的那种问题。

**做法：只提示，不替换。**

| 文件                                       | 改动                                                                                       |
| ------------------------------------------ | ------------------------------------------------------------------------------------------ |
| `src/domain/glossary.ts`                   | 新增 `findGlossaryDrift(terms, chapters)` 与 `GlossaryDrift` / `GlossaryCheckChapter` 类型 |
| `src/features/writing/GlossarySheet.tsx`   | 顶部不一致报告 + 行内标记 + `onOpenChapter` 回调                                           |
| `src/features/knowledge/KnowledgePage.tsx` | 接线：关抽屉 → `navigate('/write', { state: { openChapterId } })`                          |
| `src/features/writing/WritingPage.tsx`     | 消费 `openChapterId` 意图（只消费一次），直接打开那一章的编辑器                            |

**判据是原文与译文对照，不是译名的历史版本。** 某一章的原文里出现过 `Ashford`（忽略大小写）、
而译文里找不到当前登记的「艾许佛」，这一章就没跟上。之所以能这么判，是因为翻译时原文整份留在了
`Chapter.sourceContent` 里。

这个选择比「记录每条译名的旧版本」好三点：不用加字段、不用迁移；作者直接手写一条译名（从来没有旧版本）
也一样能查；而且顺带能发现模型当初压根没照译名表译的情况 —— 那是历史版本方案查不出来的。

三条刻意的边界：

- **只看翻译过的章节**（`sourceContent` 非空）。中文原创章节没有留底原文，里面的「阿什福德」
  无从判定是不是同一个对象，猜一个只会制造假警报
- **译文里命中一次就算通过**。长章节里代词、简称、单名满地都是，要求处处写全名的话几乎每章都会被标红
- **只提示，不改字**。同一个词会出现在对话、称谓、复合地名里，机械替换会出事。所以给的是
  「哪几章 + 一点就跳过去」，而不是「全部替换」按钮。批量替换是破坏性操作，要做就得配二次确认与撤销栈，
  收益远不如把判断权留给作者

**不一致报告放在抽屉顶部，不是只在行内标记。** 跑到后期译名表会有几百行，指望用户滚着找哪几行
被标了是不现实的。行内那句「译文不一致」只是定位用的记号，真正可操作的清单在顶部。

**比对用已保存的译名，不用输入框里的草稿。** 正在改的那一版还没写进库、更没影响过任何正文，
拿它去比对只会在打字过程中疯狂闪烁。

**跨页跳转沿用导入入口那套「意图只消费一次」。** 译名表在知识库、章节正文在写作页，
跳转靠路由 state 传 `openChapterId`；写作页读到后立刻 `navigate(pathname, { replace: true })` 清掉 ——
不清的话用户关了编辑器、在页内点点再回来，它会再次自动弹开。

**验证**：`glossary.test.ts` 新增 10 条（含「中文原创章节不参与」「命中一次即通过」「残缺条目不参与」），
`GlossarySheet.test.tsx` 新增 8 条，新建 `glossaryJump.test.tsx` 3 条端到端（走真实路由：
译名表算出不一致 → 点章节 → 写作页打开那一章 → 意图不重复触发）。

## 已修缺陷记录：非安全上下文

**症状**：用平板 / 手机通过局域网 IP（`http://172.16.x.x:5173`）打开，新建作品时报
`crypto.randomUUID is not a function`，一本书都建不出来。

**原因**：`crypto.randomUUID()` 是**安全上下文专有 API**，只在 HTTPS 与 `localhost` 下存在。
局域网 IP 走纯 HTTP，属于非安全上下文，该方法是 `undefined`。而 `newId()` 是所有实体 id
的唯一来源 —— 它一挂，整个应用连一条数据都写不进去。在开发机上用 `localhost` 测永远碰不到。

**修法**：`newId()` 按可用性降级 ——
`crypto.randomUUID()` → `crypto.getRandomValues()` 自己拼 UUID v4（**不受安全上下文限制**，
这是局域网访问时真正生效的那条）→ 时间戳 + `Math.random()` 兜底。
测试用 `vi.stubGlobal` 把三种环境各跑一遍，并断言输出符合 UUID v4 的版本位与变体位。

**同类排查**：全仓扫了一遍安全上下文专有 API，只有另外一处 ——
`navigator.clipboard`（导出正文的「复制」）。它本来就有 `?.` 守卫与 `execCommand` 兜底，
顺手给兜底路径补上了 iOS Safari 需要的 `contentEditable` 与 `setSelectionRange`。
其余用到的 API（IndexedDB、fetch、localStorage、Blob / `createObjectURL`、FileReader、
`TextDecoder('gb18030')`）都不受安全上下文限制。

**留给后来人的规矩**：新增浏览器 API 前先确认它是不是 secure-context only（看 MDN 条目上
有没有「Secure context」标记）。只在 `localhost` 上验证，这类问题会一路带到真机才暴露。

**识别范围就是「哪些属性能从文本观察出来」。** rubric 七维 + 文体取向 + 子类。刻意排除两项：

- **创作方法论**。它是「接下来怎么规划大纲」的选择，不是既有文本的属性。从正文反推作者当年用的
  是雪花法还是三幕式是伪精确，而这个字段直接决定后续大纲结构 —— 猜错的代价不对称。
- **名家风格参考**。那是「我想像谁」而不是「我像谁」。让模型判定「接近某位作家 60%」既容易错，
  也不该由机器替作者宣称这种关联。技术上它还是数组套对象，`getFieldValue` 会把它 `String()` 成
  `[object Object]`，本来就无法走字段级 diff。

**归纳排在收尾，不单开一个步骤。** 三条理由：取样必须在翻译**之后**（否则归纳出的是英文的句式
节奏）；反向提取刻意不带文风，所以风格落在它后面对提取没有任何影响；共用同一个 `batchId`，
用户在一个收件箱里连着确认，流程上一道关卡都不多。**附带调用独立 try/catch** —— 十几分钟提取
的成果不能因为一次可选的风格调用出错就丢掉，失败只写一行说明。

**开关放在分章步骤**，那是钱花出去之前最后一个能改的地方；写入 job 之后界面不再提供开关
（跑到一半改它没有意义）。`withStyle` 不建索引，因此不需要升 Dexie 版本，读取侧用 `!== false`
语义兼容旧行 —— 与既有的 `withSummaries` 一致。

**取样是纯函数且完全确定性**：跳过过短的章 → 章数多于所需时让出开篇 → 等距取最多 3 章 →
每章取中段并对齐句子边界 → 总长卡 4000 字。不用随机数，否则 prompt 缓存失效、测试也不可重复。
截断刻意对齐句末标点：半句开头会被模型当成作者的断句习惯，污染「句式节奏」那一维。

**子类要本地归一化。** 模型会回「现代都市」「悬疑推理」这类组合词，也可能回一个该取向下根本不存在
的子类（严肃文学下没有任何子类）。`normalizeSubGenre` 按 id / label 精确匹配、再按包含匹配，
匹配不上就留空 —— 一个找不到约定的子类进了 prompt 只会白占字段。

**枚举字段是确认管道本来缺的一块。** 文体取向只有三个合法值，用文本框会让用户填出
`TraditionSchema.parse` 拒绝的值，而且要到点「采用」时才报错。加了 `'enum'` 之后展示 label、
存机器值，`options` 从 `TRADITIONS` 派生而不是抄一份（抄的那份一定会漂移）。扩展
`STYLE_PROFILE_FIELD_SPECS` 对既有的手动取样无影响：那条提案的 payload 里没有这两个键，
`computeDiff` 对两边都空的字段直接跳过，`ProposalReview` 的 `!value && !diff` 也不会渲染，
`applyEdits` 只写用户真正编辑过的路径。

**自查出的一个真实缺陷**：「让出开篇」原先写成对**过滤后**的列表 `slice(1)`。当稿件里只有两章
够长时，这会把一半样本扔掉 —— 比拿楔子去归纳的损失大得多。改成只在章数多于所需（>3）时才让出。
测试里那条断言先失败，才暴露了这个顺序问题。

**验证**：`extractStyle.test.ts` 28 条（取样规则 12、子类归一化 5、schema 3、payload 2、提示词 5、
确定性 1），`ImportScreen.test.tsx` 新增「从旧稿归纳文风」10 条端到端（同批提案、payload 归一化、
不碰方法论与名家参考、第 4 次调用用的是文风提示词、确认后三类字段一起落库、枚举渲染成下拉且
显示中文、可在收件箱把判错的文体改回去、取消勾选一次调用也不多花、归纳失败不影响条目提案并说明
原因、稿件太短跳过）。983 个测试 / 48 个文件。

**草稿存在任务上，不另开表。** 选定目的地之前一章 `Chapter` 都不写，分章结果和译文放在 `ImportJob.drafts`。

## Task 18: 写作规范与按规范检查

- [x] 完成

**目标**：作者把自己的创作约束（同人差异说明、信息分层、命名与合并规则等）作为作品级「写作规范」放进各任务的提示词，并能在写完一章后用 AI 按规范逐条检查。

**实现要点**

- 每部作品 0 到多份规范：标题 + 正文 + 启用开关 + 作用范围（写正文 / 规划 / 章节摘要 / 提取设定 / 检查）+ 排序
- 原文直接保存（作者自己的文字，不走提案管道）；支持粘贴、`.txt` / `.md` 上传、差异说明模板
- 按作用范围注入对应任务的系统提示**稳定前缀**；生成前在注入清单里可见、可临时取消
- AI 精简：可编辑预览 → 另存为新规范、原文自动停用（原文不覆盖）
- 按规范检查本章：长章分段、逐条结果、会话内展示不落库
- 备份含规范；旧备份照常恢复

**测试要求**

- 没有启用规范时，所有提示词与之前**逐字节相同**
- 各作用范围边界、精简与检查的端到端

**Demo**：粘贴一份同人差异说明 → 整章生成的注入清单里看到它 → 写完用「按规范检查」逐条核对、定位到原句。

关键实现决定：

- **「没有启用规范时，所有提示词与之前逐字节相同」是硬约束，有专门基线**：`noNormsBaseline.test.ts` 用字面量常量 + `toBe` / `toEqual`（禁止快照），夹具写成对象字面量、只 `import type`，同一文件能拷回旧代码交叉验证；`noNormsInputs.test.ts` 再用 `?raw` 读两份源码做「夹具同步」用例，防两份夹具各自漂移
- **规范进稳定前缀，排在核心设定之前**。前缀里越靠前的内容越该是最不易变的：规范写好后很少改，核心设定却会随知识库确认增减；顺序反过来，每确认一条核心设定，规范那几千 token 就跟着失去缓存
- **规范不参与预算裁剪**。作者显式定下的约束被预算悄悄挤掉等于约束失效；想省就临时取消或在知识库停用
- **作者原文直接保存、AI 精简另存**（5.1）：精简是「另存为新规范 + 原文自动停用」的一次写入，原文正文不变；有未保存修改时禁止精简，避免精简一份库里不存在的内容
- **检查是会话内提示，不是数据**：结果只在面板内存里，正文改动后提示可能过期；不落库、不自动改。「按建议改写」只是选中原文、打开段落加工并预填建议，照常走可编辑预览
- **长章分段检查**：超 8000 字符按行边界切段，先展示分段数与预估 token 再请求；任一段截断或失败整次报错并说明第几段 —— 部分结果看上去就像「其余段落没问题」
- **翻译不带规范**：翻译的第一原则是忠实原文，带规范会诱导模型「修正」原文；译名一致性由作品级译名表负责
- 规范与世界观条目、文风档案的分工：条目回答「世界能发生什么」，规范回答「这本书选择发生什么、现在进行到哪里、按什么规矩写」，文风管句式与语感

**提取器覆盖中文 RTF 的两种并存写法**：

- 老式：汉字按文件代码页（`\ansicpg`，中文几乎都是 936=GBK）编成字节，以 `\'hh` 十六进制转义内联在文本里 —— 攒成字节流后按声明的代码页解码（936→GB18030、950→Big5、65001→UTF-8，缺省按规范 1252）；
- 新式：`\uN` 码位转义（负数表示 65536+N），后跟一个给老阅读器的 fallback 字符（个数由 `\ucN` 定，缺省 1），提取时跳过；相邻两个 `\u` 拼出代理对。

其余约定：`\par` / `\line` 是换行、`\tab` 是制表符、`\\` `\{` `\}` 还原转义、文件里的真实 CR/LF 只是排版空白；fonttbl / colortbl / stylesheet / pict / 页眉页脚 / field 等目的地**整组跳过**（pict 里的二进制十六进制不能漏进正文）；`\emdash`、`\lquote` 等符号映射成中文标点；`\'` 后不是两位十六进制时不吞字（引号按普通文字保留）；解码出 U+FFFD 标记 lossy，与纯文本读取同义。

**按内容而不是按扩展名识别**：RTF 文件一律以 `{\rtf` 开头，编码探测把 7-bit ASCII 的标记当 UTF-8 读出来后，靠前缀判断 —— 被改名成 `.txt` 保存的 RTF 也能正确提取，而不是把满屏控制词当正文。

**验证**：`rtf.test.ts` 新增 29 条（结构 / `\uN` 与代理对 / GBK·UTF-8·1252 三种 `\'hh` / 跳表 / 标点映射 / 边界）；`readManuscript.test.ts` 新增 4 条（.rtf 提取、改名识别、空 RTF 拦截、体检文案）；`ImportScreen.test.tsx` 新增 1 条端到端（上传 .rtf → 正文提取 → 说明来源 → 可进入分章）。

## 增量：分章导出与整本压缩包

**零依赖 zip，够用就自己写。** 只用到经典 ZIP（local file header + central directory + EOCD），浏览器原生的 `CompressionStream('deflate-raw')` 产出的正是 ZIP 要的 raw deflate；环境没有它、或测试要固定字节时退回 store（不压缩）。中文路径在 local 与 central header 都打 UTF-8 标志位（general purpose bit 11），否则 Windows 解压出来是一堆乱码。引入一个压缩库要多打几十 KB、多一条供应链，而这里只差一个 CRC32（反射多项式 `0xEDB88320`）和几个字段偏移。分章导出离 4 GB 很远，不写 ZIP64，单文件超限直接报错。

**PDF 用非嵌入的 CID 字体。** `/BaseFont /STSong-Light` + `/Encoding UniGB-UTF16-H`，正文写成 UTF-16BE 十六进制串，另写 `/ToUnicode` 让文字能被复制；标题用描边做伪粗体，页脚是「第 N 页 / 共 M 页」。嵌一份中文字体是每章几 MB，子集化要自己啃 TTF/CFF，位图方案又把书撑到几十 MB；非嵌入字体只靠字体名 + GBK 编码，一章约 5–15 KB。方案定稿前在 macOS 上用 CoreGraphics 与 pdfium 实际渲染过中文、分页、页码、标题折行，文本也能被 MuPDF 提取。折行做了中文避头尾：闭合标点悬挂在行尾（≤2 个全角字符、不越页边距），开引号/开括号带到下一行行首；拉丁词不拆。

**超出 GBK 的字统一换成 □，不是只处理 emoji。** 容易想到「非 BMP 才要处理」，实测不是：`㵘`（U+3D58）在 Adobe-GB1 里有 CID 但跨 supplement，macOS 上被显示成「獒」；`䶮`、`㛃` 同理。所以生成了一份 139 段 / 21887 个码位的 GBK 覆盖表（约 1.3 KB），PDF 文本里不在表内的码位一律换成 `□`（U+25A1，GBK 覆盖得到），非 BMP 字符全部替换。宁可给一个诚实的占位符，也不能让读者看到随机错字 —— 要原样保留就选 TXT / MD / RTF。

**命名按「这次导出的最大章号」补零，目录按线分开。** 每条线内取实际导出的最大 index，补 `max(3, 位数)` 位（`第001章`、`第0123章`），保证文件管理器里按名字排序就是章序；固定三位写到 1000 章以上会乱。标题为空时文件名只留章号；标题里 `\ / : * ? " < > |` 与换行、控制字符去掉，结尾的 `.` 也去掉（Windows 不允许），超过 40 字截断。书名超过 40 字同样截断 —— 书名同时是 zip 根文件夹名与下载文件名，个别解压器对单级名字有 255 字节上限（120 个汉字约 360 字节就超了）。zip 根目录是书名（空书名回退「未命名作品」），主线章节直接放根下，外传各进 `外传·X` 子文件夹 —— 外传本来就不该和主线同号章节混在一起。

**逐章格式覆盖只记「改过的那几章」。** `formats` 是 `chapterId → PackFormat`，没记录就跟着默认格式；改默认格式时已覆盖的章不变。四个格式各有去处：平台要 TXT、自己读要 PDF、给编辑要 RTF、以后还要排版要 MD，一次打包里混着放是正常需求，而不是分四次导出。列表里每行一个原生 `<select>`，面板里直接看得见每个文件是什么格式。

**先出计划，再生成内容。** `planChapterPack` 是纯同步函数，只算文件名、目录、跳过计数，面板打开就能即时渲染列表与统计；点「下载压缩包」才走 `buildChapterPackZip` 生成 RTF / PDF 并把整包压成字节。这样每改一次格式不会重排一遍 PDF，异步也只留在真正需要它的地方。

**与现有单文件导出互不影响。** 原有「全书 / 单章 / 外传」范围、Markdown / 纯文本格式、预览、复制、下载全部保持原样；打包模式单独一套控件，也不显示「复制」（zip 没法复制）。不做单章 RTF / PDF 下载：这两个格式的价值在「整本每章一个文件」，单开一个入口只会多一条要维护的路径。txt / markdown 直接复用 `formatChapter`，与现有单章导出逐字节一致，不会出现「同一章两种导法内容不同」。

**测试覆盖**：新增 `gbkCoverage.test.ts` / `rtf.test.ts` / `pdf.test.ts` / `zip.test.ts` / `chapterPack.test.ts` 与 `ExportSheet.pack.test.tsx` / `download.test.ts`，覆盖 GBK 边界与 `□` 替换、RTF 转义与 `extractRtfText` 往返、PDF 的 xref 偏移自洽 / 分页 / ToUnicode、zip 的 CRC 标准向量与 deflate·store 两条回读路径、补零与命名净化、逐章覆盖与跳过计数，以及面板的默认格式 / 覆盖 / 下载字节以 `PK` 开头 / 失败提示与范围顺序（打包在前、全书在后）；现有单文件导出行为用例不变。

**验证结果**：typecheck 通过；83 个测试文件 / 1883 个测试全绿（本次新增 7 个测试文件、113 条：gbkCoverage 12 / rtf 16 / pdf 23 / zip 21 / chapterPack 24 / 导出面板打包 9 / download 6 / 原有导出面板测试补 2 条范围顺序），连跑稳定；`npm run build` 通过（WritingPage 按路由懒加载，107.5 kB / gzip 36.7 kB，无体积告警）。手工产物验证：混合 txt·md·rtf·pdf 与「外传·X」子目录的样例 zip 用系统 `unzip -t`、Python zipfile（UTF-8 标志位/CRC/extractall）、bsdtar 三重校验通过；PDF 用 macOS CoreGraphics、pdfium 渲染并目视检查中文/分页/页码/避头尾/□ 净化，MuPDF 文本提取正确；RTF 用 macOS `textutil` 读回中文、emoji、生僻字与空行正确。性能：200 章 ≈ 48 万字的整本打包（plan+build，四格式混合）实测 72 ms、zip 191 kB。

**关键决定**：

- **回溯不调模型**：章节顺序/标题/摘要已是事实，确定性映射 + 预览确认比模型重写可靠，且零成本。
- **回溯不设目标字数**：旧稿现有字数是历史事实，不是写作目标；写进 targetWords 会被误读成「每章写 26 字」。
- **前沿续写只给 3–5 章**：一次调用接上当前进度；太多等于替作者写整本，太少不解决「下一章写什么」。
- **结果仍是提案**：不写正文、不自动落库、不自动改人物命运/感情/凶手；提案可改文本，采用后才追加末卷。
- **零迁移**：不新增 Dexie/备份版本；复用现有 outlineTree 提案与章节关联字段。

**验证结果**：

- 默认并行/串行 **124 文件 / 2445 tests 通过 + 1 skip**；typecheck/build 通过；QA 独立 m3 套件 **37 例**（回溯数据层 10 / UI 8 / 续写服务 11 / UI 8）。
- 沙盒新增《旧稿十章》与 `outline-continue` mock：`m3-01` 回溯预览 → `m3-02` 回溯树 → `m3-03` 规划依据 → `m3-04` 续写细目+提案 → `m3-05` 采用后追加末卷；页面异常 0。
- 文学顾问复核：回溯「敢用」、续写「依据够但判断材料不够」；P1 已修（现有字数仅参考、空梗概提示、续写细目四要素、入口改「规划后续 3–5 章大纲」），复审确认可提交。

**遗留 / P2 / 真机项**：

- P2：续写提案两套采用按钮（ProposalInbox 全局 + 单条）可去重；三个大纲入口（细化/自动大纲/互动推演沉淀）的关系可加一句说明。
