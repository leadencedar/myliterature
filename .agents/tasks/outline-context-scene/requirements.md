## 1. 背景

用户反馈：在大纲节点的**梗概**或细化时的**额外要求**里写到知识库里已有的人物/设定时，AI 细化出的子节点有时不按该条目的设定写；即使作者手工「关联设定」，细纲也只体现「这个人存在」，不体现他的性格、软肋、说话方式或世界规则的代价。

已核实的机制（证据见第 2 节）：

1. **细化链路自建上下文**：只注入作者手工勾选条目（`linkedEntryIds`）的「标题 + 一句话摘要」，不做名称匹配、不注入 `pinned` 核心设定、不渲染条目字段（`outlineExpand.ts:87-93`）。
2. **细化结果不落关联**：`outlineTree` 提案 payload 只有缩进文本，落库时 `linkedEntryIds` 恒为 `[]`（`apply.ts:256-275`）。下一层细化或写正文仍要靠名字重新猜。
3. **名称匹配粗糙**：只认完整 title/alias 子串，trim + lower；无评分、按条目顺序取前 8 条；泛化别名（「师父」「他」）会挤掉真正相关的人（`entrySearch.ts:39-45`、`SummaryChainContextBuilder.ts:419-423`）。
4. **细化产物不可写**：子节点梗概只要求「谁想做什么、遇到什么阻碍、结果如何」，没有场景卡约束，模型容易写成事件概述或设定复述；写正文时又缺「本章要落地几场戏」的结构承诺，于是「写着写着就收尾」。
5. **细化链路自身有两处 bug**：`runExpand` 用已保存的 node 但用面板本地 `linked`，改了梗概/关联未保存就直接细化会看到旧值（`OutlineNodeSheet.tsx:148-167`）；`replace` 细化会删掉旧子节点并解除已写章节的大纲关联（`apply.ts:156-165`、`DexieNovelRepository.ts:431-439`），确认面板没有告知；大纲树创建非事务（`apply.ts:256-275`），大子树失败会留下半棵。

## 2. 目标

M1 结束时，作者应当可以：

1. 在大纲节点梗概（或细化额外要求）里写到一个知识库人物/设定，**细化时该条目的完整字段自动进入上下文**，细纲体现其性格/软肋/说话方式/世界规则代价，而不只是名字。
2. 在细化前看到「本次将参考哪些设定」（核心设定 + 显式关联 + 名称命中），并临时增减。
3. 采用细化结果后，**在一个确认面板里看到并调整**「每个新子节点将关联哪些条目」，确认后写入；不做静默关联，也不丢父节点的显式关联。
4. 细化出的子节点是**可直接开写的场景卡**：谁要什么、阻碍、转折、结尾局面/认知变化，并至少有一处由人物软肋或规则代价驱动的选择/拒绝。
5. 写正文时目标字数**来源可见**（大纲值或默认 3000），prompt 有场景数/节拍结构，生成被截断时明确提示，而不是当成完成。
6. 现有能力不回归：无新输入的旧调用 prompt 逐字节不变；不升 Dexie / 备份版本；不破坏既有测试基线（有意更新的基线单独评审）。

## 3. 范围

### 3.1 T0：细化链路修复（必做）

- 细化前先落盘当前表单（标题/梗概/目标字数/状态/关联），失败则中止并提示。
- `replace` 细化前二次确认，明确「将替换 N 个子节点，M 个已挂章节会解除大纲关联（正文保留）」。
- 大纲子树落库事务化：替换/追加在单个仓储事务里完成，失败不留半棵树。

### 3.2 T2/T3：规划上下文与场景卡（必做）

- 新增共享的「条目选择 + 渲染」模块，规划侧与正文侧复用同一套 `renderEntry` 与匹配规则（旧 `mentionedEntries` 语义保持不变）。
- 名称匹配增强：NFKC/大小写/空白归一、评分（title > alias、长名优先、2 字名降权）、泛化别名降权、每层上限、返回命中原因。
- 细化 system prompt 加「遵守核心设定 + 场景卡 + 设定落地为选择」任务约束；user prompt 增加【核心设定】【相关设定（完整字段）】【未收束伏笔（可选）】块与注入清单。
- 细化结果采用后，增加「关联确认」面板（建议 links 可展开、可移除、随确认写入；会话内记住被移除项）。

### 3.3 T1 结构件与截断防线（必做，M1 只做这一半）

- targetWords 口径：有值以其为准，为空默认 3000；生成面板显示来源，可跳去大纲修改。
- 章节 prompt 增补：目标字数对应的场景数**参考**（3000≈1–2 场，6000≈3–5 场，更长的章按节拍可 3–6 场）、按梗概节拍展开、节拍不足写深一场而不是凑字数、结尾收在钩子上、文体篇幅建议与本节目标冲突时以本节目标为准。
- `runStream` 透传 `maxTokens`（按 target 推导并夹取安全范围）；生成结果检查 `finishReason === 'length'`；用户中止与截断都标记「未完成」，不显示「生成完成」。

### 3.4 不在 M1

- 生成后的目标差额提示、「补未落地场景」按钮（M2 T1 收尾）。
- 章节归档、知识库增长、大纲状态联动（M2 T4）。
- 自动大纲（M3 T5）、文风指纹/锚点/检查（M4 T6）。
- 新增 `OutlineNode`/`Chapter` 字段、Dexie v8、备份 v5、大纲提案 payload 结构变更。
- 多方向「推荐故事发展」、AI 润色、文风评分。

## 4. 用户故事与验收场景

### US-1 提到人物就按设定出细纲

给定已有人物条目「沈砚」，字段含「说话方式：短句、爱用反问」「软肋与恐惧：妹妹」。
当作者把卷节点梗概写成「沈砚在渡口与裴照相遇，被迫接下去北方的差事」，不手工勾选任何条目，点击「细化这一节点」。
则：细化面板的「本次参考设定」列出沈砚与裴照（名称命中）及核心设定；模型收到的 user prompt 含两人的完整字段；生成出的子节点梗概里，沈砚的沉默/反问或妹妹软肋**影响了具体选择**，而不是只出现名字。

### US-2 关联可确认、可移除、不静默

当作者采用这份细化结果后：
则：出现「关联确认」面板，逐节点列出建议关联的条目（含父节点显式关联，标注来源）；作者可取消某条；确认后 `linkedEntryIds` 写入，取消的条目本次不写入；不点确认则一条都不写。

### US-3 替换与事务安全

当节点已有 3 个子节点、其中 2 个已挂章节（都有正文），作者再次细化并采用：
则：确认前明确列出「替换 3 个子节点、2 章解除关联」；采用过程失败不会留下半棵树或删掉一半旧节点。

### US-4 字数结构

当大纲节点 targetWords=6000，点击「生成本章」：
则：面板显示「目标 6000 字（来自大纲）」；prompt 要求 3–5 场、按梗概节拍展开、优先于文体建议；若模型输出被 `finish_reason=length` 截断，界面明确显示「生成被截断，未完成」，保留内容但建议续写/重试。

### US-5 默认值

当大纲节点 targetWords 为空：
则：生成面板显示「目标 3000 字（默认）」，prompt 按 3000 处理；作者可去大纲把目标改成实际值。

## 5. 成功指标（M1 验收）

1. **细化设定覆盖率**：人工抽 20 个「梗概提到已有条目」的细化任务，至少 18 个的 prompt 中包含该条目完整字段（现为 0，除非手工关联）。
2. **关联质量**：抽 20 个采用后的子节点，错配关联率 <5%（宁漏勿错）；作者取消过的条目在本次会话内不再出现。
3. **细纲可写性**：抽 10 个子节点，至少 8 个具备「目标—阻碍—转折—结尾局面/认知变化」四要素，且至少 1 处选择由软肋/规则代价驱动。
4. **截断可见性**：构造 `finish_reason=length` 的响应，界面 100% 显示「未完成/被截断」；正常完成不受影响。
5. **字数目标可见性**：生成面板 100% 显示目标值及来源（大纲 / 默认）。
6. **零回归**：无条目的旧 `buildExpandUserPrompt` 调用逐字节不变；整套 typecheck/test/build 通过；不新增 Dexie/备份版本。

## 6. 约束与红线

- **产品原则**：结构化数据落库必须经作者确认；关联只建议、不静默写回。
- **零迁移**：M1 不新增实体字段；links 通过采用后的确认面板直接 `updateOutlineNode` 写入。
- **缓存纪律**：核心设定进细化 system prompt（同一本书内稳定），逐节点条目进 user prompt；无新输入时 prompt 逐字节不变。
- **移动端优先**：细化面板的注入清单与关联确认要可折叠、可一键采用，不增加多次全屏确认。
- **不制造焦虑**：不新增「未关联条目数」之类的负债指标。
- **精度优先**：匹配宁可漏、不可错；短名/泛化别名不得抢占真正相关的条目。

## 8. 术语

- **场景卡**：可直接开写的细纲单元，包含「谁想要什么 / 什么在阻碍 / 转折点 / 结尾局面或认知变化」。
- **核心设定**：`pinned` 条目，始终注入、不参与预算裁剪。
- **显式关联**：作者手工选择的 `linkedEntryIds`；**推断关联**：按名称匹配得到的候选。
- **注入清单**：细化前展示的「本次将参考的设定」列表，含来源与 token 估算。
