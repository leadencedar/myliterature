# M2.1 · 归档采用安全修与伏笔流水

> 来源：5 类作者用户测试的 2 个 P0（见 `.agents/tasks/user-testing-m2/summary.md`）
> 目标：不升 schema、不大改 UI，先把「可能覆盖旧库」和「伏笔不可审计」两个风险降下来。

## 范围

1. **合并/替换默认不选**：归档收件箱里 action=merge/replace 的提案（摘要 replace、进展 replace、已有条目的合并）默认标记为忽略；「采用本批」只采用新增与未忽略项。作者展开后点「恢复」才会纳入本批。同时显示提示：「本批含 N 条合并/替换，已默认不选；展开核对后点「恢复」才会写入。」
2. **待确认计数说全**：编辑器状态行从「N 条知识库更新待确认」改为「N 项待确认（含摘要、进展、条目）」，N=本批全部 pending 提案数；挂载恢复同样按全部计数。
3. **伏笔流水可见**：归档服务把本章 `newOpenThreads / resolvedThreads / openThreads` 写入 localStorage 审计（按 batchId + chapterId）；收件箱顶部按章显示「新埋 / 收束 / 现存」，并提示「若误收束，在摘要的『未收束伏笔』里加回」。审计丢失不影响提案与数据（零迁移）。

## 非目标

- 不新增 Dexie 字段/表；不改摘要数据模型；不做批次全局收件箱重排（M3）。
- 不自动采用摘要/进展；作者仍逐项确认。

## 验收

- 本批含 merge/replace 时，默认「采用本批」不会提交这些提案；展开点「恢复」后可作为本批提交。
- 状态行计数 = 收件箱本批全部 pending 数量（摘要+进展+条目）。
- 收件箱显示本章新埋/收束/现存伏笔；resolved 项可在摘要 openThreads 编辑里加回。
- 既有 create-only 批次行为不变；其他 ProposalInbox 调用方行为不变。
