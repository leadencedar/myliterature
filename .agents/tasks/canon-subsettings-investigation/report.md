# 同人原作脉络与复杂角色子设定：产品与架构调查报告

## 一、结论先行

这两个缺口不能靠“再多写几条世界观”解决。现有系统缺的是两个独立、可计算的层：

1. **原作脉络层（Canon Layer）**：保存作品与版本、按时期组织的原作事件、时间截面、角色阶段状态、信息可见范围、事实置信级和来源。它给出“分叉前的基线”，再与互动推演现有的世界线差异叠加。
2. **角色子设定层（Facet Layer）**：以人物条目为根，保存能力、形态、装备、被动、资源、限制和战术等子设定，以及触发、前置、依赖、协同、冲突、消耗和禁止推论。它解决“有什么”之外的“什么时候能用、能否组合、用了以后发生什么”。

建议一期采用以下方案：

- 原作脉络使用**独立的规范化事件账本 + 显式时间截面**，不要复用普通 `KnowledgeEntry`，也不要继续把整份原作说明塞进写作规范。
- 复杂角色使用独立的通用 `Facet` 表，以普通人物 `KnowledgeEntry` 为根；不要给 `KnowledgeEntry` 直接加一棵任意深度树。
- 能力选择采用**确定性候选召回 + 小型结构化 LLM 选择器 + 本地规则复核**。一期不依赖向量数据库。
- 生成前形成“行动 / 能力计划”，默认自动继续，在“本次注入 / 本步依据”中折叠展示，允许临时增删，不增加强制确认步骤。
- 互动推演把资源、形态、伤势、装备、已知秘密和能力可用性写成类型化世界线差异；沿当前路径现算，回退无需反向修改，兄弟分支天然隔离。
- 资源追踪不设全局固定的“精确或模糊”模式。新增作品级**状态模拟风格 / 叙事精度策略**，依据风格档案、写作规范、作品类型和资源定义给出可见建议，并允许每一种资源单独覆盖。
- 可迁移 OC 使用跨作品全局母版。加入作品时克隆为项目快照并重映射子设定关系；之后独立修改，母版更新不自动污染已有作品。
- 生成后只给一致性问题和修改建议，不自动改正文；结构化状态若不合法则按现有“宁可少记”原则拒绝该状态变化并明确提示。

现有互动推演并不是推倒重来。它已经具备最难复用的地基：树形世界线、路径叠加、兄弟隔离、字段锁定、差异过滤、摘要检查点、沉淀大纲、推演章节上下文和逐字节零回归护栏。新设计应扩展 `WorldlineDelta` 和上下文装箱，而不是另造一套分支系统。

## 二、现有系统的能力与证据

### 2.1 已经能做到的事情

#### 结构化知识库、核心设定和可变性

- `KnowledgeEntry` 已有分类、名称、别名、摘要、自由字段、核心标记、章节来源、版本、作用范围和逐字段锁定，但**没有父子关系、能力关系或条件模型**。现有字段见 `src/domain/schema.ts:125-151`。
- 分类模板可以自定义字段；内置世界观与人物模板已经区分世界线上的锁定 / 可变字段，例如规则、代价、性格、说话方式默认锁定，身份、关系、成长弧线默认可变。见 `src/domain/defaults.ts:13-114`。
- 已有“时间线”建议分类，但每条只含“时间 / 事件 / 后果”三个普通文本字段。见 `src/domain/defaults.ts:163-169`。指南也明确要求“一事件一节”，说明它只是扁平条目，而不是时间截面或事件状态机，见 `docs/世界观写作指南.md:80-93`。
- 条目编辑器按分类模板渲染一组字段，并提供核心设定、推演作用范围和字段可变性；没有层级、依赖、互斥或资源配置入口。见 `src/features/knowledge/EntryEditorSheet.tsx:24-49,260-340`。
- 条目列表按分类分组、卡片平铺，搜索名称、别名、摘要与字段正文；没有树形导航。见 `src/features/knowledge/EntryList.tsx:8-12,38-44,62-65,99-103`。

#### 写作规范能临时承载同人约束，但不能计算

- 产品目前把“时间截面、原作差异、信息分层”放进写作规范原文。规范按作用范围整份注入，并且不拆分、不合并。见 `docs/产品文档.md:169-201`。
- 这使模型在文字足够清楚时可以遵守“后期人物不能提前出现”等规则，但程序无法回答“当前截面前发生了哪些事件”“某角色此刻知道哪些事实”“事件 E 在本分支是延迟还是取消”。产品文档也把结构化差异说明明确留到以后，见 `docs/产品文档.md:201`。

#### 互动推演已有可靠的世界线叠加基础

- `ScenarioSetup` 已记录主角、起点时间 / 地点 / 处境、结局目标、里程碑、基调和预计步数，但时间与地点只是自由文本，并不引用原作版本、事件或时间截面。见 `src/domain/schema.ts:475-500`。
- `WorldlineDelta` 已支持字段覆盖、本线新条目、条目处境、OC 状态、事件和标记。见 `src/domain/schema.ts:372-415`。
- `effectiveKnowledge` 只沿“根 → 当前节点”应用差异，后写覆盖先写；这正是兄弟分支隔离所需的机制。见 `src/domain/worldline.ts:196-344`。对应测试覆盖了“2a 的改写在 3a 可见、2b 看不到”和本线人物隔离，见 `src/domain/worldline.test.ts:153-205`。
- 生成前、仓储落库前都会过滤未知条目、模板外字段、锁定字段和非法规则状态；手工编辑若有非法项则整次拒绝。见 `src/domain/worldline.ts:414-572,614-714`，以及 `src/data/dexie/DexieNovelRepository.ts:910-983,1005-1028`。
- 回退只改 `cursorNodeId`，不改 `mainNodeId`，也不发生成请求；推进才写新节点并切主线。见 `src/data/dexie/DexieNovelRepository.ts:994-1003` 和 `src/features/scenario/useScenarioRunner.ts:402-488`。
- 长路径已有每 5 步检查点摘要，最近 3 步保留原文；这可以直接承载以后更丰富的状态，而不必把整条路径反复塞入 prompt。见 `src/domain/scenario.ts:243-335`。

#### 普通写作、推演沉淀与检查链路已经贯通

- 普通整章生成已有稳定前缀 / 易变后缀、token 预算和“本次注入”清单。默认预算为 24,000 tokens，名称推断条目上限为 8。见 `src/context/ContextBuilder.ts:132-143`。
- 推演路径可以按连续步骤沉淀为大纲，代码校验“对应步骤”首尾相接、不重叠、不遗漏。见 `src/features/scenario/pathOutline.ts:18-66,300-365`。
- 来自推演的章节已经注入四类材料：推演专属设定、分叉前经过、步骤原文和世界线状态。见 `src/features/scenario/chapterContext.ts:107-201`；装箱位置在易变后缀，见 `src/context/SummaryChainContextBuilder.ts:219-240`。
- “按规范检查”已经具备分段、结构化结果、原句定位、只提示不改正文、截断即失败等可复用能力。见 `src/features/writing/normCheck.ts:67-118,155-229` 和 `src/features/writing/NormCheckSheet.tsx:77-84,150-207`。
- 所有需要持久化的 AI 结构化产出已有统一 Proposal 单行道，确认后才写库。见 `src/proposal/apply.ts:13-18,97-103`。
- 结构化 LLM 调用已有 JSON Schema、Zod 校验和一次修复重试，可以直接承载小型能力选择器。见 `src/llm/structured.ts:23-31,44-52,52-138`。

### 2.2 两类需求究竟缺在哪里

| 缺口类别                      | 原作脉络                                                                                                                                                                     | 复杂角色子设定                                                                                                                                                                                                                                                        |

### 2.3 当前召回为什么不足以解决复杂能力

普通章节的默认预选只有：

1. 大纲 `linkedEntryIds`；
2. 上一章摘要 `appearingEntryIds`；
3. 大纲标题 / 梗概中的名称命中；
4. 上一章摘要 / 关键事件中的名称命中。

实现集中在 `computeDefaultEntryIds`，见 `src/context/SummaryChainContextBuilder.ts:372-429`。名称推断最多 8 条。互动推演稍强一些：把本线曾改写的条目作为显式候选，最多 12 条，再从最近情节、行动和摘要里按名称推断最多 8 条，见 `src/features/scenario/scenarioPrompt.ts:84-85,279-333`。两者仍然无法根据“狭窄室内、左手受伤、已拔大太刀、妖力不足、需要净化而非杀伤”完成能力资格判断。

“按规范检查”也只带核心条目和正文中按名称命中的最多 8 个条目，见 `src/features/writing/NormCheckSheet.tsx:150-158`。此外，推演材料只传给整章生成，不传给段落加工或规范检查，见 `src/features/writing/ChapterEditorScreen.tsx:308-320,584-619`。所以当前检查无法系统验证“本章使用的能力是否满足当时形态 / 资源 / 信息条件”。

### 2.4 当前 prompt 成本机制既是基础，也是风险

现有装箱顺序为“作品与风格 → 写作规范 → 核心设定 → 关联条目 / 大纲与摘要”，规范和核心设定强制注入，见 `src/context/SummaryChainContextBuilder.ts:35-39,116-160`。产品目标明确是控制成本和注意力，而不是填满上下文窗口，见 `docs/产品文档.md:470-474`。因此新功能不能把“结构化”误解为“把全部结构重新序列化进 prompt”；必须先召回，再只展开本场景需要的节点。

## 三、原作脉络层设计

### 3.1 方案比较

| 方案                                                 | 优点                                                                                             | 关键问题                                                                                             | 结论                                     |
| ---------------------------------------------------- | ------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------- | ---------------------------------------- |
| **A. 继续用普通条目 + 写作规范**                     | 无迁移；立即可用；作者可自由写                                                                   | 事件、阶段、认知和分叉处置都只是文字；无法按截面计算；整份规范反复注入；模型容易把作者全知泄漏给角色 | 只保留为兼容入口，不作为产品模型         |
| **B. 单行 `CanonPackage`，内部存一整棵 JSON / 文档** | AI 一次提取和整体确认容易；原子写入简单                                                          | 每次修改整行；移动端编辑困难；版本、事件、来源和角色阶段难局部复用；备份合并冲突粒度过大             | 可作为导入过程的临时草稿，不作为最终存储 |
| **C. 独立的作品 / 版本 / 事件 / 截面 / 分支表**      | 可按事件和角色计算；能精准装箱；世界线 delta 可引用稳定 id；来源和版本可审阅；局部编辑与合并安全 | 表与 UI 较多，需要新迁移、导入提案和引用完整性校验                                                   | **推荐一期采用**                         |

推荐 C，但一期界面仍应是“事件列表 + 并行组 + 时间截面”，不做复杂流程图。数据先规范化，图形化事件网留到二期。

### 3.2 一期数据结构草图

以下是产品模型草图，不是实现代码。

```text
CanonWork
- id, novelId
- title                         原作名称
- defaultVersionId
- description
- createdAt, updatedAt

CanonVersion
- id, workId
- label                         例如“漫画版”“动画第一季”“游戏 A 路线”
- medium                        manga | anime | novel | game | route | other
- baseVersionId?                派生版本可指向基版
- variantOrder
- notes

CanonEvent
- id, workId, versionId
- variantKey?                   对应不同版本中的“同一逻辑事件”
- phase                         时期 / 篇章
- orderGroup                    时间顺序组；小者先发生
- parallelKey?                  同组并行事件的分组键
- dependsOnEventIds[]           直接因果前置，不等于所有时间前置
- title, summary
- participantEntryIds[]         关联普通人物 / 势力 / 地点条目
- visibility[]                  author | public | faction(entryId) | character(entryId)
- claimType                     canon-fact | character-hypothesis | behavior-inference
- certainty                     confirmed | inferred | open
- sourceRefs[]                  versionId + 章节/集数/页码/链接/备注
- tags[]

CanonSnapshot
- id, workId, versionId
- title                         例如“决战前夜”“动画第 12 集结束后”
- cut:
  - throughOrderGroup           此组之前的事件均已发生
  - occurredAtBoundaryEventIds  同一并行组中此刻已经发生的事件
- characterStages[]:
  - entryId
  - stageLabel
  - identitySummary
  - availableFacetIds[]
  - unavailableFacetIds[]
  - equippedFacetIds[]
  - activeFormFacetIds[]
  - factionEntryIds[]
  - knownEventIds[] / unknownEventIds[]
  - sourceRefs[], certainty
- notes

CanonBranch
- id, novelId, snapshotId
- title
- divergenceEventId?
- baseEventPolicies[]:
  - eventId
  - disposition                 retained | delayed | changed | cancelled
  - replacementSummary?
  - newTimingHint?
  - reason
```

设计说明：

- **版本不混写**：一个 `CanonSnapshot` 只绑定一个主版本。其他版本通过 `variantKey` 对照，默认不进入生成 prompt，避免漫画与动画互相覆盖。
- **顺序与并行都能表达**：`orderGroup` 负责粗顺序；同组事件可并行，截面用“边界组 + 已发生事件 id”表达组内进度。二期若需要复杂因果图，可在现有 `dependsOnEventIds` 上扩展，不需迁移事件身份。
- **置信级不是可见范围**：`certainty=open` 表示原作留白，作者全知层也不能把它补成事实；`visibility=author` 表示存在一个确定事实，但角色不知道。两者必须分开。
- **来源只用于审阅与追溯**：prompt 默认只带来源短标签，不带 URL 列表和长证据正文，避免重现当前长规范的注意力问题。
- **角色阶段引用 Facet id**：原作人物在某时期“会什么 / 不会什么”与复杂 OC 使用同一子设定语言，避免两套能力模型。

### 3.3 时间截面的计算结果

从一个 `CanonSnapshot` 应计算出四组内容，而不是拼一份长文：

1. **已发生的原作事件**：`orderGroup` 小于边界，或在边界的 `occurredAtBoundaryEventIds` 中。
2. **尚未发生的原作事件**：边界之后的事件，作为导演层未来基线，不能让角色提前知道或使用其产物。
3. **角色阶段状态**：身份、可用 / 不可用能力、装备、形态、阵营。
4. **分层认知**：
   - 作者层：所有 `confirmed` 事实；`inferred` 明确标为推断；`open` 明确标为不可补全。
   - 公开层：`public`。
   - 阵营层：角色当期所属阵营可见的事实。
   - 个人层：`character(entryId)` 与 `knownEventIds`。

生成提示中要明确分成“作者层事实（不得自动变成角色认知）”和“当前视角角色已知”。模型可以利用作者层安排伏笔，但角色的台词、决策和能力计划只能使用角色层信息。

### 3.4 与世界线 delta 的叠加

在现有 `WorldlineDelta` 中新增类型化事件变化：

```text
canonEventChanges[]
- eventId
- state: occurred | retained | delayed | changed | cancelled
- replacementSummary?
- newTimingHint?
- cause
```

计算顺序固定为：

```text
原作版本事件
  → 时间截面（已发生 / 未发生 + 角色阶段 + 可见范围）
  → CanonBranch 的作者预设改动
  → 根到当前节点的 canonEventChanges（后写覆盖先写）
  → 当前有效原作状态
```

规则：

- 截面之前的事件默认是历史事实。若作者要改“开场前已经不同”，应在 `CanonBranch` 中显式写 AU 基线，不让单步模型随意倒改历史。
- 截面后的事件默认 `retained + pending`；真正发生时记 `occurred`，偏离时记延迟 / 改变 / 取消。
- 取消或改变有 `dependsOnEventIds` 的事件时，只把后续事件标成“因果待复核”，**不自动连锁取消**。LLM 可以提出处理建议，但用户或当前世界线的后续步骤才决定沿用、延迟、改变或取消。
- 同一事件在路径上以后写覆盖先写；回退后只读取另一条路径，因此直接复用现有 `effectiveKnowledge` 的兄弟隔离机制。
- `events[]` 仍可保存同人原创事件；`canonEventChanges[]` 专门引用原作事件。两者不能混成短文本，否则失去可追踪性。

## 四、复杂角色“子设定”设计

### 4.1 `KnowledgeEntry.parentId` 与独立 `Facet` 表比较

| 维度              | 给 `KnowledgeEntry` 加 `parentId`                  | 独立 `Facet` 表                                     |
| ----------------- | -------------------------------------------------- | --------------------------------------------------- |
| 复用现有条目 CRUD | 高                                                 | 中，需要新 UI / 仓储                                |
| 表达能力规则      | 仍受分类自由字段限制                               | 可直接建触发、前置、资源、冲突等类型字段            |
| 搜索与统计        | 子能力会污染“知识条目数”和全局搜索                 | 人物页内管理，不把每个招式当世界实体                |
| 导入合并          | 当前按名称全书合并，同名子能力可能误合并           | 可按 `ownerEntryId + parentId + title` 对齐         |
| 世界线与选择器    | 仍需另加大量关系字段                               | 可直接输出紧凑候选卡并做本地校验                    |
| 全局 OC 母版      | 跨书复制整棵 `KnowledgeEntry` 容易混入作品限定字段 | 母版与项目 Facet 使用同一 payload，克隆和重映射清楚 |
| 零回归            | 所有现有条目查询都可能受到影响                     | 没有 Facet 时现有条目查询完全不变                   |

**推荐独立 `Facet` 表**。顶层人物仍是普通 `KnowledgeEntry`，保持身份、外貌、性格、目标、软肋、关系、口吻和成长弧线；子设定只处理可选择、可组合、可受状态影响的细节。

### 4.2 一期 Facet 数据结构草图

```text
Facet
- id, novelId, ownerEntryId
- parentId?
- relationToParent              contains | variant-of | component-of | rule-of | loadout-of
- order
- kind                          group | ability | form | equipment | passive |
                                resource | constraint | tactic | technique |
                                companion | blessing | other
- title, aliases[], summary
- rules                         能做什么及判定规则
- injectionLevel                always | conditional | reference-only
- triggerConditions[]           何种场景应进入候选
- prerequisites[]               真正使用前必须满足
- dependsOnIds[]                缺少依赖则不能使用
- synergyWithIds[]              推荐组合，但不强制
- conflictsWithIds[]            明确互斥
- exclusiveGroupIds[]           形态、武器姿态等同组只能选一
- capacityClaims[]              注意力、双手、身体动作、媒介通道等占用
- resourceEffects[]             consume | reserve | generate | restore
- sceneTags[]                   近战、远程、净化、飞行、室内、潜行等

```

条件使用受限结构，而不是让一期实现任意表达式语言：

```text
FacetCondition
- kind: scene-tag | location-tag | form-active | equipment-equipped |
        resource-at-least | injury-state | knowledge-known | flag | freeform
- refId / key?
- op: present | absent | eq | gte | lte
- value?
- description                  给作者和选择器看的原文
```

资源效果同时支持三种精度：

```text
ResourceEffect
- resourceFacetId
- operation: consume | reserve | generate | restore
- exactAmount?                 精确模式
- bandShift?                   分档模式，例如 -1
- narrativeEffect?             叙事模式，例如“短时间内不能再次连续使用”
```

### 4.3 继承、深度与不变量

- 作用范围解析：子设定显式值 → 最近祖先 → 顶层人物 `KnowledgeEntry.scope` → `universal`。
- 可变性解析：子设定显式值 → 最近祖先 → 类型默认。能力规则、限制、资源定义和装备规则默认锁定；“是否已学会 / 当前是否装备 / 当前形态 / 当前余量”属于运行时状态，不靠改写 Facet 定义表达。
- **不允许任意深度**。一期限制人物根下最多 3 层 Facet：`分组 → 子系统 → 具体能力/规则`。上述样本足够容纳；更深关系用依赖、协同、冲突和资源链接表达。任意深度会增加循环、继承歧义、移动端导航和 prompt 路径长度，却不会增强能力判定。
- 仓储必须拒绝：父节点跨人物 / 跨作品、父子环、超过 3 层、依赖不存在、自己依赖自己、互斥或协同引用非法对象。
- `reference-only` 不参与自动召回，除非作者显式添加或另一条已选 Facet 依赖它；它适合来源考据、兼容别名和不直接参与生成的补充说明。

### 4.5 跨作品 OC 母版

当前所有人物都以 `novelId` 归属于单一作品，仓储接口也只有 `listEntries(novelId)` / `createEntry(novelId, ...)`，见 `src/data/NovelRepository.ts:72-99`；代码中没有跨作品人物模板设施。

按已确认决策，新增应用级：

```text
CharacterTemplate
- id, title, entryPayload, version, createdAt, updatedAt

TemplateFacet
- 与 Facet 相同的内容字段
- templateId 替代 novelId / ownerEntryId
```

“加入作品”必须在一个事务中：

1. 克隆顶层人物为新的项目 `KnowledgeEntry`；
2. 克隆全部 TemplateFacet，生成新 id；
3. 重映射 parent、依赖、协同、冲突、资源引用；
4. 写入 `templateOrigin = { templateId, templateVersion }` 仅作溯源；
5. 应用作品自己的作用范围、原作版本和状态模拟策略。

之后项目副本和母版完全独立。母版更新不自动写入项目；若以后提供“吸收母版新版”，应生成字段级 / 子树级 Proposal。项目中提升出来的新能力默认只更新项目副本；更新母版必须是另一项显式操作。

## 五、“何时用什么设定”的选择机制

### 5.1 方案比较

| 方案                                    | 成本与确定性                     | 召回质量                                                                            | 一期适配性                                                           |
| --------------------------------------- | -------------------------------- | ----------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| 纯关键词 / 名称                         | 免费、可复现；现有代码已具备     | 对显式招式名有效；对“需要净化”“狭窄空间”“左手受伤”等语义弱                          | 可做第一层，不足以单独使用                                           |
| 向量 / RAG                              | 语义召回好；可处理不同措辞       | 需要 embedding、索引、模型版本与重建策略；纯前端还要处理体积、密钥和 IndexedDB 索引 | 二期。当前路线也把 RAG 放在后续，见 `docs/设计方案.md:26-29,470-474` |
| 纯 LLM 路由                             | 能理解场景和组合                 | 若把几十条完整能力都交给它，仍然长；结果不稳定；每次多一次调用；失效时无确定降级    | 不单独采用                                                           |
| **混合：确定性候选 + 小型结构化选择器** | 候选和硬检查可复现；选择器输入小 | 能兼顾语义、组合和前置                                                              | **一期推荐**                                                         |

### 5.2 一期选择流程

#### 第 0 步：收集场景信号

- 普通章节：大纲标题 / 梗概、用户额外要求、上一章摘要与结尾、地点、视角人物、当前装备 / 形态 / 资源状态。
- 互动推演：当前挑战、本次选项或自由行动、最近 3 步、起点地点、当前有效原作状态、当前世界线状态。
- 从推演沉淀的章节：优先使用对应步骤已经记录的 `usedFacetIds` 和状态变化，不重新猜一遍。

#### 第 1 步：永远注入

以下内容使用紧凑格式进入稳定前缀，不能临时取消：

- 顶层人物核心身份、性格、软肋、说话方式；
- `injectionLevel=always` 的子设定；
- 角色级和能力系统级硬约束、禁止推论；
- 当前处于激活状态的形态 / 装备所需的定义；
- 当前资源的单位、上限和跟踪方式，但不是整段历史日志。

“always”必须在 UI 中标注成本，避免用户把全部招式都设成 always。

#### 第 2 步：确定性候选召回

按固定分数排序，取最多 **24 个紧凑候选**：

1. 作者显式关联、行动中直接点名、上一步实际使用；
2. 标题 / 别名 / 场景标签精确命中；
3. 对标题、摘要、标签和触发条件做中文字符二元 / 三元组重合评分；
4. 当前地点、挑战类型、已装备、形态、资源、伤势、已知秘密匹配；
5. 对前四类命中的 Facet 展开一跳依赖、资源、冲突、协同和祖先分组；
6. `reference-only` 默认排除。

这比当前仅按名称子串的 `mentionedEntries` 更强，但仍完全在前端、无需新依赖。

#### 第 3 步：本地资格预检

对结构化条件先算出 `met / unmet / unknown`：

- 装备、形态、位置、世界线 flag、已知秘密等可以确定判断；
- 精确资源可做数值判断；分档资源可判断档位；
- 自由文本条件只能标 `unknown`，交给选择器并在计划中提示。

硬性 `unmet` 的能力不能被选择器宣称为可成功使用；它最多作为“主角尝试但失败”的候选。

#### 第 4 步：小型结构化 LLM 选择器

建议新增低温结构化任务，复用现有 `generateStructured` 的 Zod 与修复重试。输出：

```text
AbilityPlan
- selected[]（最多 8）
  - facetId
  - reason
  - role: primary | support | passive | attempted
  - combineWithIds[]
  - prerequisiteChecks[]: conditionId + met/unmet/unknown + evidence
  - conflictChecks[]: targetId/groupId + clear/conflict/unknown + reason
  - plannedResourceEffects[]
- warnings[]
```

本地再次校验：id 必须来自候选；依赖必须补齐；确定为 `unmet` 的前置不能被改成 `met`；冲突组、容量和资源不能被选择器绕过。现有任务配置已经把结构化推理设为低温、开 thinking，见 `src/llm/taskProfiles.ts:55-59,93-106,151-157`。

#### 第 5 步：“本次注入 / 本步依据”可见、可调

- 增加折叠组“行动 / 能力计划”：显示能力名、选择理由、组合、前置、冲突、预计消耗和警告。
- 默认自动继续，不再增加一次确认按钮。
- 作者可临时删除条件能力、从候选或树中添加能力；硬约束与禁止推论不能删除。
- 手工加入前置不满足的能力时，计划标成“尝试”，生成不得把它写成无代价成功。
- 所有变更只影响本次调用，不改角色档案；互动步骤实际发生的状态变化另记入世界线。

### 5.3 稳定前缀与缓存

- 稳定前缀只放：作品 / 风格、写作规范、原作版本与截面摘要、核心条目、顶层人物、always Facet、硬约束。全部按稳定 id 排序，不放时间戳、token 数或本次选择理由。
- 条件能力全文、当前状态、事件处置和 AbilityPlan 放易变后缀。选择不同能力不会截断前面的缓存命中。
- 选择器的 system prompt 固定；24 个候选使用每条几十字的紧凑卡片，不把完整来源和长规则都送进去。只有最终选择的 Facet 才把完整规则交给正文生成。
- 来源 URL、考据说明和 `reference-only` 正文不进入常规 prompt。

### 5.4 失败降级

选择器未配置、网络失败、输出修复后仍不合法时：

1. always / 硬约束仍然注入；
2. 从确定性候选中取资格为 `met` 的前 6 个，并展开依赖；
3. 不自动使用 `unknown` 或 `unmet` 的能力；
4. UI 标注“本次使用规则召回，未经过 AI 选择”；
5. 作者仍可临时增删；正文生成不因选择器失败而整体不可用。

如果连确定性候选也为空，就按顶层人物和硬约束继续，绝不退化成“把全部子设定塞进去”。

## 六、状态模拟风格与世界线状态

### 6.1 为什么不能全书只选“精确”或“模糊”

同一角色内，左轮弹药适合精确计数，妖力适合分档，注意力或精华循环可能只适合叙事状态。全书单选会迫使抽象资源伪精确，或让离散弹药失去约束。因此策略应是“作品级推荐 + 每资源实际策略”。

### 6.2 数据模型草图

```text
SimulationPolicy
- id, novelId
- recommendationMode: auto | author
- inputFingerprint              genre + style + relevant norms + resource schemas
- recommendedDefault           exact | banded | narrative
- rationale[]                  UI 可见
- resourcePolicies[]
  - resourceFacetId
  - mode                        exact | banded | narrative | none
  - source                      recommended | author
  - unit?
  - min?, max?, initial?        exact
  - bands[]?                    banded，例如充足 / 吃紧 / 濒尽 / 耗尽
  - narrativeRules[]?           narrative
  - allowDebt                   默认 false
- evaluatedAt

Scenario.setup.simulationSnapshot
- policyId / fingerprint
- resolvedResourcePolicies[]    开局时复制的实际策略
```

### 6.3 自动判断规则

系统在导入 / 编辑资源子设定后给出建议，不在每次生成前重复判断：

1. **结构先于文风**：有明确单位、容量和固定消耗的离散资源，如弹药、次数、魂核槽，优先精确。
2. **连续量默认分档**：体力、妖力、耐力等若没有可信数字，优先分档，不伪造 73/100。
3. **抽象资源默认叙事**：注意力、精神负担、精华积蓄、关系压力等优先记录“充足 / 分散 / 透支 / 需要恢复”及规则。
4. **作品风格调整建议**：硬核战术、游戏系统、军事作品提高精确比例；严肃文学、关系驱动、弱系统作品降低数字密度。
5. **写作规范优先**：规范若明确“弹匣 6 发”“不计算具体妖力数值”，直接形成对应建议。
6. 规则冲突或信息不足时选择叙事模式，并标“依据不足”，绝不把未知解释成无限。

可用一次低温结构化 LLM 对自由文本风格 / 规范做推荐，但最终结果必须展示“建议模式 + 理由 + 输入来源”，作者可在作品设置和每个资源上覆盖。

### 6.4 降级与历史稳定性

- 推荐器不可用时使用上述确定性默认：离散且有容量 → 精确；连续且有档位 → 分档；其余 → 叙事。
- 风格档案或写作规范变化后，只把 `inputFingerprint` 标成“建议可能已过期”，**不自动重算**。
- 作者点“重新评估”后，新策略只用于之后新建的推演和普通生成。
- 每个推演在开局复制一份 `simulationSnapshot`。旧节点始终按当时策略解释，避免风格变化把历史的“妖力吃紧”重新解释成某个数字。
- 活跃推演若要切换策略，必须由作者选择“从当前节点起采用”，并在该节点写一条策略切换及显式状态转换；之前的精确日志或分档日志原样保留。

### 6.5 类型化的角色状态差异

保留现有 `ocChanges` 作为旧数据兼容，同时新增：

```text
actorStateChanges
- resourceChanges[]
  - resourceFacetId
  - exactDelta? / setExact?
  - bandShift? / setBand?
  - narrativeAdd[] / narrativeRemove[]
  - reason
- formChanges[]                 enter | exit
- equipmentChanges[]            acquire | lose | equip | unequip | damage | reload
- injuryChanges[]               add | worsen | heal | remove，带部位/严重度/限制
- knowledgeChanges[]            learn | forget | disprove，引用事件/秘密/条目
- facetAvailabilityChanges[]    learn | lose | seal | restore
- policyChanges[]?              仅显式切换策略时
```

每一步的生成尾部自动提出这些变化，本地规则校验后随节点保存，并在“本线状态”高亮显示、允许编辑。有效状态仍按根到当前节点现算；回退只是换路径，兄弟分支不会看到另一线的消耗、伤势、装备或秘密。

提升规则：

- 永久学会 / 失去能力、永久装备归属、资源上限永久变化，可以生成项目级 Facet / 人物 Proposal，确认后成为该作品的通用基线。
- 当前弹药、临时妖力、伤势、当前形态通常只属于剧情状态，不应默认提升。作者显式选择时，先说明它会把“当前处境”变成“所有线的开局事实”。
- 提升只改作品副本，不改全局 OC 母版；更新母版需要单独确认。

## 七、生成正确性闭环

### 7.1 推荐流程

```text
场景 / 挑战 / 行动
  ↓
确定性召回 + 资格预检
  ↓
结构化 AbilityPlan（默认自动继续，可展开修改）
  ↓
正文生成
  + 结构化尾部：实际使用 Facet、资源/形态/伤势/装备/认知变化、原作事件变化
  ↓
本地硬规则校验与 sanitize
  ↓
一致性提示（只提示）
  ↓
用户采用正文；互动状态留在当前世界线
```

### 7.2 生成前计划

计划回答：

- 这一步 / 这一章准备使用哪些 Facet；
- 为什么与当前场景有关；
- 前置条件哪些满足、哪些未知、哪些不满足；
- 哪些能力组合，是否争用注意力、双手、形态或媒介；
- 预计消耗与状态变化；
- 哪些能力只能作为失败尝试。

计划默认自动继续，符合已确认的交互选择。只有出现“确定冲突、资源将低于下限、必须知道但角色未知”等硬问题时，计划区突出警告；仍不弹第二个强制确认框。

### 7.3 正文与结构化尾部

互动步骤已经使用“一次流式正文 + 结构化尾部”的模式，正文完成后解析变化并落节点，见 `src/features/scenario/stepSchema.ts:22-89` 和 `src/features/scenario/useScenarioRunner.ts:426-488`。可扩展其尾部，不必再读一遍正文提取状态。

普通章节在有 Canon / Facet 上下文时也可复用该模式，尾部只作为本次预览的检查材料，不自动写入普通章节的全局状态；没有相关数据时继续走当前纯文本 `chapter-draft`，保持请求逐字节不变。

### 7.4 生成后检查

不建议硬塞进现有“按规范检查”的语义。建议新增“设定与能力检查”，复用它的分段、问题卡、原句定位和“按建议改写”组件，但它无需存在写作规范也能运行。

检查输入：原作截面和当前分叉状态、角色当期可知信息、AbilityPlan、选中 Facet 全规则、生成前状态、正文、模型提出的生成后状态。

问题类型至少包括：

- `canon-time`：使用尚未出现的人物 / 装备 / 信息；
- `knowledge-leak`：角色知道了作者层或其他阵营秘密；
- `unplanned-use`：正文使用未进入计划且未注入规则的能力；
- `prerequisite`：前置未满足；
- `resource`：消耗、恢复或下限不一致；
- `conflict`：互斥形态、武器、注意力或身体动作同时占用；
- `hard-rule` / `forbidden-inference`：违反硬限制或作出被禁止的推论；
- `state-mismatch`：正文发生了变化，结构化状态却没记，或反之；
- `canon-causality`：已取消的事件仍被当作既成未来。

检查只输出严重度、关联事件 / Facet id、正文引文、原因和建议。它不改正文、不补写状态、不自动改变原作事件处置。作者采用建议时仍走现有可编辑预览。当前规范检查坚持同一原则，见 `src/features/writing/NormCheckSheet.tsx:77-84`。

互动节奏上的建议：每步立即做本地硬校验；只有出现结构化警告、作者点“深入检查”或准备沉淀时才额外调用 LLM 检查。普通章节若使用了 Canon / Facet，可在生成预览后自动运行一次检查，但失败不丢正文。

### 9.4 测试重点

1. **Canon 计算**：版本隔离、并行边界、截面前后、角色阶段、四级可见范围、确定 / 推断 / 留白、来源引用。
2. **Canon × 世界线**：沿用 / 延迟 / 改变 / 取消后写覆盖；兄弟分支隔离；取消前置后仅标记下游待复核，不自动改。
3. **Facet 不变量**：最大 3 层、无环、同作品 / 同 owner、依赖 / 协同 / 冲突引用完整、范围与可变性继承。
4. **候选召回**：名称、别名、标签、n-gram、当前状态、图关系扩展、上限 24、`reference-only` 不误入。
5. **选择器**：非法 id、漏依赖、篡改本地 `unmet`、冲突、资源不足、修复失败后的确定性降级。
6. **状态策略**：精确 / 分档 / 叙事三种 reducer；每资源覆盖；推荐器失败降级；风格变化不重解释旧节点。
7. **世界线状态**：弹药、形态、伤势、装备、秘密在回退和兄弟分支中隔离；祖先编辑后后代现算变化并提示旧事实。
8. **正确性检查**：只产生问题，不改正文、不改状态；原句定位与按建议改写仍需作者确认。
9. **三链路**：互动、普通章节、沉淀章节都拿到正确截面和 Facet；推演沉淀直接使用步骤已记的能力 id。
10. **兼容**：Dexie v7 → v8、备份 v1–v5、全局模板克隆 id 重映射、删除与悬空引用清理。
11. **零回归**：无 Canon / Facet 时所有现有 prompt、注入清单和 token 估算逐字节不变。
12. **缓存**：同一稳定输入顺序固定；场景能力变化只改变易变后缀。

### 9.5 主要风险与成本

| 风险 / 成本           | 影响                             | 控制方式                                                              |
| --------------------- | -------------------------------- | --------------------------------------------------------------------- |
| AI 拆分或原作提取错误 | 错误结构会比缺结构更危险         | 全部先 Proposal；保留来源定位；未确认不参与生成                       |
| 作者录入负担          | 原作事件和复杂能力很多           | 上传提取 + 手工调整并存；树模板；批量确认但可逐项展开                 |
| 选择器漏召回          | 正确能力没进入候选，LLM 无法选择 | n-gram + 标签 + 当前状态 + 图扩展；显式添加；确定性兜底；二期向量补强 |
| 选择器多一次调用      | 增加延迟与费用                   | 候选卡 ≤24、输出 ≤8、低温常规模型、稳定 system；失败不阻塞正文        |
| 状态过于游戏化        | 文学作品被数字压扁               | 状态模拟风格自动推荐；每资源可精确 / 分档 / 叙事                      |
| 状态过松              | 硬核作品出现无限弹药 / 无限能量  | 离散资源精确、本地不允许低于下限、状态变化可见可编辑                  |
| 版本混用              | 漫画 / 动画事实冲突              | 一个截面只选一个主版本；其他版本只做对照，不默认注入                  |
| prompt 重新膨胀       | 子设定越结构化反而塞得越多       | always 只放硬约束；两阶段召回；只展开最终选择；来源不注入             |
| 历史被新风格重解释    | 旧分支状态含义改变               | 策略指纹 + 推演开局快照 + 显式从某节点切换                            |
| UI 复杂度             | 手机端树和关系难编辑             | 最多 3 层、按钮排序、关系分区编辑；一期不做图编辑器                   |

工程量判断：这是一次**高成本但边界清晰的领域扩展**。最大工作不在表单，而在引用完整性、状态 reducer、备份迁移、三条生成链路和零回归测试。独立表方案虽然一期代码更多，但比把关系塞进 `KnowledgeEntry.fields` 后再反复补洞更便宜。

## 十、已经确认的产品决策

以下不再作为待决问题：

1. 原作脉络同时支持“上传资料 → AI 提取 → 作者确认”和手工编辑。
2. 子设定同时支持 AI 自动拆树后调整确认，以及手工建树。
3. 能力计划默认自动继续，以可展开清单展示并可临时增删，不强制每次额外确认。
4. 状态模拟方式由作品风格自动推荐，作者可见、可覆盖，并允许同一作品不同资源采用不同精度。
5. 可迁移 OC 使用跨作品全局母版；加入作品时生成独立快照，母版更新不自动影响已有项目。
6. 能力 / 资源状态自动记入当前世界线，突出显示并可编辑；提升为作品通用基线时再走确认。

## 十一、仍需用户决定的问题（3 项）

1. **一个时间截面是否只能选一个“主版本”？** 推荐“一个主版本 + 可查看的其他版本差异”，不自动混合。若需要漫画和动画按字段混搭，版本模型和冲突 UI 会明显扩大。
2. **上传的原作资料确认后是否长期保留全文？** 推荐默认只长期保存结构化结果、来源定位和用户明确选择保留的原文；完整上传文本可选归档。长期保留便于重新提取，但会增大备份并带来资料管理负担。
3. **深度一致性检查何时调用？** 推荐普通章节在使用 Canon / Facet 时于生成预览后自动检查；互动每步只做本地硬校验，LLM 深查在出现警告、作者手动触发或沉淀前运行。若每个互动步骤都强制深查，延迟和调用次数会接近翻倍。
